# Opus 5.5 architecture review

# TWINGS KAIPER 셀프서비스 아키텍처 사전 리뷰 (Opus 5.5)

이 리뷰는 구현 전 설계 위험을 검토한 것입니다. 소스 승인이나 최종 Fable 리뷰가 아닙니다. 제공된 문서와 코드만 읽었고, 실행·DB·브라우저 증거는 없습니다.

## 결론

첫 구현으로 안전하게 만들 수 있는 범위는 다음과 같습니다.

- 초대 → 가입/로그인 → 캠페인 복귀
- 참여자별 비공개 대화·파일
- 위험 신호 검토함과 Slack outbox (외부 발송은 닫힘)
- 관리자 정보구조 개선
- 대리 제작 동의·약관의 **초안 문서**
- 캠페인 결제 상태기계 (가짜 게이트웨이와 닫힌 플래그로만)

실결제, 지급, 대리 얼굴 저장·생성, Slack 실발송, 약관 원문 교체, 클라우드 migration은 모두 닫힌 상태로 남겨야 합니다. 이것은 문서의 경계와 일치합니다.

다만 아래 두 가지는 브랜드 화면을 확장하기 전에 고쳐야 할 코드 수준 차단점입니다.

## 차단점

### 코드·설계 결함 (구현 전 수정)

**C1. 캠페인과 브랜드 테넌트 일치 검증이 없음**
- `configureCampaignProduction`(lib/campaigns/production.ts)은 임의의 `campaignId`를 임의 프로젝트의 계약에 묶을 수 있습니다.
- `loadCampaignParticipation`은 `b.project_id` 기준으로 참여 현황과 게시 URL을 돌려줍니다.
- 관리자가 한 번만 잘못 연결해도 브랜드 A의 참여자 정보가 브랜드 B에 노출됩니다.
- 대화·파일이 이 연결을 재사용하면 피해 범위가 커집니다.
- 조치: `campaigns`에 소유 조직 또는 프로젝트를 명시하고, 설정 시 `campaign.organization_id = project.organization_id`를 강제합니다. 가능하면 복합 FK로 겁니다.

**C2. `rejected`의 의미가 섞여 있음**
- `blocked()`는 `['selected','rejected']`에 생성을 허용하고, 참여 집계는 `rejected`를 선정 수에 포함합니다.
- `rejected`가 "게시 반려(재제출 가능)"라면 맞습니다. "지원 불합격"이라면 비선정자가 계약 수량을 쓰게 됩니다.
- 조치: enum을 `application_rejected` / `post_rejected`로 분리하거나, 현재 의미를 스키마 주석과 테스트로 고정합니다.

**C3. 단일 상태 컬럼이 원칙 3과 충돌함**
- `campaign_applications.status`가 `posted → verified → paid`를 한 열로 표현합니다.
- 결제 환불이나 검수 철회 같은 역방향 사건을 표현할 수 없고, `paid`가 "관리자가 참조를 기록함" 이상을 증명하지 않습니다.
- 1차에서는 그대로 두되, UI 문구를 "지급 기록됨"으로 표시합니다.
- 별도 `campaign_payouts`(기록자, 참조, 시각, 금액 스냅샷)는 지급 단계에서 분리합니다.

**C4. 락 순서가 문서화되어 있지 않음**
- 예약 경로의 락 순서: campaigns → campaign_productions → brand_projects(share) → contract(update) → application.
- 브랜드 스튜디오 제작 경로나 프로젝트 보관/상태 변경이 contract나 project를 먼저 잠그면 교착이 생길 수 있습니다.
- 대화·초대·결제 같은 신규 경로도 이 루트 락 순서를 따라야 합니다.

### 외부·법무 의존 (닫힌 상태 유지)

**L1. 브랜드 결제**
- 가격·수수료·환불·세금계산서 규칙이 정해지지 않았습니다.
- 자금 흐름 구조가 미정입니다. TWINGS 자체 용역 매출인지, 크리에이터 보상의 대행 수령인지에 따라 전자금융·정산 규제 검토 범위가 달라집니다.
- 법무 확인 전에는 "TWINGS 서비스 대금" 구조로만 설계합니다. 브랜드 돈을 크리에이터에게 넘기는 장부는 만들지 않습니다.

**L2. 지급**
- 토스 지급대행 계약과 seller 등록이 필요합니다.
- 원천징수와 지급명세서 처리를 세무 검토해야 합니다.
- 계좌정보 수집도 아직 하지 않습니다.

**L3. 대리 얼굴**
- 정보주체 동의가 필요하고, 초상·퍼블리시티 관련 법무 검토가 필요합니다.
- 제공사(seedance) 약관이 실존 인물 대리 업로드를 허용하는지 확인해야 합니다.
- 미성년자 처리 기준이 필요합니다.
- 본인 확인 전에 제3자가 올린 얼굴 사진을 **저장하는 것 자체가** 수집입니다. 따라서 1차에서는 업로드 경로를 만들지 않습니다.

**L4. 약관·개인정보처리방침**
- 개정 시 사전 공지 기간을 법무가 판단해야 합니다.
- 비공개 메시지를 위험 분류기로 읽는 목적을 처리방침에 고지해야 합니다.
- 운영에서 스캔을 켜는 것은 고지 승인 이후입니다.

**L5. 기타 외부 의존**
- Slack 실발송: 봇 토큰과 실발송 승인이 필요합니다. 채널 `C0C9DRS4DT7`이 생성됐다는 것은 연동 완료의 증거가 아닙니다.
- 로컬 AI 호스팅: 운영 런타임에서 모델을 실제로 돌릴 수 있는지 미확인입니다. 규칙 기반 판독기를 기본으로 하고, 모델은 선택 adapter로 둡니다.
- Migration: 0045/0130과 신규 migration 모두 대표/Director가 적용합니다.

## 상태기계

**초대**
- `issued → accepted | revoked | expired`
- 수락 시 `user_id`에 바인딩합니다. 같은 사용자가 다시 수락하면 같은 결과를 돌려주고, 다른 사용자가 수락하면 거절합니다.
- 토큰은 해시로만 저장합니다.
- 복귀 대상은 서버에 저장된 `campaign_id`로 정합니다. `returnTo` URL 파라미터는 받지 않습니다 (open redirect 방지).
- 수락의 결과는 `applied` 지원서입니다. 개인 초대에 `preselect`가 붙은 경우에만 campaigns 행 락 아래에서 인원을 확인하고 `selected`로 만듭니다.
- 수락은 `brand_members`에 어떤 행도 쓰지 않습니다.

**지원서**
- `applied → selected → posted → verified → paid`
- 이탈 상태: `application_rejected`, `post_rejected → posted`(재제출), `withdrawn`
- 게시 링크 제출(`posted`)은 자기 주장일 뿐입니다. 브랜드 화면에는 "제출됨·미검수"로 구분해 표시합니다. 현재 `loadCampaignParticipation`은 `posted` URL을 그대로 노출합니다.

**대화 스레드**
- 단위: `(campaign_id, application_id)`, 지원서당 하나.
- 상태: `open → read_only`(철회, 불합격, 캠페인 종료 시)
- 메시지 상태: `sent → hidden_by_admin`. 하드 삭제는 보존 정책이 정해질 때까지 하지 않습니다.
- 접근 주체:
  - 해당 크리에이터 본인
  - 캠페인 소유 프로젝트의 **현재** 권한 있는 브랜드 멤버 (매 요청마다 재확인)
  - 관리자: 목적 사유를 입력해야 열람할 수 있고, 열람 이력이 기록됩니다.

**파일**
- `uploading → ready | rejected → deleted(soft)`
- 비공개 버킷, MIME/크기 검사, 짧은 서명 URL을 사용합니다.
- 파일은 스레드 단위로 격리하고, 다른 지원서 ID로는 조회할 수 없습니다.

**보상 조건 제안**
- `proposed → accepted | declined | withdrawn | superseded`, 리비전 포함.
- 1차에서는 **비구속 기록**입니다. 지급 금액의 원천이 아니며 결제나 지급 장부를 건드리지 않습니다.
- UI에 "TWINGS 확정 전 효력 없음"을 표시합니다.

**캠페인 결제** (usage 패턴 복제, 별도 테이블)
- `studio_quote(issued → accepted | expired | superseded)`
- `order(pending → confirming → paid | failed | review | expired → refund_pending → refunded)`
- 금액은 관리자가 발행한 견적에서만 옵니다. 브라우저가 보낸 금액은 일치 여부만 확인합니다.
- `paid`는 캠페인 공개, 제작 허용, 계약 수량 증가, 지급 중 어느 것도 일으키지 않습니다.
- 부분 환불은 지원하지 않습니다 (`PARTIAL_CANCELED → review`). 환불은 관리자의 전액 결정만 허용합니다.
- 플래그 `CAMPAIGN_PAYMENTS_OPEN`의 기본값은 off입니다. 운영(production)에서는 live 키와 `liveEnough` 조건을 동시에 요구합니다.

**위험 신호**
- 스캔 상태: `unscanned → scanned | scan_failed`
- 플래그: `open → acknowledged → dismissed | actioned(사람 기록)`
- Slack outbox: `pending → sent | failed(n회) | suppressed(중복)`
- 중복 키는 `(subject_id, category, 시간창)`입니다.
- 분류기 출력은 enum 카테고리와 점수, 모델/규칙 버전뿐입니다. 메시지 안의 텍스트는 실행 대상이 아닙니다.

**대리 제작 동의**
- 1차에서는 스키마 초안(인물·브랜드·캠페인·포맷·기간·용도, 버전, 철회)과 문서만 만듭니다. 쓰기 경로는 만들지 않습니다.

## 권한·프라이버시 불변식

1. 캠페인 참여는 `brand_members`를 만들지 않습니다. 브랜드 프로젝트 API는 크리에이터에게 계속 403/404를 반환합니다.
2. 참여자는 다른 참여자의 스레드, 파일, 보상 제안, 결과, 인원 정보를 볼 수 없습니다. 조회 수단은 ID 열거, 목록, 카운트 응답, 서명 URL 재사용을 모두 포함합니다.
3. 브랜드는 게시 전 렌더, 입력 사진, 프롬프트, 계약 ID, 스토리지 키를 볼 수 없습니다 (기존 규칙 유지).
4. Slack에는 플래그 ID, 카테고리, 관리자 링크만 보냅니다. 다음은 보내지 않습니다:
   - 원문 메시지
   - 이름·이메일
   - 얼굴 이미지
   - 계좌정보
   - paymentKey
   - 브랜드명·캠페인명 (기밀일 수 있음)
5. 위험 분류기는 DB 읽기와 플래그 insert 외의 권한이 없습니다. 결제, 권한 변경, 제재, 생성 함수를 import할 수 없습니다 (모듈 경계 테스트로 확인).
6. 모든 신규 테이블은 RLS enable/force를 켜고 public/anon/authenticated 권한을 회수합니다. 접근은 service_role만 허용합니다. 스키마가 없으면 닫힌 상태로 응답합니다 (`campaignProductionSchemaReady` 패턴).

## 권장 1차 구현

**포함**
- 위 C1, C2 수정과 C4 락 순서 문서·테스트
- 초대 발급·철회, 링크 복사 (메일 발송 없음), 가입·로그인 후 복귀, 지원서 생성
- 스레드·메시지·파일, 브랜드 멤버 권한 재확인, 관리자 열람 감사 로그
- 보상 제안 기록 (비구속)
- 위험 규칙 판독기, 검토함 UI, Slack outbox
  - Slack 전송기는 fake만 테스트합니다.
  - `RISK_SLACK_ALERTS` 기본값은 off입니다.
- 캠페인 견적·주문·확인·대사 로직 (fake 게이트웨이, 플래그 off)
  - 기존 `lib/brands/usage/payment.ts`는 수정하지 않습니다.
  - 공통화가 필요하면 순수 함수(snapshot 분류)만 추출하고, 기존 usage 테스트 전량 통과를 조건으로 합니다.
- 관리자 정보구조: 브랜드 → 캠페인 준비 → 포맷/계약 → 참여자 → 제작/납품 → 검수/지급, 각 단계에 "현재 상태·막힌 이유·다음 행동" 표시. 한국어와 영어 모두.
- 대리 제작 동의서와 약관·처리방침 변경안 초안 (`docs/legal/drafts/`, 서비스 원문은 교체하지 않음)

- 대리 얼굴 업로드·저장·생성
- 위험 신호 기반 자동 조치

## 수용 테스트 (실제 DB: PGlite 또는 Postgres)

**테넌트·권한**
- T1. 조직 X의 캠페인을 조직 Y의 계약에 연결하면 거절됩니다. Y 멤버의 `loadCampaignParticipation` 결과는 빈 배열입니다.
- T2. `application_rejected` 상태의 지원자는 생성이 거절됩니다 (`not_selected`). `post_rejected`는 기존 규칙대로 동작합니다.
- T3. 초대를 수락해도 `brand_members` 행 수가 변하지 않습니다. 크리에이터가 브랜드 프로젝트 API를 호출하면 거절됩니다.
- T4. 참여자 A가 B의 스레드·파일·제안 ID로 조회, 다운로드, 서명 URL 재사용을 시도하면 전부 404입니다. 목록과 카운트에도 B의 흔적이 없습니다.
- T5. 브랜드 멤버의 권한을 회수한 직후, 다음 요청부터 스레드 읽기·쓰기·파일 다운로드가 거절됩니다.
- T6. 관리자가 사유 없이 스레드를 열면 거절됩니다. 사유를 입력하면 열람되고 감사 로그 1행이 생깁니다.

**초대**
- T7. 신규 가입과 기존 로그인 모두 수락 후 해당 캠페인으로 복귀합니다. `returnTo` 파라미터는 무시됩니다.
- T8. 만료, 철회, 다른 사용자의 수락은 거절됩니다. 같은 사용자의 이중 수락은 지원서 1개, 같은 응답입니다.
- T9. 남은 1자리에 `preselect` 초대 두 건을 동시에 수락하면 정확히 1건만 `selected`가 됩니다.

**메시지·파일**
- T10. 같은 `requestId`로 메시지를 두 번 보내면 1행만 저장됩니다. `read_only` 스레드에 쓰기는 거절됩니다.
- T11. 파일 MIME, 크기, 개수 초과는 거절됩니다. 업로드가 중단되면 `ready`가 되지 않습니다.

**결제** (fake 게이트웨이)
- T12. 클라이언트 금액이 견적과 다르면 `amount_mismatch`이고 게이트웨이 호출은 0회입니다.
- T13. confirm 타임아웃 시 상태는 `confirming`으로 유지되고, 대사에서 DONE을 받아 `paid`가 됩니다. 새 주문은 생성되지 않습니다.
- T14. `paid`가 된 뒤에도 캠페인 공개, `campaign_productions.enabled`, `generation_limit`, 지원서 상태가 변하지 않습니다.
- T15. 운영 환경과 test 키 조합, 또는 플래그 off에서는 `payments_closed`입니다.
- T16. 같은 주문에 대해 `confirm`이 동시에 들어오면 하나만 `confirming`이 되고 나머지는 `already_processed`입니다.
