## 2. 결제 — 오류 없이 열기

### 2.1 원칙
- 결제 로직은 `lib/billing/*`·`lib/auth/purchase-gate.ts` 한 경로만 쓴다. 금액은 서버 저장가(`chargeKrwFor`)만, 브라우저 금액은 쓰지 않는다(이미 그렇다).
- 개방은 코드가 아니라 환경이다: 라이브 키 교체 → `RENDER_PIPELINE_PUBLIC=on` → 재배포. 순서는 `docs/qa/toss-checkout/README.md` "운영 개시".

### 2.2 감사 결과 (2026-10-22, main 866f168 읽기 전용)

**견고한 것**: 금액은 서버 저장가만 쓰고 승인 응답과 대조한다. 같은 주문의 중복 승인·성공 URL 재생은 행 잠금으로 `already_processed`(409). 렌더 작업 생성은 멱등. 오류 메시지에 키·내부 정보가 없다. 승인 유실은 `reconcileTossPayments`가 주문번호로 다시 확인해 이행한다.

**고쳐야 하는 것** (브랜치 `payment-hardening`, 전부 테스트 선행):

## 3. 첫 경험 — 로그인부터 첫 결과물까지

### 3.1 지금의 막힘
- `RENDER_PIPELINE_PUBLIC`이 `on`이 아니면 일반 계정은 "곧 열립니다" 패널에서 끝난다(의도된 상태). 개방 뒤에도 아래가 남는다.
- 템플릿 페이지가 정적이라 스튜디오가 먼저 "닫힘"으로 그려졌다가 `/api/renders/access` 응답 뒤 바뀐다(모바일에서 깜빡임).
- `#make`가 길게 스크롤해야 나온다. 카메라 버튼이 없다(PR #76이 추가).
- 결과 대기 페이지는 "기다리세요"뿐이고 예상 시간·알림 약속이 없다.
- 첫 방문자에게 "무엇을 어떻게 하는 곳인지" 말해주는 화면이 없다.

### 3.2 설계 (모바일 우선, 데스크톱은 같은 구조)
1. **가입 직후 1회 시작 시트** (`profiles.onboarded_at`, 건너뛰기 가능): 세 장 — "① 포맷을 고르세요 ② 정면 셀카 한 장 ③ 완성되면 알려드려요". 마지막 장에 "내 사진 미리 올려두기"(선택) + "포맷 보러 가기".
2. **템플릿 페이지**: 예시 결과물이 첫 화면에서 음소거 자동재생(이미 쇼릴 규칙과 같은 조건). 모바일은 **하단 고정 CTA** "내 얼굴로 만들기 · 3,900원"(가격은 템플릿 페이지에서만 노출한다는 규칙 유지). 누르면 셀카 시트(§4) → 결제. 스튜디오 초기 상태는 "닫힘"이 아니라 **중립 스켈레톤**으로 그리고 접근 응답으로 확정한다.
3. **결제 직전 한 줄**: "보통 N분 걸려요. 완성되면 알려드릴게요." N은 엔진·길이별 실측 중앙값(`render_jobs` 완료 시간으로 계산, 표본 10건 미만이면 엔진 기본값).
4. **대기 페이지**: 단계 셋(사진 확인 → 만드는 중 → 마무리) + 알림 선택(푸시/이메일, §5) + "기다리는 동안 다른 포맷 보기". 6초 폴링은 탭이 보일 때만, 2분 뒤부터 15초로 늦춘다.
5. **결과 페이지**: 다운로드·공유 카드(§12 "공유 카드" 결정: OG = 내 프레임 + 나도 만들기) · 별점 · "문제 알리기"(기존) · "다른 포맷으로 또 만들기".
6. 문안은 전부 사전(`messages/*.ts`), 창업자 톤. 새 마커 `data-onboarding-sheet`, `data-make-cta`, `data-render-stage`, `data-notify-choice`.

## 4. 내 얼굴 — 최대 10장 보관, "이 얼굴로 만들까요?"

PR #76의 `identity_selfies`를 그대로 확장한다(새 테이블 없음).

- **데이터**: "계정당 현재 1장" 부분 유니크 인덱스를 **활성 사진 최대 N장**(N=`IDENTITY_SELFIE_LIMIT`, 기본 1 → 약관 문구 갱신 뒤 10) 검사로 바꾼다. 컬럼 추가: `is_default`, `last_used_at`, `deleted_at`, `label`(선택, "안경", "긴 머리" 같은 메모). 중복은 라이브러리 전체 sha256으로 판정.
- **API**: `GET /api/identity/selfie` → 목록+기본, `POST` 저장(동의 필수, 하루 20회), `PATCH` 기본 지정/라벨, `DELETE` 소프트 삭제(저장 파일은 계정 삭제 런북에 포함).
- **화면**: 템플릿의 만들기 지점에서 저장된 사진이 있으면 **시트** 하나 — 기본(또는 마지막 사용) 사진 크게 + "이 얼굴로 만들까요?" + [이 사진으로 만들기] [다른 사진 고르기 ▸ 썸네일 그리드 + 새로 찍기]. 사진이 없으면 인라인 업로더(PR #76 그대로). 계정 페이지는 그리드(최대 10) + 기본 표시 + 삭제.
- **안전장치(불변)**: 본인 사진 동의 없이는 저장 안 됨, 제공사 검수·자산 대조·신고 24시간 검토 그대로. 각도·밝기 판정은 권고만. 한 계정의 사진은 **같은 사람**이어야 한다 — 자동 판정은 하지 않고(얼굴 매칭은 권고 범위를 넘는다) 약관과 신고로 다룬다.
- **은행 용량**: 렌더 뒤 삭제(`ARK_RELEASE_AFTER_USE`)가 켜져 있으면 10장이어도 무료 등급 50칸을 넘지 않는다. 끄면 사람당 10자산이 되므로 그때는 유료 등급 전환과 같이 결정.
- **약관**: 현재 §5.3은 "본인 얼굴 사진 한 장"·"계정당 인물 자산 그룹 1개"다. 10장은 "같은 사람의 사진 최대 10장"으로 문구만 바뀌고 그룹 1개 원칙은 그대로다. **문안은 대표 승인**(§13).

## 5. 모바일 — 앱처럼, 그리고 앱으로

### 5.1 결정이 필요한 사실: 스토어 앱과 5% 마진은 같이 못 간다
> **2026-10-28 대표 결정으로 대체됨 → §19.** 아래 26%·×1.4는 한국 제3자 결제 기준이었다. 스토어 기본 결제는 소규모 사업자 요율 15%라 앱 안 결제가 성립한다. 아래는 당시 기록으로 남긴다.

- 앱 안에서 디지털 결과물(영상·이미지)을 파는 앱은 Apple·Google 인앱결제 대상이다. 한국은 2022년부터 제3자 결제를 허용하지만 Apple 수수료는 **26%**(2022년 발표 기준, 최신 수치는 개발자 문서 재확인 필요)이고 PG 수수료는 별도다. 템플릿 원가 플로어 마진이 5%인 지금 구조에서는 앱 안 결제가 성립하지 않는다.
- **PWA(홈 화면 설치)는 이 문제가 없다.** iOS 16.4+에서 설치한 웹앱은 푸시 알림·배지를 받는다(설치 필수, 브라우저 탭에서는 불가, 권한 요청은 사용자 동작 뒤). Android는 설치형 PWA + 푸시가 안정적이다.

**추천 경로**
1. **지금: PWA를 "앱"으로 완성한다** — 설치 안내, 앱 셸, 푸시, 카메라. 결제는 그대로 토스. 비용 0, 심사 없음.
2. **다음: 스토어 앱은 "구매 없는 동반 앱"으로** — 내 작품·알림·캠페인·탐색만 하고 결제는 웹에서(Capacitor 래퍼 + 네이티브 푸시 + 딥링크). 인플루언서 캠페인이 붙으면 구매 없이도 앱의 이유가 생긴다. Apple 3.1.1/4.2 심사 위험이 있으므로 그때 다시 판단.
3. 앱 전용 가격(웹가 ×1.4 내외)으로 인앱결제를 받는 길은 **권하지 않는다**(같은 상품 두 가격).

→ 대표 결정 §13-1.

### 5.2 앱 셸 (설치형 모드 전용)
- `display-mode: standalone`일 때만 **하단 탭 4개**: 포맷 · 캠페인(인플루언서) 또는 내 작품 · 내 사진 · 계정. 템플릿 만들기 화면처럼 하단 고정 CTA가 있는 페이지에서는 탭을 숨긴다(2026-10-07 "하단 고정 UI 없음" 결정은 브라우저 모드에 그대로 둔다).
- `viewport-fit=cover` + `env(safe-area-inset-*)`, 상태바 색은 브랜드 bg(#0A0A0A) — 지금 manifest의 흰색 theme은 v1.2 Dark Brand와 맞지 않는다.
- manifest: 192/512 `maskable` 아이콘, `screenshots`, `shortcuts`(포맷 보기·내 작품), `start_url=/{locale}/video?source=pwa`, `id` 고정.
- 설치 안내: Android `beforeinstallprompt` 저장 후 첫 결과물 뒤에 1회 제안, iOS는 공유 시트 안내 카드 1회. 둘 다 "다시 보지 않기".
- 헤더 셋(공개/앱/계정)을 하나의 `AppChrome`으로 합친다. 공개 페이지는 정적 유지.
- 화면 전환: View Transitions API(지원 브라우저만), 시트는 CSS 트랜지션. 외부 라이브러리는 기본 추가하지 않는다(필요하면 §13-11).
- 서비스워커: `public/sw.js`에 `push`·`notificationclick` 핸들러 추가, 내비게이션 network-first 유지.

### 5.3 완성 알림 (긴 작업일수록 중요)
- **푸시(설치형 PWA)**: `push_subscriptions`(user_id, endpoint, p256dh, auth, user_agent, created_at, last_seen_at, revoked_at) + VAPID 키(Vercel 환경변수) + `RenderNotifier` 구현 `push`. 결제 직후 "완성되면 알려드릴까요?"에서 권한 요청(사용자 동작 뒤). `render_jobs.notify_channel` CHECK에 `push` 추가.
- **이메일**: 항상 보낸다(기존). **버그 수정**: 이메일 없는 카카오 계정은 콜백에서 빈 값을 저장하지 말고 `/account`에서 이메일을 받거나 푸시로 대체한다.
- **카카오 알림톡**: 번호 인증 + 채널·템플릿 심사가 선행(대표 할 일 §10 3번). 어댑터만 추가하면 되는 구조는 이미 있다. 2단계.
- 알림 본문은 사전에, 링크는 `/renders/{id}`. 실패도 이유와 함께 알린다(이미 메일은 그렇다).

## 6. 인플루언서 — 팔로워 3,000+에게 열리는 캠페인

### 6.1 자격
- **인플루언서 = 연동된 Instagram 또는 TikTok 계정 중 하나라도 팔로워 ≥ 3,000**. 합산이 아니라 단일 계정 기준(§13-4에서 확인).
- 연동 경로
  - Instagram: "Instagram API with Instagram Login"은 **프로페셔널(비즈니스·크리에이터) 계정만** 연결되고 팔로워 수를 돌려준다. 개인 계정은 API로 검증할 수 없다.
  - TikTok: Login Kit + `user.info.stats` 범위(`follower_count`). 앱 심사 선행.
  - **수동 경로**(API 승인 전·개인 계정): 프로필 링크 + 팔로워 화면 캡처 → 관리자 확인 → `source=manual`. 화면에는 "확인됨 · 2026-10-22" 식으로 출처와 날짜를 보여준다.
- 데이터: `social_accounts`(id, user_id, platform instagram|tiktok|youtube, external_id, handle, follower_count, measured_at, source api|manual, token_encrypted, token_expires_at, status active|revoked, created_at) + `profiles.influencer_since`(자격 생긴 시각, 자동 계산). 90일마다 재측정, 3,000 미만으로 떨어져도 참여 중 캠페인은 유지.
- 전부 서버에서 판정한다(`loadApplyState`·`applyToCampaign`·`acceptInvitation`). 화면만 숨기지 않는다.

### 6.2 캠페인 탭
- 내비·하단 탭의 "캠페인"은 인플루언서에게만 보인다. 일반 사용자에게는 계정 페이지에 **문 하나**: "인스타그램·틱톡을 연결하면 브랜드 캠페인으로 콘텐츠도 만들고 수익도 생겨요"(§13-5: 티저 노출 여부).
- 캠페인 목록은 **뷰어별·무캐시**로 바꾼다(`force-dynamic`, `private, no-store`). `campaigns.audience` = `public | influencers | invited` + `campaign_targets`(campaign_id, user_id, invited_by, invited_at) — "특정 사람에게만"을 표현한다. 공개 마케팅 페이지 `/{locale}/campaigns`는 `public`만 보여준다.
- 카드(Brandazine 셀프 캠페인 화면에서 배운 것 + 우리만 할 수 있는 것): 포맷 미리보기 영상 · 보상(범위) · 선정 N명 · 조건(플랫폼·팔로워·성별 등 브랜드 조건) · 기간 · **"내 얼굴로 미리 보기"**(결제 없이 포맷 예시를 내 셀카로 1장 이미지 프리뷰 — 원가가 있으므로 §13-6에서 허용 여부). 지원 → 선정 → 제작(지정 템플릿, 결제 없음) → 게시 링크 → 검수 → 정산은 기존 상태 머신 그대로.

### 6.3 브랜드 셀프서비스 (brand.twings.app)
- **캠페인 만들기 마법사**: ① 포맷 고르기(오리지널·작가 포맷·브랜드 전용 제작) ② 보상(고정/조회수/혼합 — 기존 payout 규칙)과 예산 ③ 대상(전체 인플루언서 / 조건 / 지정 크리에이터 선택) ④ 기간·슬롯·게시 조건(광고 표기 필수) ⑤ 검토 요청. **TWINGS 승인 전에는 공개되지 않는다**(지금처럼 관리자가 상태를 바꾼다).
- **크리에이터 풀**: 동의한 인플루언서만 노출(핸들·플랫폼·팔로워 구간·대표 작품). 연락처·실명 없음. 브랜드는 "초대"만 할 수 있고 선정은 TWINGS.
- **지원자 보기 · 결과 리포트**: 기존 참여자 화면 확장(게시 링크·조회수·METRICS 출처 표시). Meta/TikTok 지표 API 연동은 토큰이 있을 때만, 아니면 self/admin 출처 그대로.
- **결제**: 기존 2차 활용 결제 패턴(`lib/brands/usage/payment.ts`, `TossGateway`, 서버 확정 견적)을 캠페인 결제에 재사용. KAIPER 문서의 "결제만으로 선정·검수·지급을 완료 처리하지 않는다" 원칙 유지.
- 새 경로는 `isBrandPath`·`brandRouteAllowed`에 등록해야 브랜드 호스트에서 404가 나지 않는다.

## 7. 템플릿 메이커 — AI 크리에이티브가 워크플로우를 올리는 경험

### 7.1 용어 (혼동 방지)
- **템플릿 메이커(메이커)** = AI 크리에이티브(공급자). 노트북·데스크톱에서 작업한다. 호칭의 원본은 §14.2다 — 이 절 이하와 §8·§10·§11에 남은 "작가"는 전부 "메이커"로 읽는다(2026-10-24 확정, PR #94가 사전을 교체했다).
- **인플루언서** = 캠페인 참여자(§6). **사용자** = 결과물을 사는 사람.
- 한 계정이 셋 다일 수 있다. 역할은 자격(작가 승인, 인플루언서 자격)으로만 생긴다.

### 7.2 Higgsfield 블로그에서 배운 것 (2026-10-22, @kaye_creatives 조회수 상위 글)
- 글 구조: 인사 → **Step 1 캐릭터 시트**(셀카를 `@image`로 태그한 프롬프트 + Recreate 버튼) → Step 2 자산·장소 참조 이미지 → Step 3 샷별 **이미지 프롬프트 + 비디오 프롬프트**(각각 "Copy prompt"·"Recreate"). 조회수 1만 전후, 좋아요 50 전후.
- 댓글에 "5번 돌렸는데 하나도 안 닮았다"가 있다. 공유된 프롬프트는 재현이 보장되지 않는다 — 우리가 더 잘할 지점은 **검증된 재현**(스튜디오 테스트 렌더 통과 뒤 공개)과 **얼굴 자동 결속**(사용자는 태그를 몰라도 된다).
- 그대로 따오지 않는 것: 프롬프트 복사 버튼이 기본인 구조. 우리는 "만들기"가 기본이고, 레시피 공개는 작가 선택이다.

### 7.3 레시피 v2 — 단계와 슬롯
`prompt_items.prompt_text`(단일 문자열)를 유지하면서 `prompt_items.recipe`(jsonb, 서버 전용)를 추가한다. `recipe`가 있으면 파이프라인은 그것을 쓰고, 없으면 지금처럼 `prompt_text` + 사진 1장이다(기존 9편은 변경 없음).

```jsonc
{
  "version": 2,
  "slots": {
    "selfie":  { "kind": "image", "source": "user", "required": true },      // 항상 image1 = 사용자 얼굴
    "product": { "kind": "image", "source": "creator", "asset": "ast_…" },   // 작가가 올린 참조(비공개 저장)
    "scene":   { "kind": "image", "source": "creator", "asset": "ast_…" }
  },
  "steps": [
    { "id": "sheet", "kind": "image", "engine": "seedream-5.0-pro",
      "inputs": ["selfie"], "prompt": "Character reference sheet … {{selfie}} …",
      "params": { "aspect": "16:9" } },
    { "id": "shot1", "kind": "video", "engine": "seedance-2.5",
      "inputs": ["sheet", "scene"], "prompt": "… {{sheet}} … {{scene}} …",
      "params": { "aspect": "9:16", "duration": 10, "resolution": "720p" } }
  ],
  "output": { "from": "shot1" }            // 캐러셀은 { "frames": ["f1","f2",…] } 1~6장
}
```

- `{{slot}}`·`{{step}}`은 엔진별 참조 문법으로 치환된다(ModelArk `Image 1/2`, OpenAI 다중 이미지, Kling 참조 이미지). 작가는 엔진 문법을 몰라도 된다.
- **1차 범위**: 단계 최대 2(이미지 1 + 영상 1) 또는 이미지 1~6(캐러셀). 영상 2개 이상을 이어 붙이는(ffmpeg 합성) 템플릿은 2차 — Vercel 함수 안에서 못 하고 별도 워커가 필요하다.
- 엔진 추가: **Kling**(공식 API, 이미지→영상·다중 참조), **Nano Banana 계열**(Gemini 이미지 API). 각 엔진의 **실인물 정책**을 스모크로 먼저 확인하고(`needsIdentity` 매트릭스), 통과한 엔진만 작가 선택지에 올린다. Kling 4.0·Seedance 2.5·GPT Image 2.5·Nano Banana·Seedream 5.0 Pro 단가는 §9.
- **비공개 템플릿의 사용자 경험**: 셀카 한 장만 넣으면 끝. `selfie` 슬롯이 유일한 사용자 입력이라는 제약을 **제출 시 검증**한다(작가 자산은 전부 `source: creator`).
- **공개 템플릿**: 작가가 `disclosure = { prompts: true, assets: true|false }`를 고르면 템플릿 페이지에 "만드는 법" 섹션이 열린다 — 단계별 프롬프트(슬롯은 `[내 사진]`으로 표시) + 복사 버튼 + 작가 자산(공개 선택 시). 공개해도 판매는 같다(원클릭·검증·얼굴 결속이 가치).
- **페이지 순서**: `presentation = make-first | story-first`. 기본 make-first(예시 → 만들기 → 설명). story-first는 설명·과정이 먼저, 만들기가 아래. 작가가 고른다.

### 7.4 작가 흐름 (데스크톱)
1. `/{locale}/creators` 프로그램 소개 → `/creators/apply` 지원(활동명·포트폴리오·샘플·매체·도구·메시지·권리 확인) → 관리자 승인. (`codex/creator-onboarding`에 구현돼 있다 — 리베이스해 쓴다.)
2. `/creators/workspace`: 내 포맷 목록·상태·검수 메모·정산 현황. (같은 브랜치.)
3. **새 포맷 등록** (새로 만든다): 한 화면 좌우 분할 —
   - 왼쪽: 제목(ko/en) · 매체(영상/이미지/캐러셀) · 엔진 · 단계 편집기(프롬프트, 슬롯 끼워 넣기 버튼 `[내 사진]`·`[참조 1]`, 파라미터) · 작가 자산 업로드 · 예시 결과물(필수, 작가 본인 얼굴 또는 권리 있는 얼굴) · 공개 범위 · 페이지 순서 · 희망 로열티(§8).
   - 오른쪽: **미리보기**(템플릿 페이지가 어떻게 보일지) + **테스트 렌더 1회**(작가 본인 셀카, 작가 부담 없음·TWINGS 원가 부담, 포맷당 N회 제한).
   - 제출 → 스튜디오 검수(테스트 셀카 3장으로 렌더 → 얼굴 유지·정책 통과) → 가격·번역·미디어 확정 → 공개. 공개 뒤 수정은 새 버전(기존 규칙).
4. 레시피 **가져오기/내보내기 JSON**(이 스키마 그대로). Higgsfield 등 다른 도구의 프롬프트는 붙여넣기 + 자산 업로드가 1차 경로다(§11).

### 7.5 카탈로그 — "TWINGS 오리지널"과 "메이커 템플릿"
- 카드 크레딧: 오리지널은 없음, 메이커 템플릿은 `by @handle`. 템플릿 페이지에 메이커 블록(핸들·소개·"메이커 프로필 보기") → `/{locale}/makers/[handle]` 공개 프로필(메이커가 `public_profile`을 켠 경우만, 트리거가 `author_handle`을 채우고 끄면 비운다 — 0060). 구현: PR #94.
- VIDEO·IMAGE 탭은 유지. 각 탭 안을 레일로 나눈다: **TWINGS 오리지널** → **메이커 템플릿**(메이커 템플릿이 0편이면 두 번째 레일이 나오지 않는다) → **인기**(결제 수 기준, 임계치 전엔 숨김 — 미구현). 출처를 고르는 칩은 두지 않는다. 레일 제목이 출처를 말한다(대표 2026-10-28, §15.6).
- 둘 다 스튜디오 검수를 거치므로 "검증됨" 배지는 공통이다. 한국어 표기는 §13-10.

## 8. 작가 수익 — 숫자는 대표가 정한다

> **2026-10-28 대표 결정으로 바뀜 → §19.3.** 구독제에서 메이커는 템플릿에 얹은 크레딧을 가져간다. 아래 80/20과 원화 R은 단건 판매 기준 기록이다.

### 8.1 이미 기록된 결정
`docs/CREATOR-PLATFORM.md`: **작가 80% / TWINGS 20%, 매출이 아니라 배분 대상 이익(매출 − 부가세 − 환불 − 제공사 원가 − 결제 수수료) 기준.** 코드(`lib/creator-platform/economics.ts`)도 이 규칙이다. 대표가 "비율은 아직 생각 안 했다"고 했으므로 이 결정이 유효한지 먼저 확인한다(§13-2).

### 8.2 문제: 5% 플로어 가격에서는 80%가 거의 0이다
예: 3,900원 템플릿(목표 마진 5%) → 배분 대상 이익 약 180원 → 작가 몫 약 140원/건. 작가를 모을 수 없는 숫자다.

### 8.3 제안: 작가 가산 로열티 (기존 80/20 규칙은 그대로)
- 작가 템플릿 판매가 = **원가 플로어(5% 포함) + 작가 로열티 R**. R은 작가가 범위 안에서 정한다(예: 500~5,000원, 기본 제안 1,500원 — 범위·기본값은 대표 결정).
- 배분 대상 이익 = 기존 공식 그대로 → 자동으로 (기본 마진 + R)의 80%가 작가, 20%가 TWINGS. 코드 변경은 "가격 = 플로어 + R"뿐이고 정산 공식은 손대지 않는다.
- 예: 플로어 3,900 + R 2,000 = 5,900원 → 작가 약 1,740원, TWINGS 약 440원 + 결제·운영.
- 캐러셀: 장당 플로어 합(200~1,100원/장) + R.
- 오리지널은 R=0(지금과 같다).

### 8.4 정산 운영 (전부 대표 결정 항목)
- 주기(월 1회), 최소 지급액, 지급 수단(계좌이체 수동 → 토스 지급대행), 세금(개인 사업소득 3.3% 원천징수 / 사업자 세금계산서), 환불 시 역산, 원가 증빙이 없는 건은 `cost_pending` 유지(기존).
- 작가 공간의 "정산 현황"은 **발생액**이지 송금이 아니다(기존 문구 유지).
- 이미지 전용 보상 크레딧(SNS 게시 보상)은 별개 제도이며 작가 로열티와 섞지 않는다.

### 9.3 Higgsfield·시장 (설계 참고)
- Higgsfield는 공개 API(`api.higgsfield.ai`, 84개 모델)와 공식 MCP(OAuth, 사용자 크레딧 소모)가 있다. **제3자가 다른 사용자의 프로젝트·프롬프트를 읽는 API는 없다.** 공식 MCP는 **그 사용자 본인**의 프로젝트·프롬프트·소스 자산을 읽고 게시할 수 있다.
- 공유 방식: Shots(프롬프트+모델+Recreate), Open Projects("프롬프트 공개 / 숨김" 선택), 평점 포인트와 크레딧 보상. 프리셋·프롬프트 마켓이나 작가 수익 배분은 없다. Earn은 브랜드 캠페인 영상당 지급(1편 상한 $1,000/첫날, $2,500/누적), 제휴 ≤25%.
- 작가 배분 벤치마크: Notion 템플릿 92%−$0.40, Figma 85%, ArtStation 92~95%, Envato 50%, Adobe Stock 33~35%, Civitai 작가가 가격 책정, YouTube 55/45. 디지털 템플릿 마켓은 **85~92%**가 흔하다 — 단, 이들은 원가가 0인 파일 판매다. 우리는 건당 엔진 원가가 있으므로 "매출의 N%"가 아니라 §8.3처럼 **로열티 가산**이 맞다.

## 10. 관리자 (admin.twings.app) — 위 변화를 운영할 수 있게

## 11. MCP는 도움이 되나 (대표 질문)
- MCP는 "에이전트가 도구를 부르는 규격"이다. 작가가 브라우저 폼에 프롬프트를 붙여 넣는 일을 줄여주지는 않는다.
- **Higgsfield 연동**(§9.3): 제3자용 "남의 프로젝트 읽기" API는 없다. 공식 MCP는 작가 **본인** 계정의 프로젝트·프롬프트·자산을 읽을 수 있다. 그래서 가능한 그림은 "작가가 자기 Claude에 Higgsfield MCP와 TWINGS MCP를 둘 다 붙이고 '내 프로젝트 X를 TWINGS 포맷으로 올려 줘'"다 — 작가 쪽 설정이 필요한 파워유저 경로이지, 등록 폼을 대체하지 못한다. 1차 경로는 **붙여넣기 + 자산 업로드 + JSON 가져오기**(§7.4)다.
- **TWINGS MCP 서버**(우리 쪽): 레시피 JSON 스키마(§7.3)를 먼저 공개하면, "레시피 검증 · 테스트 렌더 · 제출" 세 도구짜리 MCP는 그 위에 얇게 얹힌다. 작가 10명이 넘고 에이전트 등록 요청이 생기면 그때 붙인다.
- 결론: **지금은 붙이지 않는다.** 레시피 JSON(가져오기/내보내기)을 설계에 포함해 두고, Higgsfield 블로그의 "Step별 프롬프트" 구조는 우리 등록 화면의 단계 편집기가 그대로 받아들일 수 있게 한다.

## 14. "작가"라는 말이 맞는가 (대표 질문, 2026-10-22)

**판단: 한국어는 "작가"(정식 표기 "포맷 작가")를 유지한다. 영어는 "creator".**

- **왜 "크리에이터"가 아닌가**: twings.app에서 "크리에이터"는 이미 **소비자 쪽** 이름이다. 헤더의 "크리에이터 | 브랜드" 전환, 캠페인 도메인의 `creator_id`(= 인플루언서 참여자), 월 구독 이름 "크리에이터 플랜"이 전부 그 뜻으로 쓰인다. 공급자(워크플로우를 올리는 AI 크리에이티브)까지 "크리에이터"로 부르면 한 화면에서 같은 말이 두 역할을 가리킨다.
- **왜 "작가"인가**: ① 저작과 인세의 뜻을 품는다 — 로열티를 받는 사람에게 맞는 말이고, 웹툰·웹소설·크몽처럼 수익을 나누는 국내 플랫폼이 쓰는 말이다. ② "작품(결과물)·작가 포맷·by 작가" 로 카드·배지·프로필이 한 어휘로 이어진다. ③ 이미 사전(`messages/ko.ts`)과 PR #79가 "포맷 작가"를 쓰고 있어 바꾸면 비용만 든다.
- **주의**: "작가" 혼자 쓰면 문학·회화 느낌이 강하므로, 프로그램 소개·지원서·계약처럼 역할을 설명하는 자리에서는 **"포맷 작가"**, 카드 배지와 템플릿 페이지의 크레딧은 **"작가 ○○"** 처럼 짧게 쓴다. "AI 작가"는 쓰지 않는다(AI가 저자라는 뜻으로 읽힌다).
- **대안이 필요하면**: "메이커"(가볍고 친근하나 범용적), "아티스트"(격은 높지만 프롬프트 워크플로우에는 과장). 둘 다 "작가"보다 로열티 의미가 약하다.
- **영어**: 이 역할의 업계 표준은 "creator"(Higgsfield·OpenArt·Civitai)다. 영어 헤더의 "Creators | Brands"도 소비자 뜻이라 같은 충돌이 있으므로, 영어 사이트의 전환 라벨을 "For you | Brands" 류로 바꾸는 일은 워딩 패스(§4)에서 같이 다룬다.
- 결론적으로 §13-10의 표기는 **"TWINGS 오리지널 / 작가 포맷"**, 카드 크레딧 **"작가 @handle"**(en: "by @handle")로 둔다. 바꾸고 싶으면 사전 키 한 곳(`creatorProgram.*`, `community.*`의 "포맷 작가")만 고치면 된다.

## 15. 디자인 — 지금 수준과 SOTA까지의 거리 (2026-10-22 크리틱)

방법: Impeccable critique. 독립 평가 2건 — A 디자인 디렉터 리뷰(twings.app 공개 6페이지를 375px·데스크톱에서 실제 열람 + 앱 화면 PR 캡처 4장 + 소스), B 결정론적 디텍터(`components`·`app` 333파일 스캔, 0건 — AI 슬롭 패턴 없음, 브라우저 오버레이는 생략). 대표의 "SOTA급" 요구에 대한 판단이다.

### 15.1 판정
- **브랜드 껍데기는 우리 것, 제품 경험은 바꿔치기 가능.** 염소 마크·단일 파랑 accent·Pretendard 디스플레이·크리에이터/브랜드 pill은 분명히 TWINGS다. 그러나 "내 얼굴로 트렌드 포맷의 주인공"을 **증명하는 픽셀이 공개 페이지에 없다** — 셀카→장면 한 쌍이 전부 로그인·결제 뒤에 숨어 있다. 스톡 영상 마켓에 옮겨도 아무도 모른다.
- Nielsen 10항목 **22/40**. 토대(토큰·정직한 카피·접근성 기본)는 좋고, 4번 일관성(한 화면에 같은 CTA 4개·라벨 2종, 페이지마다 다른 판매 상태 문장, 엔진명 2.0/2.5 불일치)이 전체를 끌어내린다.
- 감정 곡선: 이 제품의 정점은 "내 얼굴이 장면에 들어간 순간"인데 그 순간이 결제 + 2~5분 뒤에 있고, 그 전에 두 번 김이 빠진다 — 히어로 CTA 바로 아래 "공개 준비 중" 고지, 결제 직전의 빈 별점("아직 평가가 없어요").
- 가장 authored한 화면은 역설적으로 `/brands`(다크 히어로·4:3 포맷 스터디·승인 수치·실제 게시물 링크)다. 소비자 화면도 그만큼 "증거 먼저"여야 한다.

### 15.2 SOTA와의 격차 (CapCut 템플릿·Higgsfield·Remini·Meitu 기준)
| 순간 | SOTA | 지금 TWINGS |

### 15.3 고칠 순서 (우선순위)
1. **P0 템플릿 페이지 = 결제 결정 화면 정리.** CTA 라벨 하나("내 사진으로 만들기"), 바깥 H2·링크 버튼 제거, 별점은 1건 이상일 때만, AI 한계 고지 + "실패 시 전액 환불" 한 문장을 가격 박스 안에. 모바일은 safe-area sticky 하단 바(가격 + CTA), 설치앱 탭바와 공존 규칙.
2. **P1 증거를 로그인 앞으로.** 히어로에 "셀카 → 장면" 2-up(권리 정리된 내부 인물 1명), 템플릿 페이지 미디어 옆에 같은 포맷의 before/after 1쌍. 이것이 §3.2 첫 경험의 핵심이고, 포지션 문장을 화면이 증명하는 유일한 방법이다.
3. **P1 상태 문장 한 소스.** 홈 "공개 준비 중" / 템플릿 "지금 결제" / 요금제 "준비 중"이 동시에 보인다. `storefrontOpen()` 하나가 모든 availability 문장을 구동하고, 요금제는 실제 파는 단건을 위로, 구독은 티저로. 엔진명은 소비자 화면에서 뺀다(§12 "모델 선택 UI 없음"과 같은 논리).
4. **P1 카드 프레임을 제품에 맞춘다.** 세로 템플릿은 4:5 카드 2열 + 길이 칩 + 비율 칩, 16:9는 가로 템플릿에만. 2026-08-14 "모든 카드 16:9" 결정의 재검토가 필요하다(§13-15). → 2026-10-28 세로·정사각 4:5 카드 + 가로 템플릿은 두 칸 와이드 타일로 갱신(§15.6).
5. **P2 카탈로그 첫 문단.** GEO 정의문은 그리드 아래로(HTML엔 유지), 선택 상태 스타일을 pill 하나로, "YAGI 제작"처럼 전부 같은 라벨은 뺀다. → 2026-10-28 칩 줄을 없애고 탭은 글자 탭으로(§15.6).
6. **P2 대기·결과.** 단계 셋(사진 확인 → 만드는 중 → 마무리) + 기다리는 동안 다른 포맷 루프 + 완성 공유 카드(§12 결정) + "같은 얼굴로 하나 더".
- 접근성 메모: `data-studio-ai-note`·`data-engine-chip`의 0.7rem·opacity 45~60은 4.5:1에 못 미칠 가능성이 높다. 카드 자동재생 영상에 보이는 정지 컨트롤이 없다.
- `/brands`의 Morphic 실명은 2026-10-08 대표 승인분이다(AUDIENCE-RENOVATION.md).

### 15.4 결론
"SOTA급"은 색·폰트·모션을 더 얹는 문제가 아니라 **증거의 순서** 문제다. 지금은 설명 → 가격 → 결과이고, SOTA는 결과 → 한 번의 확인 → 결제다. 디자인 토큰은 유지하고(흰 바탕·파랑 accent·Pretendard), 위 1~6을 §12 단계 1의 "첫 경험" 브랜치에 합쳐 한 번에 간다. 완료 기준: Nielsen 재측정 30/40 이상, 모바일 템플릿 페이지 첫 화면에 결과물·가격·CTA가 함께 보임, 홈 첫 화면에 셀카→장면 쌍.

### 15.6 카탈로그 카드 틀과 필터 (대표 피드백 2026-10-28)
- 피드백(`/ko/video` 화면): ① 카드가 결과물 비율을 따라가자 16:9·4:3 템플릿이 9:16 카드 옆에서 낮은 띠가 되어 묻혔다. 예전처럼 같은 틀이 낫다. ② 필터 세 줄 가운데 비디오/이미지 탭만 쓸모가 있다. 출처 칩(전체 · 오리지널 · 메이커)과 용도 칩(전체 · 시네마틱 · 단편 · 뮤직비디오 · 브랜드 광고 · 유저 콘텐츠)은 하는 일이 없고, 둥근 알약이 줄지어 있으니 보기에도 설득력이 없다.
- 1차 결정(같은 날 갱신됨): 모든 카드를 같은 4:5 세로 틀에 넣는다. 운영 화면의 실제 미디어에 틀만 바꾼 CSS를 입혀 390px·1440px로 비교했다(`docs/qa/catalog-frames/05·06`). 1:1은 모든 카드가 작아지고 9:16을 더 많이 자른다. 4:5 + 흐린 배경(가로 예시는 통째로 두고 뒤에 흐린 사본)은 가로 템플릿이 다시 낮은 띠가 되어 피드백 ①로 돌아간다.
- 2차 피드백(실제 영상이 도는 프리뷰를 본 뒤): "4:3이랑 16:9가 좀 죽어 보인다." 16:9를 4:5로 가운데 자르면 가로의 약 55%(4:3은 약 40%)가 잘려, 넓은 장면이 얼굴 클로즈업이 된다. 구도와 시네마틱한 느낌이 사라지고(90년대 사투리 인터뷰, 작은 방의 백일몽, 가상 뷰티 광고가 가장 심하다), 카드가 보여 주는 모양이 `16:9` 칩과 어긋난다.
- **결정(Director, 2026-10-28): 결과물이 가로로 긴 템플릿(16:9, 4:3, 3:2 …, 가로/세로 > 1)은 그리드 두 칸을 쓰는 와이드 타일이다. 세로·정사각 템플릿은 한 칸짜리 4:5 카드 그대로다.** 타일의 미디어 높이는 모든 화면 폭에서 옆 4:5 카드의 미디어 높이와 같다. 4열이면 타일 폭은 두 칸 + 간격, 높이는 한 칸의 1.25배로 약 1.65:1이 된다. 16:9는 가로의 약 7%만, 4:3은 세로의 약 19%만 잘린다. 고정 8:5 대신 정확한 계산을 쓴다. 타일의 미디어 상자가 크기 컨테이너이고 높이는 `(100cqi − 간격) × 0.625`다. 간격은 그리드가 `--card-gap`으로 알려 준다(폰 0.75rem, `sm`부터 1rem). 그래서 한 줄의 제목과 칩이 같은 선에 놓인다.
- 한 줄 구성: 폰(2열)에서 와이드 타일은 한 줄을 다 쓰는 약 1.65:1 카드다. 데스크톱(4열) 한 줄은 타일 2장, 타일 1장 + 카드 2장, 카드 4장 가운데 하나다. 예시는 계속 틀을 꽉 채우게 자르고(`object-cover`, 초점 가로 가운데·세로 35%) 비율 칩도 그대로 둔다.
- 순서: `grid-auto-flow: dense`는 쓰지 않는다. 키보드 순서와 화면 순서가 어긋나기 때문이다. 대신 `components/prompts/card-frame.ts`가 정해진 규칙으로 순서를 짠다. 그리드는 두 칸 단위로 찬다(타일 1장, 또는 나란한 카드 2장). 짝 없는 카드는 다음 카드를 앞으로 당겨 옆에 앉힌다. 그러면 모든 타일이 짝수 칸에서 시작해 2열·4열 어디서도 중간에 빈칸이 생기지 않는다. 짝을 찾지 못한 카드는 레일 맨 끝으로 간다. NEW가 먼저 오는 규칙도 지킨다. NEW 묶음에서 카드 한 장이 남으면 그 묶음 끝에서 첫 번째 이전 카드와 짝을 짓는다. 나머지는 추천 → 최신 순서 그대로다. 단위 테스트가 길이 8까지 가능한 모든 배열에서 빈칸 없음, 누락 없음, 타일끼리·카드끼리의 순서 유지를 확인한다.
- 적용 범위: `/{locale}/video`·`/{locale}/image`·홈 갤러리(`PromptRail`), AI 크리에이티브 프로필 `/{locale}/makers/[handle]`(같은 `PromptRail`), 템플릿 페이지의 관련 템플릿, 렌더 대기 화면의 "다른 포맷 보기". 모두 2열 → 4열 그리드다. 와이드 타일은 그리드가 두 칸을 줄 때만 켜진다(`frame="wide"` + `col-span-2`). 다른 곳의 카드(예: 3열 그리드인 홈 `Featured` 섹션, 지금은 어디서도 렌더하지 않는다)는 4:5 그대로다. 홀수 열 그리드에서는 두 칸 단위가 줄 경계를 넘어 빈칸이 생기기 때문이다.
- 그리드: 폰 2열, 768px부터 4열. 3열 단계는 없다. 3열이면 와이드 타일이 빈칸을 남기고, 데스크톱 한 줄이 차면 폰 두 줄도 찬다. 레일 끝에 반 줄이 남는지는 템플릿 수와 비율이 정한다. 그리드로 막지 않는다. 몇 편을 올릴지는 템플릿 선정과 같은 대표 결정이다.
- **출처 칩과 용도 칩은 없앴다**(`/{locale}/video`·`/{locale}/image`와 홈 갤러리). 출처는 레일 제목("TWINGS 오리지널" / 메이커 컬렉션)이 말한다. `?useCase=` 주소 상태와 개수 줄("n개 템플릿")도 함께 뺐다. 거르는 기능이 없으면 몇 편인지는 그리드가 보여 준다. 템플릿의 `use_case` 값은 데이터로 남는다(템플릿 페이지가 쓴다).
- 비디오/이미지 전환은 파란 알약 대신 헤어라인 위의 글자 탭이다. 열린 탭은 검은 글자에 2px 밑줄, 다른 탭은 55% 잉크(흰 바탕 대비 4.5:1 이상). 사이트 내비게이션이 현재 위치에 긋는 밑줄과 같은 어법이다.
- 스윕: `/{locale}/video`의 레일마다 카드 하나하나를 본다. 비율 칩이 가로로 긴 카드는 `col-span-2` + `data-frame="wide"` + 높이 계산식을, 나머지는 `data-frame="portrait"` + `aspect-ratio:4 / 5`를 가져야 한다. 짝수 칸이 아닌 곳에서 시작하는 타일이 없어야 하고, 스냅숏에 타일이 한 장 이상 있어야 한다. `data-frame="landscape"`·16:9 틀·`data-use-case-filter`·`data-origin-filter`·`aria-pressed`는 없어야 통과한다.

### 16.1 지금 브랜드가 할 수 있는 것 / 없는 것
- 할 수 있다: 조직·구성원, 브리프 제출(`/brand/projects/new` 긴 폼 하나 → `brand_projects.requested`), 선정된 참여자만 보기(상태·프로필 URL), 1인용 초대 링크, TWINGS가 낸 견적 수락·결제, 리포트 읽기, 2차 활용 결제, 스튜디오 제작.
- 없다: **캠페인 만들기**(포맷·보상·슬롯·기간·게시 조건은 관리자만), **지원자 보기**(`applied`는 숨김), **크리에이터 풀**(검증된 크리에이터 표가 없음, 팔로워는 자기 신고), 하나의 캠페인 타임라인(참여자·결제·리포트가 탭 밖 별도 페이지, `bw-*` 스타일 아닌 임시 Tailwind, 문안도 `messages/campaign-*.ts`에 흩어짐).

### 16.2 설계 원칙
- 브랜드는 **정하고 보고 지불**한다. 선정·검수·지급 확정은 계속 TWINGS가 한다(KAIPER 원칙 유지: 결제가 선정·검수·지급을 대신하지 않는다).
- 캠페인 하나 = 화면 하나. 프로젝트 상세 탭에 **지원자·참여자·결제**를 합쳐 한 타임라인으로 보여준다(브리프 → 검토 → 모집 → 선정 → 제작·게시 → 리포트 → 정산).
- 기존 서비스·컴포넌트 재사용: `createBrandProject`·`loadBrandProject`·`loadProjectCollaboration`·`issueInvitation`·`loadCampaignParticipation`(퍼널 수)·`campaignPerformance`·펀딩 `quote→accept→order→confirm`, `ActionForm`·`ConfirmStep`·`ProjectTabs`·`CampaignPerformance`·`ParticipantDetail`·`FundingActions`. 새로 쓰지 않는다.
- Operate 모드. 브랜드 워크스페이스의 `bw-*` 토큰과 `brandWorkspace` 사전으로 통일한다.

### 16.3 캠페인 마법사 (`/brand/projects/new` 교체)
5단계, 각 단계가 저장되는 초안(`brand_projects` 확장 + `campaign_drafts` 없이 프로젝트 행에 jsonb `campaign_terms`):
1. **포맷**: TWINGS 오리지널·작가 포맷(공개 템플릿) 또는 "브랜드 전용 제작 요청". 카드 2열 4:5 미리보기(§15 카드 재사용).
2. **보상·예산**: 보상 방식(고정/조회수/혼합 — 기존 `payout` 모델), 1인 보상액 범위, 총 예산(부가세 기준 포함), 인원(슬롯).
3. **대상**: 전체 인플루언서 / 조건(플랫폼·팔로워 최소·성별·지역) / 지정 크리에이터(풀에서 선택 — 16.5 전까지는 초대 링크 방식).
4. **기간·게시 조건**: 모집 마감·게시 마감, 필수 해시태그·멘션·광고 표기(필수 고정)·금지 사항.
5. **검토 요청**: 요약 한 화면 → "TWINGS 검토 요청". 상태 `requested`. 관리자는 기존 `/admin/campaigns`에서 `campaigns` 행을 만들고 `bindCollaboration`으로 연결(기존 경로). 마법사 값은 관리자 화면에 미리 채워진다.
- 저장은 단계마다(이탈해도 유지), 모바일 가능하지만 데스크톱 우선.

### 16.4 캠페인 타임라인 (프로젝트 상세 재구성)
- 탭: 개요(타임라인·다음 행동) · 브리프 · **지원자/참여자** · **결제** · 리포트 · 파일·대화 · 계약·2차 활용. 참여자·펀딩 페이지는 탭으로 흡수(경로는 리다이렉트로 유지).
- 지원자 보기: `applied`도 보인다 — 핸들·플랫폼·팔로워(출처 표시: 자기 신고/확인됨)·포트폴리오 링크·지원 메시지. 브랜드는 **"선호"** 표시만 할 수 있고(`brand_preferred_at`), 선정은 TWINGS. 선정 뒤에는 제작·게시·검수 상태와 게시물 링크·지표(출처 표시).

- 퍼널 숫자(지원→선정→제작→게시→검수→지급)는 `loadCampaignParticipation`.

## 17. 인플루언서 자격·크리에이터 풀 (B2) — 대표 결정 반영 (2026-10-23)

**결정(§13-4·5, 대표)**: 처음에는 **수동**으로 간다. 프로필 링크 + 팔로워 화면 캡처를 받고, **로컬 AI(Qwen/Gemma, 워크스테이션 gpu-arbiter `127.0.0.1:11434`)가 캡처에서 팔로워 수를 읽어 제안**하고 관리자가 확인한다. 캠페인 탭은 **일반 사용자에게도 거슬리지 않게 노출**한다(일반인 참여 캠페인을 원하는 기업이 있다). 자격 기준은 연동 계정 중 **한 계정이라도** 3,000 이상(합산 아님).

### 17.1 자격 신청과 확인
- `/account`의 "SNS 연결" 카드 → `/identity/social`(새 app 경로, `APP_PREFIXES` 등록): 플랫폼(instagram|tiktok|youtube)·프로필 URL(`canonicalPost`와 같은 정규화)·팔로워 화면 캡처 1장(JPEG/PNG ≤5MB, 서버에서 sharp 재인코딩·메타 제거, 비공개 버킷). 제출 즉시 상태 `submitted`.
- 표 `social_accounts`(0057 core / 0141 glue): id, user_id, platform, handle, profile_url, follower_count int null, claimed_count int null(사용자 입력), evidence_key, status `submitted|verified|rejected|expired`, source `manual|api`, ai_count int null, ai_confidence numeric null, ai_model text null, reviewed_by, reviewed_at, measured_at, note, created_at. 유니크(user_id, platform). `profiles.influencer_since timestamptz`(최초 verified 시각, 자격 판정은 서버 함수 `isInfluencer(userId)` = verified 계정 중 follower_count ≥ 3000 존재).
- **로컬 AI 보조**: 기존 `campaign-risk-worker` 패턴(앱이 작업을 내주고 워커가 비밀키로 claim/complete)을 재사용해 `social-verify-worker`(scripts/, 워크스테이션 실행)가 `submitted` 건의 캡처를 받아 Ollama 비전 모델(`qwen` 계열 우선, 없으면 `gemma`)에 "이 화면의 팔로워 수와 계정 핸들을 JSON으로"를 물어 `ai_count·ai_confidence·ai_model`을 기록한다. 워커 없이도 제출·관리자 확인은 동작한다(AI는 제안일 뿐, 확정은 관리자).
- 관리자 `/admin/community`에 "SNS 확인" 큐: 캡처·링크·사용자 입력·AI 제안을 나란히, [확인(수치 입력)] [반려(사유)]. 오퍼레이션 `social.verify|reject`. 확인 시 `follower_count`·`measured_at`·`source=manual` 기록, `profiles.influencer_since` 갱신. 90일 지나면 `expired` 표시(자격은 유지, 재제출 안내).

### 17.2 캠페인 탭 가시성
- 캠페인 목록 `/{locale}/campaigns`는 공개(`audience='public'`만 캐시된 정적). 로그인 사용자용 `/campaigns`(app)는 뷰어별·무캐시: `public` + (인플루언서면 `influencers`) + (`campaign_targets`에 있으면 `invited`). 지원 가능 여부도 서버에서 같은 규칙(`loadApplyState`·`applyToCampaign`·`acceptInvitation`).
- 일반 사용자 화면: 내비 "캠페인"은 유지(공개 캠페인이 있으니), 계정 페이지와 캠페인 목록 상단에 티저 한 줄 "인스타그램·틱톡을 연결하면 더 많은 캠페인이 열려요" + 연결 링크. 자격 있는 사용자에겐 "인플루언서 캠페인" 섹션이 위에.

### 17.3 크리에이터 풀(브랜드)
- `social_accounts.pool_consent_at`(풀 노출 동의, 사용자가 `/identity/social`에서 켬). 브랜드 `/brand/creators`(허용 목록 추가): 동의한 verified 인플루언서를 핸들·플랫폼·팔로워 구간(1천 단위 반올림)·대표 공개 작품으로 카드 노출, 검색·필터(플랫폼·팔로워 구간). 브랜드 동작은 "캠페인에 초대"뿐(`campaign_targets` 삽입 + 기존 초대 링크 발급을 계정 지정으로). 연락처·실명·정확한 수치 없음.

### 17.4 단계
B2-a 자격 신청·관리자 확인·로컬 AI 워커·탭 가시성(0057/0141) → B2-b 크리에이터 풀·지정 초대. 둘 다 플래그 `TWINGS_INFLUENCERS=on`으로 열고 기본 off.

  | 49,000원 | 258 | 영상 + §19.4 업스케일 혜택 | 기존 설계가, 크레딧 수는 제안 |

- **기존 크리에이터 구독은 앱에서 그대로 팔 수 없다.** `CREATOR_PLANS`(604·1,200 units)는 PG 3.3% 기준이라, 앱 수수료로 팔면 한도를 다 쓰는 사용자에게서 약 −1.4% 적자가 난다. 새 플랜 버전으로 바꾼다. 코드는 이 절에서 바꾸지 않았다.
- **이름은 "크레딧" / "credits"이다.**
  - SNS 게시 보상 이미지 크레딧도 같은 이름을 쓴다. 화면에는 "이미지에만"으로 표시하고, 원장은 따로 둔다.
  - "필름"은 브랜드 페이지의 영상 작품명과 겹치고, "컷"은 "5컷"과 겹친다. "코인·포인트·캐시"는 돈처럼 읽히고, "쿠키"는 옛 프롬프트 열람권 이름이다. 그래서 모두 쓰지 않는다.
- **이월.** 남은 크레딧은 1달치까지 넘어간다. 잔액 상한은 월 지급량의 2배다. 상위 플랜으로 바꾸면 유지하고, 해지하거나 내리면 그 결제 기간이 끝날 때 사라진다. ElevenLabs가 같은 방식이다.
- **환불.** 남은 크레딧은 환불하지 않고 현금으로 바꿔 주지도 않는다.
  - 예외: 첫 결제 후 7일 안에 하나도 쓰지 않았으면 전액 환불한다. 앱 결제는 스토어 환불 절차를 따른다.
- **입구.** 휴대폰 본인인증을 한 번 하면 무료 이미지 1장을 준다. 무료 체험(자동 유료 전환)은 쓰지 않는다.
- **이탈 방지.**
  - 새 템플릿을 정해진 주기로 공개하고 푸시한다.
  - 갱신 전에 이월될 크레딧을 알린다.
  - 해지 화면은 한 장이다. 하위 플랜으로 내리기, Android 일시정지(1주~3개월), iPhone 복귀 제안을 보여준다. 해지 버튼은 같은 크기로 바로 보이게 둔다. 2025년 시행 전자상거래법이 해지 방해를 금지한다.
  - 해지 뒤에도 결과물은 잠그지 않는다.
- **지켜볼 것.** 4,900원에서 24,900원은 5배 차이다. 영상 플랜 전환이 낮으면 중간 플랜(영상 2편쯤)을 검토한다.
- **2026-09-17 표현 규칙과의 관계.** TEMPLATES-IA §12의 "크레딧·포인트·충전 표현 금지, 이월 없음"은 앱 안에서는 이 결정으로 대체된다. 그 규칙의 이유는 토스 심사(선불 재화로 보일 위험)였으므로 다음 조건을 지킨다.
  - 토스 자동결제가 승인되기 전에는 웹에 "크레딧" 문구를 노출하지 않는다.
  - 약관과 자동결제 신청서에서 크레딧은 "구독에 포함된 월 이용 한도"로 정의한다. 별도 구매·충전·양도·현금 교환은 안 되고, 해지하면 사라진다.
  - 약관 제4조(지금은 "편당 1회, 충전·포인트 없음")는 앱 구독을 열기 전에 개정해야 한다. 문안은 대표 승인이 필요하다.

### 19.3 메이커 몫
- 메이커는 템플릿에 크레딧을 얹는다. 사용자는 원가 크레딧과 얹은 크레딧을 합쳐서 쓴다.
- 메이커는 얹은 크레딧 전부를 정산 단가로 받는다. 정산 단가는 원가 단가(약 129원) 고정을 제안한다. 환율이 바뀌면 플랜 버전으로 반영한다.
- 플랫폼 몫은 플랜 마진이다. 플랜은 앱 수수료를 뺀 뒤 크레딧당 약 147원을 받으므로, 다 쓰는 사용자 기준 크레딧당 약 17원(약 10%)이 남는다.
- Seedance 2.5의 원가 크레딧은 API 정가 그대로 둔다. TWINGS GPU로 원가를 낮춰 주지 않는다.
- §8.3의 원화 R(`royalty_krw` 500~5,000 CHECK)은 크레딧 단위로 바뀐다. 스키마와 정산 코드는 별도 PR에서 바꾼다.

### 19.4 업스케일 — 최상위 플랜 독점
- 49,000원 플랜만 480p로 생성하고 사무실 GPU로 업스케일한다. 같은 크레딧으로 영상을 약 두 배 만들 수 있다(추정).
- 열기 전에 확인할 것:
  - 480p 실제 단가. `lib/ark/pricing.ts`에는 720p·1080p만 있다. "720p의 약 45%"는 픽셀 수로 낸 추정이다.
  - 얼굴 유지. 480p+업스케일과 720p를 20편 나란히 만들어 비교한다.
- GPU가 꺼져 있거나 하루 상한을 넘으면 720p로 바로 만들고, 차감은 480p 크레딧만 한다. 차액은 TWINGS가 내며, 하루 상한을 둔다.
- 얼굴 검증과 제공사 검수는 업스케일 경로에서도 그대로다.

### 19.5 친구 얼굴 — 두 사람 동의 (대표 승인)
- 첫 스토어 심사 버전(v1)에는 넣지 않고 v1.1에서 연다. 첫 심사는 본인 얼굴만으로 통과시킨다.
- 두 사람 모두 TWINGS에 가입하고 본인 얼굴을 인증한다. 휴대폰 본인인증으로 성인인지 확인한다.
- 친구가 "이 사람은 내 얼굴로 만들 수 있음"을 허락한다. 허락은 30일 동안 유효하고, 언제든 철회할 수 있다.
- 찍은 얼굴이 허락한 친구의 인증 얼굴과 맞을 때만 생성한다. 다른 얼굴이 섞이면 거절한다. 얼굴 검증과 제공사 검수는 우회하지 않는다(AGENTS.md §4).
- 결과는 두 사람 모두 보고 지울 수 있다. 친구가 철회하면 그 친구 얼굴이 들어간 결과를 우리 저장소에서 지운다. 친구 얼굴도 §19.8의 에셋 돌려쓰기 칸을 쓴다.
- 약관 §5.3("본인 얼굴만")과 개인정보처리방침(얼굴 정보 별도 동의)을 개정해야 한다. 문안은 대표 승인이 필요하고, 확정 전에 법무 검토를 권한다.

### 19.6 웹 — 단건으로 버티기 (대표 승인)
토스 반려 위험을 0으로 만드는 방법은 신청한 그대로(단건 일반결제) 운영하는 것이다.
1. 라이브 키를 받기 전까지 웹은 지금 그대로 둔다(`review`). 구독·크레딧 문구는 넣지 않는다.
2. 라이브 키를 받으면 §2.3 런북대로 단건을 연다. 같은 날 토스 자동결제를 따로 신청한다. 별도 계약인지는 TOSS-CONTRACT.md의 확인 항목이다.
3. 앱 구독이 열리면 웹 단건의 신규 판매를 닫는다. 이미 산 결과물은 그대로 둔다.
4. 자동결제가 승인되면 웹에서도 같은 가격, 같은 크레딧으로 구독을 판다.
- 웨딩 화보 5컷 세트(`bridal-editorial-5-shots`)는 버티기 기간에 1,200원이다. 실셀카 스모크를 통과한 뒤 `/admin`에서 저장한다. 구독에서는 5크레딧이다.

### 19.7 앱
- **Android TWA(PR #105, `claude/android-twa`)** 는 Play **내부 테스트 트랙에만** 올린다. 공개하지 않는다. 구독제에서 구매 없는 앱은 막다른 길이기 때문이다. 패키지 이름과 서명 키는 다음 앱이 이어 쓴다.
- **앱 v1(iOS·Android, 본인 얼굴만)** 은 웹 화면을 재사용하는 Capacitor 앱이다.
  - 스토어 구독 3개를 등록한다.
  - 서버가 영수증을 확인한 뒤에만 생성을 시작한다. 토스 `DONE` 규칙과 같다.
  - 스토어 알림(App Store Server Notifications, Google RTDN)으로 환불·해지를 받으면 크레딧을 회수한다.
  - 무료 첫 이미지를 넣는다.
- **심사에서 반려되지 않게 갖출 것.**
  - Apple 로그인, 앱 안 계정 삭제, 구매 복원 버튼
  - 구독 조건 표시: 가격·기간·자동 갱신·약관·개인정보 링크
  - 심사용 데모 계정
  - 앱 안 웹 화면에서 토스 결제와 가격 문구 숨기기(PR #105의 스토어 셸 재사용)

### 19.8 Seedance 2.5 운영 제약 (ByteDance 확인)
- **엔터프라이즈 할인 없음.** 원가를 줄일 방법은 해상도·길이·실패율뿐이다.
- **동시 실행 10개.** 지금 큐(`claimRenderJobs`)는 제공사에 진행 중인 작업 수를 세지 않는다. "진행 중 10개 미만일 때만 보낸다"는 막을 추가하고, 대기 순번·예상 시간·완성 푸시를 붙인다.
- **얼굴 에셋 상주 50개.** `lib/identity/rotation.ts`가 40개까지만 쓰고, 오래 안 쓴 얼굴부터 지우며, 진행 중인 작업의 얼굴은 건드리지 않는다. 이미 구현돼 있다.

### 19.9 실행 순서
1. **지금부터 라이브 키까지:** 웹은 그대로 둔다. TWA는 내부 테스트 트랙에만 올리고, 약관 개정 문안을 준비한다.
2. **라이브 키:** 웹 단건을 열고(§2.3), 토스 자동결제를 신청한다.
3. **앱 v1:** 구독, 크레딧 원장, 영수증 확인, 무료 첫 이미지, 심사 요건(§19.7)을 갖춘다. 동시 10개 막(§19.8)도 넣는다.
4. **앱 구독 오픈:** 웹 단건 신규 판매를 닫는다. 자동결제가 승인되면 웹 구독을 연다.
5. **v1.1:** 친구 얼굴, 메이커 크레딧 정산, 커뮤니티 피드를 연다. 업스케일 혜택은 확인(§19.4)을 마친 뒤 연다.
6. **그다음:** 인플루언서 캠페인.
