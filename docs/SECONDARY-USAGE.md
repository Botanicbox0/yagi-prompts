# 2차 활용 (Brand secondary usage) — phase 0

> 상태: 구현됨(PR #25). 2026-09-24 운영 DB에 0037/0123 적용 완료. 결제는 기본 꺼짐.
> 설계 근거: 2026-09-23 logic design(Opus 5.5)·copy draft(Opus 4.6)·대표 결정(inquiry-first, 사이트 결제).
> 약관·환불·개인정보 본문(`lib/legal/documents.ts`)은 바꾸지 않았다. 가격·세금·환불 규칙·기간 프리셋·PG 수단은 대표/법무 결정이다.

## 1. 무엇을 하는가

브랜드가 캠페인 콘텐츠를 다른 채널·용도로 다시 쓰고 싶을 때, **선택한 콘텐츠와 궁금한 것만으로** 문의한다.
TWINGS가 대화로 조건을 정리하고, 크리에이터와 **시스템 밖에서** 협의한 뒤 동의를 관리자에 기록한다.
브랜드는 **최종 견적(총액·세금 기준·범위·계약서)**만 보고, 수락 후 사이트에서 1회 결제한다.
결제가 확인되면 활성화 가드가 수락한 조건을 그대로 다시 확인하고 이용 허가(grant)를 만든다.

```
브랜드(소유자/편집자)  콘텐츠·게시물 카드 "2차 활용 견적 문의" → 목적 선택(비용/조건 추천/직접 질문) → 보내기 … inquiry
스튜디오              /admin 문의함 → 검토 시작 → 대화로 범위 확인 …………………………………………………… scoping
스튜디오              범위 개정 R1 기록(채널·지역·기간 명시, 대상 고정) ………………………………………… scope_defined
스튜디오              크리에이터에게 R1과 보상액을 외부 전달 → 동의 받음 → 보상·동의·권리확인 기록(내부)
스튜디오              견적 발행(총액·세금 기준·유효기한·공유된 조건 PDF) ………………………………………… quoted
브랜드(소유자/결제담당) 견적 확인 → 수락 → 결제(토스) …………………………………………………………… accepted → paid
시스템                활성화 가드: 같은 조건 재확인 → 이용 허가 or 결제 후 확인 필요 ………………… fulfilled | blocked_after_payment
```

문의만으로는 아무것도 허가·청구되지 않는다. 비어 있는 활용처·기간·예산은 **모름**으로 저장되며 전 채널·영구·전 세계로 해석되지 않는다.
비용만 알아본 문의는 견적 없이 `answered_only`로 종료할 수 있다. 리액션 기능과 크리에이터 포털은 범위 밖이다.

## 2. 불변식 (코드와 테스트가 지키는 것)

- **권한**: 조직 멤버십이 있는 소유자·편집자만 문의·대화·취소. 뷰어는 읽기. 캠페인 전용 게스트는 탭 자체가 없다(404).
  TWINGS 팀 읽기 보기(staff)는 읽기만. `is_admin`이라도 브랜드 좌석이 없으면 브랜드로서 문의·수락·결제하지 못한다.
  조직은 항상 프로젝트 행에서 가져온다(요청의 org id를 믿지 않음).
- **수락·결제 권한(보수적 기본값, 대표 결정 D6 대기)**: 활성 소유자, 또는 스튜디오가 `brand_usage_buyers`에
  근거와 함께 등록한 **편집자**만. 기본 거부. 뷰어는 등록 불가. `is_admin` 계정은 브랜드 좌석(소유자·편집자)이 있어도 수락·결제할 수 없고,
  스튜디오는 자기 자신이나 다른 관리자 계정을 결제 담당자로 등록할 수 없다(동의 기록·견적 발행 주체가 고객 대신 구매하지 않도록). 읽기·대화는 기존 규칙 그대로.
  결제 담당 권한은 그 편집자 좌석에 묶인다: 멤버십이 해제되거나 역할이 바뀌는 순간 DB 트리거(`brand_usage_buyer_membership_guard`)가
  `membership_ended`/`role_changed`로 철회하고, 다시 초대돼도 되살아나지 않는다(새 근거로 새로 등록).
- **금액 분리**: 크리에이터 보상(`brand_usage_compensations`)과 동의 근거(`brand_usage_consents`)는 관리자 전용.
  브랜드 DTO(`loadBrandUsage`)는 필드 단위로 만들며 보상·근거·동의·마진·핀 해시·결제 키·내부 거절 사유를 담지 않는다.
  브랜드 작업은 내부 검사 실패를 모두 `conflict`로만 돌려준다. 동의 근거는 **텍스트 참조**만 받는다(파일 업로드 없음 → 기존 첨부 경로로 크리에이터 계약이 새지 않음).
- **범위와 동의**: 견적은 최신 범위 개정의 `scope_sha256`와 정확히 같은 해시의 유효 동의, 그리고 그 개정의 **최신** 보상 개정이
  모든 항목에 있을 때만 발행된다. 범위를 바꾸면 해시가 바뀌어 기존 동의가 무효, 금액을 바꾸면 새 보상 개정이라 재동의 필요.
  지표 검증(`verification='manual'`)은 동의가 아니다.
- **대상 고정(pin)**: 서버가 DB에서 채운다. 승인 콘텐츠 버전(파일 해시), 게시물 원본 그대로(URL·플랫폼 ID), 또는 스튜디오 원본 파일(해시).
  `external_import` 게시물은 문의 가능하지만 "콘텐츠 버전"으로 고정할 수 없다(`subject_unpinned`). 원본 게시물 고정은 원본 파일 제공·편집을 허용하지 않는다.
- **결제 전 확정**: 브랜드는 수락 전에 총액·세금 기준·범위·기간·제외 항목·계약서를 본다. 수락과 결제 직전에 같은 근거를 다시 검사한다.
  온라인 수락·결제는 **세금 포함 최종 총액**(`tax_basis='included'`)이고 **공유된 계약서**가 지금 보일 때만 된다. 세금 별도 견적은 발행·열람만 되고,
  스튜디오가 브랜드가 실제 낼 세금 포함 금액으로 최종 견적을 다시 보내야 한다(세율·금액을 시스템이 계산하지 않는다). 계약서 공유가 끊기면 수락·결제 버튼이 사라지고 스튜디오 문의를 안내한다.
  고정 기간은 이미 끝났으면 견적할 수 없고, 견적 유효 기한은 가장 이른 고정 기간의 끝을 넘을 수 없다. 수락·결제 직전에도 기간이 남았는지 확인한다.
  결제 직전 검사가 실패하면 **청구하지 않고** 주문을 만료시킨다. 결제 후 검사는 이미 수락한 조건을 재확인만 하며 조건을 바꾸지 않는다.
- **경합·중복**: 수락과 스튜디오 재견적은 같은 케이스 행을 잠그고 `expectedRevision`으로 하나만 성공. 같은 `requestId`는 같은 결과.
  견적당 살아 있는 주문 1개(부분 유니크 인덱스). 만료·대체된 견적의 주문은 청구 전에 거절.
- **결제 분리**: `brand_usage_payments`(order_kind `brand_usage_license`)는 `billing_payments`와 별개. 렌더 생성·`RENDER_PIPELINE_PUBLIC`과 무관.
  `TossGateway`만 재사용한다. 금액은 서버가 견적에서 가져오고 브라우저 금액은 일치 검사만. 제공사 응답의 주문 ID·결제 키·금액·통화를 서버에서 대조.
- **운영 환경(production)**: `VERCEL_ENV=production`에서는 라이브 Toss 키일 때만 결제가 열리고(`usagePaymentsOpen`), 주문·승인도 라이브 게이트웨이만 받는다.
  활성화 가드는 production에서 `environment<>'live'` 결제를 어떤 경로(직접 호출·reconcile·스튜디오 재확인)로 와도 `non_live_payment`로 막는다.
  프리뷰·로컬의 테스트/가짜 결제 흐름은 그대로 쓸 수 있다. 런타임은 서버 코드가 `UsageRuntime`으로 명시 주입하고 테스트가 두 경우를 모두 검증한다.
- **불확실한 승인**: 확인 요청이 끊기면 `confirming` + 리스로 남긴다. 복구는 먼저 **조회(retrieve)**하고, 조회 결과가
  `IN_PROGRESS`일 때만 같은 멱등 키로 다시 승인한다. 새 주문을 만들지 않는다. 모든 경로에서 제공사 스냅샷(주문 ID·키·금액·통화)을 대조한다.
  · 제공사가 확인을 4xx로 거절하면 즉시 조회해, 해당 키의 결제가 없으면 `failed`로 풀어 브랜드가 다시 결제·취소할 수 있다.
  · ABORTED/EXPIRED, 잔액 0인 CANCELED는 `failed`(돈 이동 없음). PARTIAL_CANCELED·입금 대기·잔액 불일치·스냅샷 불일치는 `review`(허가 없음, 새 주문 차단, 스튜디오 판단).
  · 조회 "없음"은 주문 기한 + 30분(제공사 승인 창)이 지난 뒤에만 미결제 증거로 쓴다. 시간 초과·네트워크 오류·리스 만료는 증거가 아니며 claim을 유지한다.
  · reconcile은 활성화 대기 → 환불 → 미확정 확인 순으로 각각 따로 20건씩 처리하고, 미확정 건은 매 시도 후 10분 뒤로 밀어 다른 건을 막지 않는다.
  · 스튜디오 `abandon`은 제공사 조회가 미결제(없음·ABORTED·EXPIRED·잔액 0 취소)를 보여줄 때만 `confirming`/`review` 주문을 푼다. 그 밖에는 거절.
- **환불**: 자동 환불 없음. 관리자 `brandUsage.resolve`(refund)로만, 사유와 함께. 해당 케이스의 이용 허가는 종료 이벤트로 끝난다. `review` 주문도 같은 경로로 취소한다.
  제공사 스냅샷이 주문과 다르면(`provider_mismatch`) 시스템이 취소하지 않으므로 Toss 관리 화면에서 처리한다.
- **이용 중 동의 철회**: 이미 허가가 난 뒤 동의 철회를 기록하면 그 동의에 묶인 허가에 `suspended` 이벤트가 추가되고(기존 기록은 그대로), 케이스는
  `blocked_reason='consent_withdrawn'`으로 문의함 맨 위에 오른다. 브랜드에는 "이용 보류"로 보이고 "이용 조건 확정"으로 보이지 않는다.
  철회된 동의로는 재개할 수 없다(종료·환불하거나 새 동의로 새 문의). 보류가 모두 풀리면 표시가 사라진다.
- **이용 허가**: 활성화 가드만 쓴다. 케이스 단위 전부 아니면 전무. 기간은 견적의 날짜에서만: 고정일(한국 시간 00:00 시작, 종료일 다음날 00:00 배타 종료)
  또는 "첫 사용일부터 N일"(스튜디오가 시작일을 한 번 기록). 상태(예정·이용 중·만료·일시 중단·종료)는 읽을 때 계산한다.
- **예측 데이터(phase 0)**: 제안(quoted)·수락(accepted)·결제(paid)는 `brand_usage_events`에서 서로 다른 이벤트다.
  `brand_usage_outcomes`는 케이스당 1행, **최종 견적**에서만 만든다(대체된 협상 개정은 세지 않음). 브랜드 최종가만 담고 크리에이터 금액은 없다.
  예측 UI·추정기는 없다.

## 3. 게이트

| 게이트 | 기본값 | 여는 방법 |
| --- | --- | --- |
| `usagePaymentsOpen()` (`lib/brands/usage/runtime.ts`, 플래그는 `lib/flags.ts brandUsagePaymentsOpen`) | **꺼짐** | 서버 환경변수 `BRAND_USAGE_PAYMENTS=on` (Vercel). production에서는 라이브 Toss 키도 필요. 대표 결정 후. |
| `RENDER_PIPELINE_PUBLIC` | false (변경 없음) | 이 기능과 무관. 서로 열지 않는다. |
| Toss 게이트웨이 | 키 없으면 클라우드에서 **없음(503)** | `TOSS_CLIENT_KEY`/`TOSS_SECRET_KEY`. 가짜 게이트웨이는 `PLAYBOOK_MODE=local` 또는 테스트에서만. |

결제가 꺼져 있어도 문의·대화·범위·동의·견적 발행과 브랜드의 견적 열람은 동작한다. 수락·결제만 막히고, 화면은
"온라인 결제는 아직 열리지 않았습니다"를 안내한다. 결제 복구(reconcile)와 관리자 환불은 플래그와 무관하게 동작한다.

## 4. 운영 절차 (현재 팀)

1. `/admin/brand-workspace/usage`에서 새 문의를 연다 → **검토 시작**. 필요한 것만 대화로 묻는다(어디에, 얼마나, 어느 나라, 편집·광고 여부).
   "조건을 추천받고 싶어요"면 구체적인 범위를 제안한다. 비용 문의로 끝나면 **문의 종료 → 답변만 드림**.
2. **범위 개정**을 저장한다. 채널(한 줄에 하나)·국가 코드·기간(고정일 또는 첫 사용일부터 N일)·편집·광고주(광고일 때)를 명시하고 항목마다 대상을 고정한다.
   링크로 가져온 게시물은 "게시물 원본 그대로" 또는 스튜디오가 올린 원본 파일로만 고정할 수 있다.
3. 크리에이터(또는 에이전시·권리자)에게 **그 개정 그대로**와 보상액을 외부에서 전달한다. 스레드를 보관한다.
4. **크리에이터 보상**을 기록하고, 동의를 받은 뒤 **크리에이터 동의**를 기록한다: 동의한 사람, 일시(한국 시간), 근거 보관 위치(예: 메일 제목·날짜),
   권리 확인 4개(소유·통제, 음악·오디오, 함께 나온 인물, 상표·로고). 계약서 본문을 붙여 넣지 않는다.
5. 브랜드에 보여도 되는 **고객용 조건 PDF**를 캠페인 계약서로 올리고 **공유**한다(크리에이터 계약서 금지).
6. **견적**: 합의한 총액과 세금 기준을 그대로 입력(자동 계산 없음), 유효 기한(고정 기간 끝을 넘지 않게), 공유된 조건 PDF 선택 → 보내기.
   온라인 결제용은 **세금 포함 최종 금액**으로 보낸다. 세금 별도로 보낸 견적은 안내용이며 브랜드는 결제할 수 없다.
7. 브랜드 소유자(또는 등록된 결제 담당자)가 수락·결제한다. 결제 후 케이스가 **이용 조건 확정**인지 확인한다.
   "첫 사용일부터" 조건이면 브랜드가 알려준 첫 사용일을 **첫 사용일 기록**으로 남긴다.
8. **결제 후 확인 필요**가 뜨면 사유를 본다. 공유를 실수로 끈 경우처럼 같은 조건이 다시 성립하면 **같은 조건으로 다시 확인**, 아니면
   대표 결정에 따라 **결제 취소(환불)**. 조건을 바꿔야 하면 환불 후 새 문의로 진행한다.
9. 결제 확인이 늦으면 문의함의 **결제 복구 지금 실행**. 매일 `/api/renders/tick`(UTC 18:00)도 같은 복구를 돌린다.
   결제가 **결제 확인 필요**(`review`)면 Toss 관리 화면에서 실제 상태를 보고 환불하거나, 제공사 조회가 미결제를 보여줄 때만 **미확정 결제 해제**.
   크리에이터가 이용 중에 동의를 철회하면 해당 허가가 자동 보류된다: **종료**와 필요 시 **결제 취소(환불)**를 대표 결정에 따라 처리한다.
10. 편집자에게 결제 권한이 필요하면 소유자의 서면 지시를 받은 뒤 케이스 화면 **결제 담당자 추가**(근거 기록).

## 6. 의도적으로 하지 않은 것 (phase 0)

- 원본 파일 전달(다운로드)과 다운로드 기록: 없음. 그래서 `source_files`(원본 파일 제공) 용도는 범위 스키마에서 제거했다(견적·허가가 전달할 수 없는 파일을 약속하지 않도록). **일반 캠페인 파일 탭으로 원본을 전달하지 말 것**(허가 기간·중단 검사를 우회한다). 필요하면 다음 단계에서 허가 연동 전달을 만든다.
- 0원 견적(기존 계약으로 선불된 경우), 부분 항목 활성화, 브랜드의 "사용 시작" 버튼, 토스 웹훅(가상계좌 등 비동기 수단 전 필요), 이메일·슬랙 알림, 예상 견적 UI·추정기.
- 동의 근거 파일 업로드(비공개 `rightsholder` 저장소가 생기기 전까지 텍스트 참조만).

## 8. 예측 견적 로드맵 (구현 안 함)

phase 0은 이력만 구조화한다(`brand_usage_events`, `brand_usage_outcomes`: 케이스당 최종 견적 1행, 범위 특징 JSON, 세금 기준, 결과).
phase 1(내부): 같은 용도·편집·광고 여부·지역 부류끼리만 묶은 범위·중앙값을 담당자에게 보여주고, 재정의 사유와 추정 버전을 기록. 표본이 부족하면 "추정 없음".
phase 2(브랜드 "예상 견적"): 승인된 비교 가능 최종 견적만, 조건·기준 시점·신뢰도와 함께, 최종 견적과 다를 수 있음을 명시. 크리에이터 금액·다른 브랜드 식별 정보는 쓰지 않는다.
교차 브랜드 이력 사용 전 계약·약관·개인정보 검토가 필요하다. 모든 기준값은 대표가 정한다.
