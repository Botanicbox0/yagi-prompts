# 영상 제작만 맡기는 고객의 여정 — 점검, 방향, PR 순서 (2026-11-15)

> 대표 지시(2026-11-15): 스튜디오를 쓰지 않고 영상 제작만 맡기는 고객이 의뢰하고, 결과물을 보고, 의견을 나누고, 수정을 받는 과정이
> frame.io 수준으로 되는지 확인하고 고친다. 의뢰 폼이 살아 있는지조차 분명하지 않고, 화면이 불편하게 설계된 느낌이며,
> 의뢰·대화·리뷰를 서비스에 어떻게 녹일지 그림이 없다.
>
> 이 문서는 `docs/BRAND-ROOMS.md`(룸), `docs/BRAND-PROJECTS-E.md`(묶음 E 개편) 위에 쓴다. 두 문서와 다르면 이 문서의 §1 점검 결과가 맞다(2026-11-15 `main` 19decc00 기준, 로컬에서 두 역할로 직접 확인).

## 1. 지금 되는 것과 안 되는 것

확인 방법: 로컬에 `project_only` 플랜 조직을 심고(`scripts/brand-workspace-fixtures.ts`), 쓰기가 남는 로컬 DB(`npm run db:local -- --dir .pglite/dev`)로
고객(`pro` 예시 계정)과 야기 팀(`admin` 예시 계정)을 번갈아 띄워 의뢰 → 납품 → 의견 → 수정 요청 → v2 → 비교 → 승인까지 실제 포인터로 걸었다.
운영은 로그인하지 않고 확인할 수 있는 것만 봤다: 주소는 전부 살아 있고(로그인으로 넘어감), `BRAND_ROOMS`는 켜져 있으며, 0085/0160(의뢰 폼 데이터)은 11-12에 적용됐다.
**운영 화면에 고객으로 들어가 보지는 못했다. 알림 메일은 보내는 코드가 없어 확인할 것이 없다.**

| 단계 | 상태 | 사실 (주소 · 컴포넌트 · 플래그) |
| --- | --- | --- |
| 1. 진입 | 부분 | 로그인하면 `/brand`(프로젝트 목록). 외주 전용 조직은 레일에 프로젝트·대화가 먼저 오고 에셋, 그 아래 스튜디오 항목 4개가 그대로 보인다(누르면 구독 안내 쇼룸). 목록 화면의 말이 "캠페인"이다: "첫 캠페인을 시작해 보세요", "캠페인 의뢰", "전체 캠페인", "캠페인 검색". 같은 곳으로 가는 버튼이 둘이다. `components/brand-workspace/rail-model.ts`, `app/(brand)/brand/page.tsx`, `BRAND_ROOMS` |

## 3. 방향: 프로젝트 하나, 가운데는 작업물

**단위는 "프로젝트" 하나다.** 의뢰 하나가 프로젝트 하나이고, 그 안에 기획서·스토리보드·시안·최종본과 대화가 있다. 고객이 하는 일은 넷뿐이다: 맡긴다, 본다, 말한다, 승인한다.
의뢰·대화·리뷰를 메뉴 세 개로 나누지 않는 이유는, 고객이 묻는 것이 언제나 "내 영상 어디까지 됐지"와 "내가 뭘 해야 하지" 둘이고 둘 다 프로젝트 하나를 열면 답이 나와야 하기 때문이다.

| 고객의 순간 | 화면 | 지금과 달라지는 점 |
| --- | --- | --- |
| 맡긴다 | `/brand/projects/new` | 제출하면 "접수됐어요"와 낸 내용이 룸 첫 화면에 보인다. 야기 팀에 알림이 간다. |
| 기다린다 | 프로젝트 목록, 룸 개요 | 상태가 한 줄이다(의뢰 접수 → 스토리보드 → 시안 → 수정 → 완료). 칩과 단계가 같은 값을 읽는다. |
| 본다 | 작업물 화면 | 작업물이 화면 전체를 쓴다. 룸의 머리말과 탭은 얇은 한 줄로 접힌다. |
| 말한다 | 작업물 위 | 쓰는 순간의 시각이 붙는다. 대화 탭은 그 의견이 모이는 곳이고, 작업물과 상관없는 얘기만 직접 쓴다. |
| 고쳐 받는다 | 같은 작업물의 v2 | 넘어온 의견 옆에 "v2에서 반영"이 보이고, 나란히 비교한다. |
| 끝낸다 | 최종본 | 승인한 버전을 내려받는다. 프로젝트가 끝나면 날짜와 보관 기간이 한 줄로 보인다. |

**레일 "야기 팀과"는 둘로 둔다: 프로젝트, 알림함.** 프로젝트는 목록과 룸이고, 알림함은 모든 프로젝트에서 내가 확인할 것(새 시안, 승인 요청, 답글)을 모은 곳이다.
지금 레일 이름 "프로젝트 · 리뷰", "대화 · 피드백"은 리뷰와 피드백이 따로 있는 것처럼 읽혀서 "프로젝트", "알림함"으로 바꾸기를 권한다(대표 결정 §6-1).

**스튜디오의 "프로젝트"와는 이름을 나눈다.** "프로젝트"는 야기 팀에 맡긴 일에만 쓰고, 직접 만든 결과를 묶는 단위는 다른 이름(예: 폴더)으로 부른다(`BRAND-STUDIO-V6-PLAN.md` §8-4의 답, 대표 결정 §6-6).
둘 사이의 다리는 에셋이다: 납품받은 영상은 에셋에 남아 스튜디오에서 쓸 수 있고, 스튜디오에서 만든 것은 의뢰 폼의 "에셋 고르기"로 참고 자료가 된다.

**없애거나 합칠 화면.** `/brand/studio/review`는 알림함으로 넘긴다. "캠페인·성과 상세" 링크는 크리에이터 캠페인 프로젝트에서만 보인다. 목록의 "최근 제작물"과 룸 개요의 번호 안내는 뺀다.

### 외주 전용 고객과 구독 고객

| | 외주 전용 (`project_only`) | 구독 |
| --- | --- | --- |

## 5. 확인하지 못한 것

- 운영에서 고객으로 로그인한 화면(예전 대화 "읽기 전용" 블록 포함)은 코드로만 봤다: 옛 프로젝트 메시지(`brand_messages`)를 대화 맨 위에 읽기 전용으로 붙이는 동작이고, 고장이 아니다.
- 야기 팀 내부 알림은 운영 환경변수가 있어야 나가므로 로컬에서는 보낸 내용까지만 확인한다.
- 승인본 내려받기가 운영 미디어 주소에서 파일로 저장되는지(다른 도메인이면 새 탭에서 열릴 수 있다)는 운영에서 봐야 한다.
