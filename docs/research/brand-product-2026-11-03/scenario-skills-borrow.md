## 0. 결론 먼저

1. **가장 값진 것은 모델이 아니라 "게이트"다.** Scenario 스킬 82개가 공유하는 뼈대는 네 가지다. 스펙을 먼저 쓴다(brand-kit) → 바뀌면 안 되는 것을 전부 열거하고 바뀌는 것 하나만 마지막 절에 둔다(consistency) → 레퍼런스마다 역할 하나와 "가져오지 말 것"을 쓴다(multi-reference) → 루브릭을 생성 전에 쓰고, 컷 단위로 pass/fail을 기록하고, 라운드 상한을 둔다(refine-loop, quality-gate). 이 네 가지는 TWINGS 고정 층(아이덴티티·절대 규칙·제작 원칙·메모리)과 같은 방향이고 코드 없이 문서·스키마·프롬프트 빌더에 바로 옮길 수 있다.
2. **TWINGS가 이미 갖고 있는 것이 많다.** `lib/design/identity.ts`는 brand-kit의 "spec sheet"와 같은 모양이고, IDENTITY §6-4-3 극소 부위 수정은 refine-loop의 "로컬 결함은 마스크 수정" 경로다. 480p 드래프트 → 승인 → 고해상도는 seedance-drafts의 경제학 그대로다. 그래서 차용은 "새로 만들기"보다 "빠진 칸 채우기"다.
3. **LoRA는 기본값이 아니다. Scenario 자신이 그렇게 말한다.** consistency 스킬의 순서는 프롬프트 베이스라인 → 레퍼런스 → 스타일 레퍼런스 → 컨트롤 맵 → 학습이고, model-training은 "레퍼런스 테스트가 세트 안에서 드리프트할 때만 학습"이라고 못 박는다. TWINGS 고정 층(레퍼런스 + 메모리 + 수치화된 룩)은 이 사다리의 1~3단을 제품으로 만든 것이다. 브랜드별 학습은 조건(§4)이 맞을 때만 고정-제작 원칙 층의 한 칸으로 들어간다.
4. **검수 규칙 초안(§5)은 Scenario의 세 가지 한계 고백에서 출발한다.** AI 품질 게이트는 "artifact를 보지 plausibility를 보지 않고", "레퍼런스를 본 적이 없고", "합성물은 결함을 평균 내 버린다". 그래서 TWINGS 절대 규칙(마크 일치·팔레트 ΔE·금지어·동의)은 점수형 게이트와 별개의 결정적 검사로 두고, VLM 판정은 레퍼런스 대비 spot-the-difference로만 쓴다.
5. **차용하지 않을 것도 분명하다.** 게임·DCC·3D 전문 도구 묶음, 매 세션 모델 재탐색(`recommend`), "모든 단계는 MCP로"라는 표면 규칙, 거부되면 공급자를 바꾸는 모더레이션 루프(IDENTITY §6-1과 충돌)는 가져오지 않는다.

TWINGS와의 거리: Scenario는 범용 생성 플랫폼이고 스킬은 "에이전트가 그 플랫폼을 잘 쓰게" 만든다. TWINGS 브랜드 엔진은 "브랜드만의 고정 층을 두고 바뀌는 것만 새로 만든다"(BRAND-ENGINE §1). 그래서 이 저장소에서 가져올 것은 도구 호출법이 아니라 **무엇을 고정하고 무엇을 검사하는지에 대한 규칙**이다.

## 2. 스킬별 문제와 메커니즘 (37개)

각 항목: 푸는 문제 / 핵심 메커니즘 / 기록값 / TWINGS 메모. 기록값은 전부 저장소의 authoring-time 수치다.

### 2.1 일관성·아이덴티티

**scenario (핵심 루프)**
- 문제: 에이전트가 모델 id를 외워 쓰거나, `dry_run`을 빼먹거나, `job_get`을 폴링한다.
- 메커니즘: 세션마다 scope(team·project) 확인 → 능력은 `recommend`, 이름은 `search` → 스키마 먼저 → `dry_run: true`로 정확한 가격 → `jobs_wait`(타임아웃이면 `pending_job_ids`로 재호출) → 결과는 `asset_display`로만 보여주고 URL을 붙이지 않는다. 파일링(컬렉션·태그)은 "정리"가 아니라 "납품의 일부".
- 기록값: `recommend` 견적 48.2 CU가 실제 55 CU로 청구된 사례 → 그래서 `dry_run`이 필수(docs/decisions.md).
- TWINGS: "가격은 실제 페이로드로 사전 확인"과 "납품 = 파일링 포함"은 §4 10단계 흐름(생성 전 견적, 메모리 적재)에 그대로 맞는다.

**scenario-brand-kit**
- 문제: 애플리케이션마다 로고를 다시 상상해서 "사촌 열 개, 아이덴티티 없음"이 된다.
- 메커니즘: **스펙 시트를 먼저 쓴다**(hex 4~6개 + 역할, 서체 2패밀리 + 역할, 보이스 한 줄, 클리어 스페이스·최소 크기, "never" 규칙 3개). 로고는 벡터로 한 번 만들고 변형(mono·reversed)은 SVG fill을 텍스트 편집. 모든 프롬프트가 hex를 스펙에서 그대로 인용. 게이트는 스펙 전문을 `text_inputs`로 넘겨 글자 단위로 읽는다. 팔레트 검사는 VLM이 아니라 SVG fill 로컬 파싱.
- 흔한 실수: 썸네일 크기에서 괜찮아 보이는 워드마크(글자 드리프트가 거기 숨는다), hex를 "분위기"로 취급.
- TWINGS: `lib/design/identity.ts`의 COLOUR(역할별)·TYPE·HARDLINES가 이미 이 스펙 시트다. 빠진 것은 "클리어 스페이스·최소 크기"와 "never 3개"를 브랜드별 테이블 칼럼으로 두는 것.

**scenario-consistency**
- 문제: "변형 2는 1과 똑같되 X만 바꿔" 요청에 에이전트가 seed를 쓴다. seed는 아무것도 전이하지 않는다.
- 메커니즘: 내구성 오름차순 사다리 — 베이스라인+델타 프롬프트 → 레퍼런스 이미지 → 스타일 레퍼런스(피사체 아님) → `asset_detect` 컨트롤 맵 → 학습 모델. **baseline-plus-delta**: 바뀌면 안 되는 것 전부(기하·카메라 높이·프레임 내 크기·빛 방향·하위 요소 위치·hex·텍스트)를 열거하고, 바뀌는 것 하나를 마지막 절에. 프롬프트는 런 사이에 byte-identical. 세트는 출력→출력 체인이 아니라 매 항목을 같은 승인 베이스라인에 앵커. 영상은 first/last frame만 보지 말고 약 2 fps로 프레임 스윕(10.5초 스팟 체크가 11.0초 결함을 놓친 사례).
- 학습으로 넘어가는 조건: 한 캐릭터가 수백 장에 반복, 4개 이상 아이덴티티가 한 장면, 모든 런이 같은 렌더링 스타일. 캐릭터당 모델 1 + 스타일 모델 1(합치면 적게 본 쪽이 드리프트).
- 기록값: reference-to-video 멤버 슬롯 7~9개, 증명용 롤 80 CU vs 기본값 130 CU.
- TWINGS: §4 2단계 "촬영 지시서"가 곧 베이스라인 열거다. IDENTITY §6-3 "색 블록을 프롬프트 끝에 그대로 붙인다"가 같은 원리.

**scenario-identity-library**
- 문제: 이름 붙은 캐릭터·소품이 세션을 넘어 재사용되지 않는다.
- 메커니즘: 인터뷰 → 베이스라인 열거 → 히어로 1장(중립 전신, 무지 배경) 게이트 통과 → `character: <이름>` 접두사 컬렉션(접두사가 조회 계약) → **게이트 통과 이미지만 입장**(한 장이 오염되면 이후 모든 풀이 오염) → 뷰별 태그(hero·back…) → 시트는 생성이 아니라 Grid Maker 조립(멤버 바뀌면 재조립). 리디자인은 새 히어로 + 이전 멤버 제거.
- TWINGS: 고정-메모리 층의 "승인한 컷"이 정확히 이 라이브러리다. "통과한 것만 메모리에 들어간다"를 규칙으로 명문화할 것.

**scenario-model-training**
- 문제: 학습을 일회성에 쓰거나, 데이터셋 문제를 epoch로 풀려 한다.
- 메커니즘: 견적 전에 **레퍼런스 테스트**(스타일 레퍼런스/히어로 레퍼런스)를 먼저 돌리고 세트 안에서 드리프트할 때만 학습. 순서: `recommend_training`(1회) → `model_create` → 데이터셋 업로드(10 id/호출) → `configure` + `dry_run`(견적만) → 승인 → `start`. `sample_prompts` 없으면 epoch별 체크포인트가 없어 과적합 시 돌아갈 곳이 없다. LoRA는 학습한 base에 묶인다(Z-Image만 변형 간 이동).
- 데이터셋 규칙(references/dataset-curation.md, help.scenario.com 인용): 5~15장(스타일은 ~20), 1024px 바닥, "가르칠 것 하나는 일정, 나머지는 전부 다양", 한 원본에서 파생한 세트는 "같은 낯선 얼굴"을 학습한다. 캡션은 **바뀌어야 할 것만 쓰고 고정할 것은 쓰지 않는다**(스타일 이름을 쓰면 단어에 묶인다). lr/epochs 표: 5~10장 5e-5/15~20, 10~25장 1e-4/10, 25~50장 2e-4/6~8.
- 기록값: 스타일 레퍼런스 테스트가 같은 브리프의 커스텀 LoRA와 비슷한 장당 가격으로 룩을 맞췄다(생성 1회 비용). 학습 비용은 서버 견적이라 숫자 없음(미확인).
- TWINGS: §4 참고. 학습 여부를 정하는 "드리프트 측정" 절차 자체가 차용 대상.

**scenario-multi-reference**
- 문제: 레퍼런스는 보여주는 전부를 빌려준다. 스타일로 준 너구리 요리사가 장면에 걸어 들어온다.
- 메커니즘: **그림마다 역할 하나**(WHO·WHERE·POSE·ANGLE·STYLE·LIGHT·PALETTE·MATERIAL·EXPRESSION·WEAR·INSPIRATION·LAYOUT) + 그림마다 "가져오지 말 것" 한 줄. 무시되기 쉬운 역할(보통 STYLE)을 맨 위에 "가장 중요"라고. 역할 충돌은 명시로 해결(팔레트 카드가 있으면 스타일 줄에 "색은 복사하지 말 것"). 레퍼런스 **누수 점검**: 역할은 보이는가, 역할 밖의 것이 보이는가. 고치는 법은 그 줄을 조이고 다시 돌리는 것이지 리터치가 아니다.
- 흔한 실수: 레퍼런스 안의 실제 간판·로고가 모델 거부를 부른다 → "invented, blank signs, no logos"로 카드를 다시 만든다.
- 기록값: 선두 멤버 4~5장, 일부 10장.
- TWINGS: IDENTITY §6-4-3 "이미지 1은 프레임·배경 픽셀 그대로, 이미지 2는 로고 모양만"이 같은 문법이다. 지시서 생성기에 역할표를 스키마로 넣으면 된다.

**scenario-product-shots**
- 문제: 텍스트로 만든 병은 잘못된 라벨을 랜딩에 올린다.
- 메커니즘: **제품은 절대 생성하지 않는다**. 업로드 사진에서 시작 → `asset_analyze`로 라벨 텍스트·기하·재질·색 **체크리스트를 1회 작성**해 모든 검사에 재사용 → preserve-first 프롬프트("레퍼런스의 그 캔, 비율·색 그대로, 라벨은 'X'라고 읽힘, 다른 텍스트 없음, 젖은 슬레이트 위, 아침 측광") → 장면당 1런 → 출력 최대 10장을 한 번에 체크리스트 대비 글자 단위 판독. 출력 해상도에서 읽을 수 없는 텍스트는 "미검증"이지 통과가 아니다. 가격·주장·프로모 카피는 이미지에 넣지 않고 오버레이.
- TWINGS: 절대 규칙 "마크 일치" 검사의 입력이 바로 이 체크리스트다. `brand_assets`(§21.5) 제품 레코드에 체크리스트 칼럼을 두면 §4 5단계가 자동화된다.

### 2.2 검수·반복·비교

**scenario-quality-gate**
- 문제: 점수 하나로 자산을 정렬만 하고 다음 런에 피드백을 넣지 않는다.
- 메커니즘: 도구 한 개(`asset_quality_gate_run`)가 pass/warn/fail + 0~100 점수 + 차원별 `reasons`/`suggestions`. 저장된 판정 읽기는 무료, 새 분석은 과금, `rerun`은 브리프/민감도가 바뀐 뒤에만. 피드백 루프: `reasons`로 결함별 수리 경로(로컬 결함 → 마스크 인페인트, 전역 → 재생성), `suggestions`는 전부 다음 프롬프트에 흡수. 같은 결함 클래스가 점수 변화 없이 반복되면 모델 교체. 종료 기준과 라운드 상한(기본 3)을 미리 정한다.
- **한계 3가지**(실측): (1) artifact 탐지기지 plausibility 판정이 아니다 — 바퀴 두 종류·바퀴집 없는 차가 92점 pass. (2) 레퍼런스를 본 적이 없다 — 플레이트와 같은 차인지 알 수 없다. (3) 합성물은 평균 낸다 — 12패널 보드가 불가능한 패널 하나를 품고 88점 pass. 수리 성공도 점수로 못 본다(깨진 패널과 고친 패널 둘 다 92).
- 기록값: Enterprise 애드온, 새 분석 1 CU.
- TWINGS: 이 세 한계가 §5 초안의 설계 근거다.

**scenario-refine-loop**
- 문제: 첫 롤을 그대로 받거나, 프롬프트 전체를 바꿔 가며 예산이 죽을 때까지 재롤.
- 메커니즘: 루브릭(취향 단어 금지, 보는 사람이 확인 가능한 pass/fail 문장) → 레시피를 시험할 최소 배치, 판정 가능한 가장 싼 티어 → 비평은 10장/호출, 출력 형식 고정 `<index>: pass|fail, <실패한 줄>` → 실패 줄마다 **가장 싼 수리**로 라우팅(로컬 결함 → 마스크; 균일 마감 → 결정적 도구; 내용·구도·팔레트 → 델타 절 수정 후 베이스라인에서 재런; 아이덴티티·스타일 → 열거 강화·레퍼런스 재역할; 전부 실패 → 모델 교체) → 라운드당 변수 하나 → 깨끗한 라운드면 종료, 3라운드 실패 또는 한 줄이 다른 수리로 2회 실패면 보고.
- 두 규칙: 판정은 루브릭을 인용한다("더 좋을 수 있음"은 판정이 아니고, 그걸 좇으면 generic으로 수렴). 재생성은 베이스라인에서, 마지막 시도에서가 아니다.
- TWINGS: §4 6단계 부분 수정과 10단계 메모리 사이에 이 루프가 빠져 있다. 관리자 검수 화면의 판정 기록 형식으로 채택.

**scenario-model-comparison**
- 문제: 모델 비교가 "느낌"으로 끝난다.
- 메커니즘: 브리프·입력·기준(pass/fail 3~5개)을 **첫 유료 호출 전에** 기록 → 후보 3~5 → 정규화(같은 프롬프트 byte-identical, 같은 레퍼런스, 출력 1개, 프롬프트 확장 플래그 끄기, seed는 모델 간 비교 불가) → `dry_run` 비용 매트릭스 + 예산 게이트(커밋 + 다음 견적 + 남은 예약 ≤ 상한) → 동시 런 → 청구 비용은 job 행, 시간은 createdAt→updatedAt → 그리드 시트 + 각 자산 원본 크기 → 표로 납품. 영상은 contact sheet로만 비교. 승자는 브리프·카탈로그별 상수가 아니다.
- TWINGS: IDENTITY §6-1 모델 역할표가 "대표의 Americano 결과"에서 고정됐다. 역할표를 갱신할 때 쓰는 재검증 절차로 문서화하면 된다. 공개 페이지엔 엔진 이름을 쓰지 않는다는 규칙은 유지.

**scenario-asset-analysis**
- 문제: 배치가 떨어진 뒤의 질문(브리프에 맞나, 어떤 룩인가, 지난주 승인본은 어디 있나)에 답하지 못한다.
- 메커니즘: 고정 목적 3개(`asset_caption`, `asset_describe` = 재사용 가능한 룩 합성, `asset_detect` = 컨트롤 맵)와 자유형 1개(`asset_analyze` = 지시문 + 이미지 10장 + 텍스트 10개). 배치는 10장/호출이라 200장 리뷰는 20호출. 출력 형식을 지시문에 고정해야 파싱된다. **렌더를 읽지 파일을 읽지 않는다**: 16-path SVG를 raster라 했고 `#101614`를 `#131A18`로 읽었다 → 정확한 색·구조는 파일 파싱. 검색은 키워드/의미 비율, 유사도(like/unlike), 구조 필터.
- TWINGS: §21.5 태깅·검색(VLM 어댑터 + pgvector) 설계와 겹친다. "정확한 값은 파일에서, 판단은 렌더에서" 분리를 설계 원칙으로.

**scenario-inspiration**
- 문제: 영감을 요청하면 에이전트는 평균을 낸다. 비슷한 브리프마다 같은 룩.
- 메커니즘: prime(잠긴 제약·열린 축·반사 답 2개를 배제·히트 기준) → widen(팀 자산·공개 카탈로그·웹·사용자 4레인 + 와일드카드) → choose(한 축 위에 상호 배타적 3~4방향, 버린 것도 말한다) → board(컬렉션). 보드의 레퍼런스마다 **role·why·take** 3필드. 한 축에 한 세계(하드 플래시와 소프트 윈도우 레퍼런스는 생성 시 상쇄). 단일 출처가 지배하면 모작. 모델에는 3~6장만, 역할 태그와 함께. 프롬프트는 보드의 축(형태군·명도 범위·재질·디테일 밀도·빛 방향·팔레트)으로 쓰고 "cinematic·beautiful·8K"는 아무것도 보존하지 않는다.
- 기록값: 무드보드 15~20장, 안티 레퍼런스 4~8장당 2~3장.
- TWINGS: 브랜드 메모리 캠페인 층(§21.3 ②)의 무드보드 스키마. 대표의 "비물질 요소를 글로 옮긴다"(PLATFORM-2.0 §21.4)와 같은 원리.

**scenario-storyboards**
- 문제: "6패널 페이지"를 한 번에 생성하면 고칠 수 없다.
- 메커니즘: 생성 단위는 페이지가 아니라 **패널**. 스크립트 표(샷 크기·앵글·행동·대사) → 캐스트 락 → 패널당 1런(베이스라인 byte-identical + 패널 절 + "clean art, no lettering") → 리뷰 → 레터링은 오버레이 → 조립. 지속되는 변화(4패널부터 새 의상)는 새 히어로를 승인하고 베이스라인을 다시 쓴다.
- TWINGS: 이미지 세트 템플릿(#103)과 리믹스의 "컷 단위" 원칙과 일치.

### 2.3 영상·오디오·마감·포맷

**scenario-video-color-grade**
- 문제: 색 보정을 생성 모델에 맡기면 프레임마다 달라지고 편집 불가.
- 메커니즘: 그레이드는 **코드가 쓰는 수학**(33³ `.cube` LUT, 공간 연산은 numpy) → 결정적, 매 프레임 동일, Premiere/Resolve에서 편집 가능. 프리셋(로그 변환·필름 스톡)은 플랫폼 도구, 조정·발명·레퍼런스 매치·마스크는 로컬 레시피. **스틸 테스트 먼저**(초 단위) → 키 측정(`inspect_frame` grid/sample/key) → 리라이트 0.3~1스톱 → 레퍼런스 매치(Reinhard, Lab) → 렌더 → 프레임 수 일치 확인 → 릴. 한 소스의 튜닝을 다른 소스에 쓰지 않는다. 룩 이름에 영화·필름 브랜드 금지.
- 기록값: 12룩 × 8초 루프 112 CU(마스크 2 + 음악).
- TWINGS: §4 8단계 "레퍼런스에 맞춘 색 보정 값을 브랜드 룩으로 저장"의 구현 원형. 메모리의 색 층 = LUT + 측정값.

**scenario-video-assembly**
- 문제: 플랫폼에 편집 도구가 없다는 오해, 레이어 계약 오류.
- 메커니즘: concat(순차, 2~50클립, 전환은 N-1)과 compose(절대 타임라인, 레이어 1~50, `startTime`/`zIndex`, `trimStart/End`는 "깎는 양") 분리. **모든 오버레이 레이어에 width/height 명시**(비워 두면 560×80 스트립이 1792×256으로 나온 사례), `fit: contain`(기본 `fill`은 늘린다). 텍스트 레이어 없음 → 제목·엔드카드는 PNG. 캡션은 마스터에 마지막 1회. concat의 오디오 드리프트 확인(길이 합, 스트림 길이, 큐와 사운드). 수정 인계를 위해 제출한 페이로드·측정 타이밍·SRT를 보존.
- TWINGS: 마감 파이프라인 문서(yagi-crm) 체크리스트로 참고.

**scenario-video-editing**
- 문제: 영상 효과 id·필드명이 이웃끼리 다르고, 비용이 클립 길이를 따른다.
- 메커니즘: 이미지 효과의 "-video" 쌍둥이 규칙. **비용은 푸티지를 따르므로 트림 먼저**. 프레임 추출 결과는 순서가 깨질 수 있어 그리드로 연속성 확인 후 id 리스트를 들고 다닌다. 투명 컷아웃은 mp4로 못 나간다(WebM/ProRes). **resize ≠ reframe**: 16:9를 세로로 만드는 건 생성형 reframe(비쌈)이거나 compositor crop(싸지만 버림)이고, 그 결정은 지출 전에.
- TWINGS: §4 9단계 채널별 비율 내보내기 사다리의 근거.

**scenario-audio**
- 문제: 오디오 스키마는 모델마다 전혀 다르다.
- 메커니즘: 음악·SFX·음성 3레인 + 영상→오디오 + 유틸. SFX 프롬프트는 소스·재질·행동·공간 + 제외("no music"). 음성 태그 문법은 멤버마다 다르고 틀린 태그는 읽혀 버린다. 노래는 스타일 필드에 가사를 넣지 않는다. 연장은 별도 audio2audio 레인. `dry_run`과 `wait`는 `parameters` 밖.
- TWINGS: §4 8단계 사운드 마감(−14 LUFS)과 music-creator 보류(CC BY-NC)에 참고. 사람 목소리 복제는 소유자 동의 — 초상권 절차와 같은 결로 둔다.

**scenario-elevenlabs**
- 문제: 11개 멤버가 거의 아무것도 공유하지 않는다.
- 메커니즘: 작업별 멤버표(표현 음성·고정 언어·대량·음악·구조화 노래·SFX·더빙·재녹음·노이즈 제거). `voiceId`가 항상 이긴다. 더빙은 트랙만 바꾸고 입은 안 바꾼다. 비용은 콘텐츠(글자 수·초·섹션)를 따른다.
- TWINGS: 참고만. 외부 발송 문안·음성은 대표 영역.

**scenario-ace-step**
- 문제: 모드마다 모델이 다르고 seed가 없다.
- 메커니즘: Text-to-Music·Cover·Repaint(Turbo/Quality) + 편집 3종. Turbo로 반복, Quality로 최종. 리페인트는 창 안을 재생성하므로 가수가 바뀔 수 있다 → 배치로 뽑아 고른다. 가사 교정은 Cover로 후보를 만들고 **들어서** 확인한 뒤 구간만 잘라 로컬에서 이어 붙인다.
- TWINGS: 음악 생성은 보류 상태라 참고만.

**scenario-caption-studio**
- 문제: 캡션 파라미터는 목적지가 결정하는데 매번 스키마부터 본다.
- 메커니즘: 한 번 묻고(어디 올리나, 번역하나, 브랜드색, 산출물) → 목적지→스타일·분절·위치·출력 표. SRT-only 패스로 **단어부터 증명**(같은 가격). `transcriptionPrompt`는 철자 힌트지 보장 아님. 교정 SRT는 base64 인라인(asset id를 넣으면 성공으로 보고하며 캡션 0개). 리뷰: 사이드카 텍스트 대조 → 2 fps contact sheet로 철자·대소문자·위치 → 큐 경계 전후 프레임 → 오디오·비디오 스트림 길이 분리 확인. CJK는 라틴 분절 캡이 안 맞는다.
- TWINGS: 캡션은 오버레이·마감 단계. "성공 job ≠ 렌더 증명"을 검수 규칙에.

**scenario-text-overlay**
- 문제: 생성 모델은 글자에서 드리프트한다.
- 메커니즘: 정확해야 하는 텍스트는 **결정적으로 렌더해 합성**. JSON 페이로드 1개 = 오버레이 1개(text layer 또는 HTML rich layer), 바뀌는 문자열은 전부 `variables`(Mustache strict). 출력 PNG에 페이로드를 `tEXt` 청크로 임베드 → 파일만으로 재생성 가능. 플랫폼에는 PNG + 페이로드를 `metadata.description`으로 보존. 서체는 의미로 고른다(응축 산스 = 외침, 기하 산스 = 프리미엄). 캔버스는 목적지 해상도와 1:1. 플레이트는 오버레이 영역을 비워 두고 생성.
- TWINGS: 로고·태그라인·법적 문구 카드. 브랜드 자산의 "카피 카드" 모델로 변형 차용.

**scenario-formats**
- 문제: 포맷마다 다시 프롬프트하면 "사촌 다섯"이 된다.
- 메커니즘: 결정 사다리(같은 비율 다른 픽셀 → resize; 가장자리 버려도 됨 → cover crop; 캔버스 확장 → expand; 다른 비율 재구성 → generative reframe; 먼 비율 → 마스터를 레퍼런스로 원 생성). 순서: 텍스트 없는 마스터 승인 → 모든 포맷은 마스터에서(파생의 파생 금지) → reframe/expand 후에 그레이드·그레인 → 측정으로 검증(4:5 요청이 29:36으로 온 사례) → 레터링은 마지막, 포맷별 안전 영역 안에.
- TWINGS: §4 9단계 그대로.

### 2.4 광고·소셜·시퀀스

**scenario-video-ads**
- 문제: 제품 샷 한 장과 브리프를 광고로 만들 때 단계가 섞인다.
- 메커니즘: 디렉터 층. 두 규칙 — **제품은 생성하지 않고, 텍스트는 생성하지 않는다**. 브리프는 한 번(목표 1개: awareness/consideration/conversion 중 하나만, 둘이면 거부; 청중은 마음 상태; 단일 제안; 창의성 다이얼 on-code/twist/wild; 길이 6/15/30s; 지출 상한) → 콘셉트 1쪽 → 스토리보드(패널별 카메라 1무브·조명·컨디셔닝·사운드·초) → **가격 매긴 보드가 유일한 승인 지점**(영상이 비싼 단계) → 스틸(비율별 원 구성) → 애니메이트(이미지→영상, `generateAudio: false`) → **fidelity gate**(프레임 추출 → 승인 레퍼런스 대비 spot-the-difference; 라벨 드리프트면 clip fail, 같은 스틸에서 재생성) → 오디오(BPM 먼저) → 조립 → pre-flight.
- 재시도 바닥(계획 가정): 제품만 3회, 복잡 모션 5~10, 얼굴·손 최대 20 → 그래서 사람을 피한다. 비율 체크리스트(길이:높이, 라벨:면)를 수치로 두고 "실루엣 일관" 같은 말로 통과시키지 않는다.
- 납품(delivery.md): 9:16 안전 영역(상 14%·하 35%·좌우 6~13%, 2026 기준 기록값), 플랫폼별 정확한 길이, 소셜 −14 LUFS/−1 dBTP, CTV −24 LKFS/−2 dBTP, 1초에 3회 초과 플래시 금지, 무음 패스.
- TWINGS: §4 흐름에 "승인 지점은 어디인가"가 빠져 있다. 2단계 지시서 승인 + 7단계 영상 전 견적 승인을 명시.

**scenario-ad-variants**
- 문제: 기존 푸티지에서 변형을 만들 때 성공한 것까지 다시 돌린다.
- 메커니즘: 변형마다 안정 라벨 + 소스 + 델타 + 불변 + 정확한 카피 + 출력 스펙 + 오디오 정책을 **기록**. 모든 변형은 소스에서 시작(마지막 변형에서가 아니라). 상태(blocked/planned/submitted/pending/failed/verified)와 **제출한 페이로드 그대로** 보존. 비교 실험이면 변수 하나만. 렌더 성공 ≠ 검증(오버레이가 안 그려진 성공 job).
- TWINGS: 브랜드 메모리의 "작업 기록" 행 모양으로 참고.

**scenario-ugc**
- 문제: 광고 문법을 UGC에 들여오면 믿음이 죽는다.
- 메커니즘: 두 규칙 — 제품 생성 금지, **말을 지어내지 않는다**(후기·숫자·효능·법적 문구 없음, 관찰 문장 > 주장). 스크립트 6비트(훅·맥락·제품·증거·반전·마무리), 입으로 쓴다. 발화 속도 기록값 1.76~1.94 단어/초(아바타 멤버가 60단어를 21초 침묵으로 채운 사례). 9:16 원 구성. 모든 생성 클립 게이트(말하는 얼굴 포함) — 손에 없는 제품, 읽히는 생성 자막은 fail.
- TWINGS: 크리에이터 캠페인 브리프의 "claims surface" 규칙. 약관 문구는 대표 영역이라 제안만.

**scenario-seedance-storyboard**
- 문제: 샷별 프롬프트로는 움직임이 컷마다 리셋된다.
- 메커니즘: 타임코드 스크립트(샷 번호·크기·앵글·렌즈/무브·동사 3개·입·출 포즈) → 캐릭터당 플레이트 1장(합본 시트 아님) → 패널은 **얇은 연필선, 맨 종이**(사진형 보드는 패널 번호가 8샷 중 6샷에 새겨졌고, 진하게 그린 연필 보드는 화살표가 물체로 렌더됨; 얇게 그리면 0/93 누수) → 패널당 1런 → **두 패스 게이트**(artifact 점수 + 플레이트 대비 차이: 개수·부착·부분-전체·의상·화면 쪽) → 보드 조립(비율 0.4~2.5 안) → 사진형 키프레임 2~3장 → 승인 → 영상(스크립트 1런 또는 체인) → 0.5초마다 샘플링 검사. 프롬프트 7섹션 중 "GUIDES ARE NOT CONTENT"는 금지문이 아니라 **정의문**("보드의 테두리·번호·화살표는 감독이 종이에 그린 계획 가이드이고 세계의 물체가 아니다")이어야 작동했다.
- 기록값: 수리한 패널 47 CU vs 보호한 영상 런 2,730 CU.
- TWINGS: Video-Creator `seedance-film-director`의 "영상 분석 → begin/end 프레임 → 작성 → 측정" 흐름과 결이 같다. "금지 대신 정의" 문법은 바로 차용.

**scenario-seedance-drafts**
- 문제: Seedance에는 seed가 없어 승인한 테이크를 다시 만들 수 없다.
- 메커니즘: 480p 드래프트(`draft: true`) → 리뷰·랭킹(2 fps contact sheet 전체 + 손·머리카락·얼굴 4지점·고정 소품 클로즈업 + 속도로 시청) → 선택한 테이크만 1080p 완성(같은 테이크, 7일 이내). 경제학: 드래프트+완성 ≥ 직접 1080p(15초 편집 2,040 vs 2,024 CU; 4초 레퍼런스 544 vs 456 CU 기록값). 테이크 5개 + 완성 1 ≈ 3,500 CU vs 1080p 5개 ≈ 10,100 CU. 단일 테이크는 드래프트가 더 비싸다.
- TWINGS: IDENTITY §6-1 "480p 드래프트를 대표에게 보여주고 승인 뒤 고해상도"가 이미 같은 관행. 비용 산식만 문서화.

### 2.5 운영·플랫폼

**scenario-workflows / scenario-workflow-authoring**
- 문제: 저장된 그래프 실행과 편집이 컨텍스트를 넘치게 하고, 입력 키를 추측한다.
- 메커니즘: 목록은 `limit ≤ 3`(레코드가 1,900~22,000자). 입력 키는 `inputs[].name` 그대로(노드 이름 아님). `dry_run`이 실제 검증기이고 긴 텍스트 캡을 무비용으로 찾는다. forEach는 1회분만 견적 → 항목 수로 곱한다. 편집은 `editor_info` 전체의 read-modify-write, `publish`가 컴파일. 다중 자산을 한 모델 입력에 넣으면 "한 장으로 섞인 결과". 외부 노드 툴 그래프는 import가 아니라 표로 줄여 번역.
- TWINGS: 레시피 v2(`lib/recipes`)의 가격 미리보기·입력 계약 문서에 참고.

**scenario-moderation**
- 문제: 거부를 전부 "문구 문제"로 본다.
- 메커니즘: 게이트 3종을 **먼저 식별**(공급자 콘텐츠 필터 / 팀 IP 탐지 / 플랜·블록리스트). 차단은 라우팅 문제 먼저, 문구 문제 둘째. 트리거는 누적(인식 가능한 캐릭터, 강도 표현 "oversized", 실존 인물 닮음). 오디오는 "no music" 같은 제외문이 필터를 건드린다 → 디제틱 사운드를 양성으로 명명. 공급자 교체 → 비율로 규모 표현 → 이름 대신 레퍼런스 → 상류 리라이터 제약 → 그래도 거부면 **멈추고 사용자에게**(변형을 갈아 끼우는 건 회피).
- TWINGS: **충돌 주의.** IDENTITY §6-1은 "업체가 정책으로 거부한 이미지는 다른 업체에 올리거나 잘라서 재시도하지 않는다. 대표에게 알린다"다. 차용할 것은 "어느 게이트가 울렸는지 분류"와 "오디오 양성 명명"뿐이고 공급자 교체 루프는 가져오지 않는다.

**scenario-report**
- 문제: 버그 보고가 재현 불가능하고 비밀이 샌다.
- 메커니즘: 분류 → 수집(실패 호출·에러 원문·`diagnostics_run`) → **먼저 가리기**(키·서명 URL·이메일·사용자명 경로·미공개 아트; team/project id는 기본 제거, 진단에 필요할 때만 묻고 "예" 아니면 아니오) → 중복 검색 → 초안(추측은 추측이라 표시) → 사용자 승인 뒤 게시. 계정·결제는 공개 이슈 금지.
- TWINGS: AGENTS §0 비밀값 규칙과 같은 결. 내부 버그 리포트 템플릿으로 참고.

**scenario-team-admin**
- 문제: 팀 거버넌스를 에이전트에서 하면서 모드를 안 읽는다.
- 메커니즘: blocklist/allowlist 모드를 먼저 읽는다(같은 `add_models`가 반대 뜻). 팀 쓰기는 OAuth의 사람 관리자만(API 키 거부). 멤버별 소비 상한(CU, 기간), 초대 32명 배치, 삭제는 목록→이름 확인→삭제. 키 생성은 MCP가 아니라 포털(비밀이 대화를 지나지 않음). 사용량은 날짜 범위 필수(미지정은 프로젝트 평생치).
- TWINGS: brand.twings.app 설정(팀·권한·MCP 토큰은 해시만) 설계에 "모델 허용 목록"과 "멤버 지출 상한" 개념만 참고. 요금제는 대표 결정 전.

**scenario-admin-analytics**
- 문제: 사용량 숫자를 중복 계산하거나 할인을 두 번 뺀다.
- 메커니즘: 날짜 양끝 포함, UTC 버킷 명시, 당일 수치는 잠정. `totals.totalCU`는 할인 후, 모델 CU도 할인 후 → 다시 빼지 않는다. 모델 CU ≠ 전체 소비(환불·비모델 작업) → 차이를 보여주되 원인 단정 금지. 사용자×모델 매트릭스는 사용자별 동일 scope 질의, 비례 배분 금지. 캐시는 scope·날짜·섹션으로 키, TTL 1시간. "ROI·시간 절약"은 usage로 입증 불가라고 못 박는다.
- TWINGS: 관리자 리포트(Phase 4 §10)와 캠페인 리포트의 회계 원칙으로 참고.

### 2.6 모델 패밀리 (TWINGS 라우팅 표와 교차)

**scenario-seedance**
- 메커니즘: 모드는 입력이 결정(`image` = 첫 프레임, `referenceImages` = 아이덴티티·세계, `referenceVideos` = 편집/연장). **컨디셔닝 규칙**: 레퍼런스 모드는 1프레임을 레퍼런스 세계의 기본 상태에 앵커하므로, 특정 상태로 열어야 하면 그 스틸을 `image`로. `@image1`은 배열 순서로 바인딩, 각 태그가 무엇을 지배하고 무엇을 안 건드리는지 쓴다. `duration` 기본 Auto는 30초 캡으로 과금된 사례. 사운드는 디제틱만 양성 명명, 음악은 따로(샷마다 키·템포가 리셋). 카메라 파라미터 없음 → 프롬프트에 지배 무브 1개.

**scenario-kling**
- 메커니즘: 18개 스페셜리스트 중 작업으로 고른다(Omni 모든 모드, I2V 티어, O1 레퍼런스, 모션 컨트롤, 립싱크, 아바타). `multiPrompt` 멀티샷, `elements`(정면 + 각도 4장). 예산은 영상 옆에서 줄어든다. 오디오는 멤버별 스위치. 4K·아바타는 `dry_run` 필수(아바타 비용 100배 범위 기록값). seed 없음 → 4K 재런은 새 테이크, 업스케일은 테이크 유지.

**scenario-seedream**
- 메커니즘: 5.0 Pro(레퍼런스 10, 정확 픽셀 672~3136 step 16, 정확한 인이미지 텍스트), Lite(14장, 시퀀스 모드), Flash(가장 쌈, `background: transparent`로 알파 보존 — 레퍼런스 1장이 알파를 가질 때만), 4.5, Layerize(이미지 분해, PSD 없음). 싼 멤버로 반복, Pro로 최종. 텍스트는 정확히 인용 + 위치 + 크기 순위, 틀리면 글자 단위 철자, 그래도 틀리면 포스트.

**scenario-gemini-image**
- 메커니즘: 하나의 `prompt`, 편집은 마스크가 아니라 지시문("모양·색·브랜딩은 그대로, 햇빛 든 데크에"). 레퍼런스 역할을 위치로("image 1은 얼굴, image 2는 옷"). 틀린 단어는 디자인을 다시 뽑지 말고 keeper를 레퍼런스로 넣고 철자만. 비용 절벽은 해상도보다 멤버 사이.

**scenario-gpt-image**
- 메커니즘: `quality`가 가격 다이얼(1024 정사각 2/3/12/20/45 CU 기록값), 사이즈 그리드 벗어나면 **에러 없이 다른 크기**로 돌아온다 → `asset_get`으로 측정. 마스크는 알파만 읽고 "가이드"로 취급 → 픽셀 동일이 필요하면 승인 편집을 원본 위에 합성. 투명 배경 알파 최대 254, 투명 픽셀 아래 색 후광. 7개 넘는 요구는 조용히 빠진다 → 깨끗한 베이스 + 편집당 변경 1개.

## 4. 커스텀 모델 학습(LoRA) vs 고정 층

### 4.1 두 접근의 차이

| 축 | Scenario (consistency · model-training) | TWINGS 고정 층 (BRAND-ENGINE §3) |
| --- | --- | --- |
| 일관성의 1차 수단 | 프롬프트 베이스라인 → 레퍼런스 → 스타일 레퍼런스 → 컨트롤 맵. 학습은 마지막 | 아이덴티티 스키마(색 역할·빛·렌즈·그레이드·서체·이미지 색 대역) + 기준 자산 + 모델별 프롬프트 원칙 + 메모리 |
| 학습 조건 | 한 캐릭터가 수백 장에 반복 / 4+ 아이덴티티 한 장면 / 모든 런이 같은 렌더링 스타일 | 조건 없음(현재 학습 경로 없음). 사람은 Higgsfield Soul(얼굴 학습)로 이미 "학습형" 경로 보유 |
| 학습 대상 | 캐릭터당 모델 1 + 스타일 모델 1. 합치면 드리프트 | 해당 없음 |
| 데이터 | 5~15장(스타일 ≤20), 1024px 바닥, 한 원본 파생 금지, 캡션은 변수만 | 승인한 컷이 메모리에 쌓임(데이터셋 후보가 자동으로 생긴다) |
| 비용·시간 | 서버 견적(수치 미확인). epoch가 선형 비용. 학습은 1회, 추론은 영원 | 레퍼런스 슬롯 비용만(Seedream 5.0 Pro 10장, NB 14장, Seedance 2.5 30장 — 기록값, TWINGS 경로(ARK·Morphic·Higgsfield)에서 미확인) |
| 되돌리기 | LoRA는 base에 묶임(Z-Image만 변형 간 이동). 모델 세대 교체 시 재학습 | 스키마·레퍼런스·프롬프트 원칙은 엔진을 바꿔도 남는다(모델 이름은 설정값, §21.5) |
| 검증 | epoch 미리보기(`sample_prompts`), 오프데이터셋 프롬프트로 과적합 판별 | 절대 규칙 검사 + 사람 검수 |

핵심 차이는 **무엇이 "브랜드"를 들고 있느냐**다. Scenario는 가중치가 들고, TWINGS는 스키마·레퍼런스·메모리가 든다. TWINGS 쪽이 엔진 교체에 강하고 설명 가능하며(왜 이 색인지 hex로 말할 수 있다), Scenario 쪽은 말로 못 쓰는 "손맛"(일러스트 스타일, 특정 질감)을 들 수 있다.

### 4.2 합치는 방법: 학습은 고정-제작 원칙 층의 "선택 칸"

- 기본 경로는 **멀티 레퍼런스 + 수치화된 룩**이다. 다음 조건이면 충분하다.
  - 제품 충실도가 실사진에서 온다(제품은 생성하지 않으므로 학습할 이유가 없다).
  - 룩이 수치로 표현된다: 렌즈·각도·거리, 프레임 내 비율, 빛 방향과 질, 영역별 hex, 들뜬 검정, 채도, 심도, 입자(PLATFORM-2.0 §21.4; `extract_image.py`로 측정). Scenario의 "스타일 레퍼런스 테스트가 LoRA와 비슷하게 맞췄다"는 기록이 이 경로를 뒷받침한다.
  - 레퍼런스 슬롯이 4장 이상이고(역할 4~5개면 충분), 한 장면에 지켜야 할 아이덴티티가 3개 이하다.
  - SKU 수가 적고(브랜드당 열 개 안팎), 세트 크기가 수십 장 단위다.
- **학습이 값질 수 있는 조건** (전부 Scenario 기준을 TWINGS 소비재 맥락으로 옮긴 것):
  - 브랜드 고유의 **비사실 스타일**(일러스트·패턴·텍스처 패밀리)이 있어 말과 레퍼런스로 재현이 안 될 때. 사진형 룩은 수치로 충분하다.
  - 마스코트·가상 앰배서더가 **수백 장**에 반복될 때. 사람 얼굴이면 이미 Soul 경로가 있고, 동의 절차(본인 얼굴만, 제공사 검수)는 그대로다.
  - 한 장면에 **아이덴티티 4개 이상**이 함께 나올 때(레퍼런스 슬롯이 주의를 나눠 가진다).
  - 생성량이 **수천 장** 단위로 커져 런마다 레퍼런스를 싣는 비용이 학습 1회 비용을 넘을 때.
  - 데이터: 승인한 컷 10~20장이 **한 미감**이고 서로 다른 샷이어야 한다(한 원본 파생 세트는 금지). 메모리 층이 쌓여야 생기는 조건이라 초기에는 성립하지 않는다.
  - 어떤 모델에서 가능한가: Scenario는 Flux 2·Z-Image·Qwen 계열 LoRA(help.scenario.com 인용). TWINGS 엔진(Seedream 5.0 Pro, Nano Banana Pro, Seedance 2.5)의 TWINGS 경로(ARK·Morphic·Higgsfield)에서 브랜드 LoRA가 가능한지는 **미확인**. 가능하더라도 공개 페이지에는 엔진 이름을 쓰지 않는다.
- 학습을 넣더라도 **절대 규칙 검사와 사람 검수는 바뀌지 않는다**(BRAND-ENGINE §6 "검사 결과는 사람 검수를 대신하지 않는다"). 학습 모델은 "제작 원칙" 층의 모델 라우팅 표에 한 행으로 들어가고, Scenario처럼 `runs_as`(base + 가중치)로 기록한다. 학습 전후 판정은 model-comparison 절차(사전 등록 기준, 같은 브리프, contact sheet)로 한다.
- 메모리 층 설계에 미리 넣을 것: 승인 컷마다 "변하는 것" 캡션(포즈·배경·빛)과 "고정" 태그를 분리 저장한다. Scenario의 캡션 원칙("바뀌는 것만 쓴다")을 메모리 스키마에 넣어 두면 훗날 학습 데이터셋이 추가 작업 없이 나온다.

## 5. 검수 규칙 초안 — Scenario 판정 기준 + TWINGS 절대 규칙

원칙 다섯 가지.
1. **결정적 검사와 판단형 검사를 분리한다.** 마크·팔레트·금지어·동의는 파일·수치·DB로 판정하고, VLM은 "레퍼런스 대비 차이"와 "구조(개수·부착·비율)"만 본다. VLM이 hex를 읽게 하지 않는다(asset-analysis 실측).
2. **판정 단위는 컷·프레임이다.** 세트·보드·클립의 평균 점수는 판정이 아니다(quality-gate 한계 3).
3. **점수가 아니라 결함 목록이 판정이다.** 수리 성공 여부는 점수 변화가 아니라 결함 목록의 변화로 본다.
4. **루브릭은 생성 전에 쓴다.** 배치를 본 뒤 쓴 루브릭은 배치의 결함을 기준으로 삼는다.
5. **사람 검수는 대체하지 않는다.** 자동 검사는 정렬·경고·차단 조건이고, 공개·납품 승인은 사람이 한다(BRAND-ENGINE §6, AGENTS §4).

루프 규칙(refine-loop에서).
- 생성 전에 루브릭(R1~R10 중 이 작업에 해당하는 줄)을 기록한다.
- 컷마다 `pass|fail, <실패 줄>`을 기록한다. 기록 없는 인상은 쌓이지 않는다.
- 실패 줄 → 가장 싼 수리: 로컬 결함(로고 흐림·옷 디테일·피부) → §6-4-3 부분 수정 / 균일 마감(톤·크롭) → 결정적 도구 / 내용·구도·팔레트 → 델타 절 수정 후 베이스라인에서 재런 / 아이덴티티 드리프트 → 열거 강화·레퍼런스 재역할 / 전부 실패 → 모델 역할표의 다음 모델.
- 라운드당 변수 하나. 라운드 상한은 기본 3(대표 결정 가능). 같은 줄이 다른 수리로 2회 실패하면 모델 문제로 보고.
- 전신 컷은 전체를 다시 만들지 않는다(BRAND-ENGINE §4 6단계).
- 판정과 수리 기록은 메모리에 들어간다("고친 부분", "쓰지 않기로 한 표현").

## 8. TWINGS 제안 (우선순위)

1. **(P0, 문서) `docs/BRAND-ENGINE.md` §4에 "승인 지점"과 "검수 루프" 두 문단 추가.** 2단계 지시서 승인, 7단계 영상 전 견적 승인, 5단계 뒤 R1~R10 판정 기록 + 라운드 상한. 출처: video-ads, refine-loop.
2. **(P0, 스키마) 브랜드 아이덴티티 테이블에 칼럼 추가.** never 규칙 3개, 로고 클리어 스페이스·최소 크기, 레퍼런스 역할 필드(role·lend·not), 제품 체크리스트(라벨 텍스트·캡·실루엣·비율 수치·재질·색). 마이그레이션은 Director·대표가 적용.
3. **(P0, 검수) §5 초안을 `docs/BRAND-ENGINE.md` 또는 새 `docs/BRAND-REVIEW-RULES.md`로.** 자동 검사는 결정적(R1a·R2·R3·R4) + VLM(R1b·R5·R6·R7)로 나눠 구현. 공개 승인은 사람.
4. **(P1, 메모리) 승인 컷 입장 규칙과 캡션 분리.** 통과한 컷만 메모리에, "변하는 것" 캡션과 "고정" 태그를 분리 저장. 훗날 학습 데이터셋 후보가 자동으로 생긴다.
5. **(P1, 프롬프트) 지시서 생성기에 레퍼런스 역할표와 "금지 대신 정의" 문법.** `seedance-film-director`에 "첫 프레임 vs 레퍼런스" 결정을 샷마다 먼저, 사운드는 디제틱만 양성 명명.
6. **(P2, 마감) 브랜드 룩 저장 단위 = LUT + 측정 통계 + 스틸 테스트 그리드.** 내보내기 체크리스트에 pre-flight(안전 영역·길이·라우드니스·플래시·무음 패스).
7. **(P2, 스킬 운영) `.agents/skills` 규칙 한 절을 TWINGS AGENTS.md에.** description "Use when", 본문 2,500단어 상한, 1단계 링크, lock 해시, 머지 전 plan-only 테스트. 검증 테스트는 별도 PR.
8. **(보류) 브랜드별 LoRA.** §4.2 조건이 성립하는 브랜드가 나타나고, TWINGS 엔진 경로에서 학습이 가능한지 확인된 뒤에만. 그 전까지 포지션은 "고정 층".

## 9. 대표 결정 필요 (임의로 정하지 않는다)

1. 팔레트 ΔE 임계값과 측정 영역(바탕·잉크·강조·제품), 피부 제외 범위.
2. 검수 라운드 상한(제안 3)과 라운드당 지출 상한 — 요금제·크레딧(§7-5)과 연동.
3. 브랜드별 LoRA/스타일 학습을 로드맵에 올릴지. 올린다면 어느 엔진 경로에서 가능한지 조사가 먼저.
4. 브랜드 메모리 무드보드에 레퍼런스 3필드(role·why·take)와 안티 레퍼런스를 둘지.
5. 거부(모더레이션) 처리: 현행 "다른 업체 재시도 금지" 유지 + 게이트 분류만 도입할지.
