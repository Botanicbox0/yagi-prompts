## 0. 한 줄

**관리자는 운영자가 아침에 열어 "지금 누가 나를 기다리나"를 보고, 그 건을 한 번에 처리하는 도구다.** 홈은 대기열이고, 모든 숫자는 그 숫자를 만든 목록으로 간다.

## 1. 쓰는 사람과 하루

- 쓰는 사람: 대표와 스튜디오 직원 2–3명(회사 도메인 자동 관리자, `docs/reviews/STAFF-ADMIN-RELEASE-20260924.md`).
- 하루: ① 홈에서 결제·렌더 문제부터 본다 ② 브랜드·크리에이터가 기다리는 답장과 검수를 처리한다 ③ 템플릿을 올리거나 고친다 ④ 가끔 설정을 바꾼다.
- 그래서 화면 순서도 ① 돈과 결과물 ② 사람이 기다리는 일 ③ 만들기 ④ 설정이다.

대기열 하나는 `lib/admin/queues.ts`의 항목 하나다: 키, 그룹, 개수를 세는 함수, 그 개수의 목록 주소. 홈은 이 레지스트리만 읽는다.

- 0건이 아닌 대기열만 위의 "처리할 일"에 순서대로 나온다. 첫 줄의 버튼만 블루로 채운다.

- PLATFORM-2.0 §10의 "브랜드 캠페인 승인 N"은 승인할 대상(브랜드 캠페인 마법사)이 생기면 이 표에 한 줄로 더한다. "정산 대기 N"의 크리에이티브 쪽은 §7.4가 정해지면 더한다.

## 3. 공통 패턴 — 네 개만

화면은 아래 네 개로 조립한다. 새 화면에서 다섯 번째 패턴이 필요하면 이 절부터 고친다.

| 패턴 | 컴포넌트 | 쓰는 곳 |
| --- | --- | --- |
| 목록 | `AdminList`: 머리(제목·개수 칩·주요 행동) → 필터 pill 한 줄 + 검색(GET) → 표 → 이전/다음 | 렌더 보드, 결제 확인, 사용자, 이후 캠페인·템플릿 |
| 상세 | `AdminDetail`: 머리(제목·상태 pill) → 행동 바(그 상태에서 할 수 있는 일만) → 사실 표 → 타임라인 | 렌더 상세, 이후 캠페인·2차 활용 |
| 대기열 카드 | `QueueCard`: 그룹 제목·합계 → 대기열 줄(이름·개수·열기) | 홈, 이후 각 그룹 화면 머리 |
| 확인 | `ConfirmCheck`: 폼 안의 필수 체크박스. 되돌릴 수 없거나 밖으로 나가는 동작에만 | 지급, 공지 메일, 공개 등 기존 |

- 관리자는 자바스크립트 없이 동작한다(`components/admin/chrome.tsx` 머리말). 필터·정렬·페이지는 링크와 GET 폼이고, 확인 대화상자는 체크박스다.
- 목록의 숫자·금액·날짜·ID 열은 `tabular-nums`. ID는 앞 8자만 보이고 전체 값은 `title`에 둔다.
- 상태 pill은 다섯 가지 톤만 쓴다: **할 일**(블루 옅은 바탕 + 글자용 블루), **진행 중**(테두리만), **완료**(흐린 잉크), **실패**(잉크 채움 + 흰 글자), **보류**(옅은 회색). 빨강·초록·노랑을 쓰지 않는다.
- 되돌릴 수 없는 버튼은 잉크 테두리 버튼 + `ConfirmCheck`다. 빨간 버튼은 없다.

## 4. 시각 규칙 (Operate 모드)

- 원칙: `docs/design/IDENTITY.md`, `TASTE.md`, `TOOLBOX.md` §1-2(워크스페이스 관리 화면). 관리자는 밀도가 우선이라 미디어 프레이밍보다 표와 숫자를 다듬는다.
- **고른 기법 네 개**
  1. **Concentric Radius + 큰 라운드 바깥 프레임:** 캔버스(`#F6F7F9`) 위에 흰 작업 면 하나(반경 20px). 안의 카드는 14px, 버튼·칩은 pill. 사이드바는 캔버스 위에 그대로 둔다(Playbook 기준 구성).
  2. **Architectural Hairlines:** 표와 카드 구분은 1px 선(`#E4E6EA`). 무거운 박스와 그림자 대신 선으로 나눈다.
  3. **Double-Ring Specular Border:** 작업 면과 대기열 카드에만 바깥 6% 선 + 안쪽 위 흰 하이라이트.
  4. **Tabular Numerals:** 개수·금액·시간·ID 전부. 숫자가 바뀌어도 줄이 흔들리지 않는다.
  - 쓰지 않는 것: 유리(오버레이가 없다), 커서 스포트라이트, 그레인, 스프링 리빌. 움직임은 hover 색 전환뿐이고 `prefers-reduced-motion`이면 끈다.
- **색:** 잉크(`#0E1013`)·본문(`#41444D`)·보조(`#676B75`)·선과 블루 하나. 블루는 `--color-blue`(=`COLOUR.accent`)에서만 섞는다: 글자 85% + 검정, hover 82%, 옅은 바탕 9% + 흰색. 관리자 CSS에 블루 hex를 새로 쓰지 않는다.
- **빨강 금지:** 관리자에서 열리는 브랜드 작업공간 화면도 포함한다. `app/(brand)/workspace.css`의 관리자 블록이 `--ys-red: #dc2626`을 켜므로, 관리자 CSS가 `html[data-admin-console][lang]`에서 `--ys-red`·`--ys-danger`를 잉크로 덮는다(브랜드 파일은 건드리지 않는다).
- **글자:** 관리자만 영문 Helvetica Neue + 한글 Pretendard Variable(`app/(admin)/layout.tsx`가 파일을 로드한다). 제목 600, 자간 −0.02em. 대문자 라벨과 블랙 대형 제목은 쓰지 않는다.
- **모바일(390px):** 메뉴는 머리의 "메뉴" 버튼(`<details>`) 안으로 접힌다. 본문이 첫 화면에서 시작한다. 표는 줄마다 두 줄짜리 카드로 바뀐다. 터치 영역은 44px.

## 5. 셸

`AdminShell`(`components/admin/chrome.tsx`)이 모든 관리자 화면을 감싼다. 서버 컴포넌트이고 데이터를 읽지 않는다.

- 왼쪽 레일: 로고 → 그룹별 메뉴(아이콘 + 이름) → 아래에 사이트 보기 · 캐시 새로고침 · 로그아웃.
- 오른쪽 작업 면: 위치 줄(그룹 › 화면) + 언어 전환 → 본문.
- `active` 키가 메뉴에 없는 화면(옛 제품)은 어떤 메뉴도 선택 표시하지 않는다.
- `html[data-admin-console]`은 관리자 레이아웃만 붙인다. `app/(app)/layout.tsx`도 `data-workspace-admin`을 쓰므로, 새 관리자 스타일은 전부 `data-admin-console` 아래에 둔다.

## 6. 오퍼레이션

- 쓰기는 전부 `lib/admin/operations.ts` 레지스트리 + `POST /admin/do`. 예외는 업로드 운송 세 경로뿐이다(감사 §4).
- 도메인마다 파일 하나: `lib/admin/<domain>-operations.ts`가 `export const <DOMAIN>_OPERATIONS = { '<domain>.<verb>': op }`를 내보내고, `operations.ts`에는 **import 한 줄 + 스프레드 한 줄**만 더한다. 메인 세션의 `lib/admin/brand-engine-operations.ts`(조직별 기능 정책·플랜)도 이 방식으로 들어온다.
- 이름은 `도메인.동사`. 새 이름은 PLATFORM-2.0 §10을 따른다: `payout.export`, `campaign.audience`, `social.revoke`, `render.retry`, `render.resendNotice`.
- 정리할 것((e)): 플레이북 21개를 `playbook-operations.ts`로 옮겨 `operations.ts`를 펼치기만 하는 파일로 만든다. `platform.manage`의 동작 11개를 `creative.*`·`community.*` 이름으로 나눈다. 참조 없는 `brandWorkspace.settings`·`campaignCollaboration.revoke`를 지운다(지우기 전에 브랜드 쪽 사용 여부를 메인 세션에 확인).

## 7. 새 화면

### 7.1 렌더 보드 `/admin/renders` (b)
- 목록: 상태 필터(전체·실패·보류·대기·진행 중·완료) + 매체(영상·이미지) + 템플릿 검색, 최신순 50개씩.
- 열: 생성 시각 · 템플릿 · 엔진·해상도 · 상태 · 소요 시간 · 비용(USD, 원가 출처) · 결제 상태 · 알림 상태 · 실패 사유.
- 머리 숫자: 최근 7일 건수·실패·비용 합, 지금 보류·대기·진행 중.
- 상세 `/admin/renders/[id]`: 상태 pill, 사실 표(작업 ID, 템플릿, 엔진, 화면비, 해상도, 시도 횟수, 제공사 작업 ID, 비용, 결과 크기), 결제(상태·금액·실패 코드), 타임라인(생성 → 시작 → 마무리 → 끝 → 알림), 결과 문의 링크.
- 읽기 전용이다. 재시도·메일 재발송은 §8.
- 사용자 열은 계정 ID 앞 8자만. 이메일·사진은 보이지 않는다(사진 키·결과 키도 화면에 쓰지 않는다).

### 7.2 결제 확인 `/admin/payments` (b)
- 토스 단건 결제 중 운영자 손이 필요한 것: `refund_pending` + `refund_manual`/`partial_balance`, `paid` + `fulfil_manual`. 상한(환불·이행 각 10회) 뒤 여기로 온다(PLATFORM-2.0 §2.2-4).
- 열: 주문 시각 · 주문명 · 금액 · 상태 · 사유 · 시도 횟수 · 연결된 렌더.
- 처리 버튼은 없다. 결제 상태를 바꾸는 오퍼레이션은 결제 로직이라 이번 범위 밖이고, 처리는 토스 콘솔에서 한다. 화면은 무엇을 봐야 하는지만 알려 준다.

### 7.3 사용자 보기 `/admin/users` (c)
- 목적: 문의·검수 때 "이 계정이 누구인가"를 UUID 복사 없이 본다.
- 기본안(PII 최소): 계정 ID 앞 8자 · 가입일 · 역할(관리자·AI 크리에이티브·SNS 확인됨·브랜드 멤버) · SNS 연동(플랫폼·상태·인정 팔로워 수) · 셀카 수 · 결제 완료 수 · 렌더 수 · 최근 활동일.
- 찾기: 계정 ID 앞부분, 또는 **이메일을 정확히 입력했을 때만** 그 계정을 찾는다. 이메일은 목록에 표시하지 않는다.
- 범위는 대표 결정(§10-2).

### 7.4 정산 내보내기 `/admin/payouts` (`payout.export`)
- 크리에이티브별·월별 CSV. 기준은 PLATFORM-2.0 §19.3: 결과물 전달 후 7일이 지난 `paid` 판매, 이익의 80%, 회사 크리에이티브는 몫 0원.
- 열 제안: 월, 크리에이티브 ID 앞 8자, 핸들, 정산 방식(회사·외부), 판매 건수, 판매액, 부가세, 결제 수수료, 제작 원가, 이익, 크리에이티브 몫, 회사 몫, 원가 미확정 건수.
- 계좌·실명·주민번호는 넣지 않는다. 열과 세금 표기는 대표 결정(§10-3).

## 8. 렌더 재시도·메일 재발송 — 지금은 읽기 전용

- 실패한 렌더의 결제는 토스 정리 패스(`lib/billing/toss-service.ts`, 렌더 상태 `failed`를 보고 환불)가 따로 환불한다. 관리자가 실패 렌더를 `queued`로 되돌리면 이미 시작된 환불과 새 렌더가 겹칠 수 있다. 렌더 수명과 결제 상태 전이는 AGENTS.md §11의 형식 검증 대상이고, `lib/renders/*`는 이 작업의 범위 밖이다.
- 이전 브랜치 `codex/admin-brand-design`의 `render.retry`는 결제 상태를 보지 않고 시도 횟수를 0으로 되돌렸다. 가져오지 않았다.
- 제안(Director 검토 후 구현):
  - `render.retry`: 실패 + 제공사 일시 오류 코드(시간 초과·5xx·`stalled`)만. 얼굴 검증·제공사 검수 거절은 재시도하지 않는다. 결제가 있으면 `paid`이고 환불이 시작되지 않았을 때만, 그리고 결제 정리가 그 렌더를 환불 대상으로 잡지 않도록 같은 트랜잭션에서 막는다. 사유 필수, 감사 기록.
  - `render.resendNotice`: 끝난 작업만. 알림 멱등 키가 작업 ID로 고정돼 있어(`renderIdempotencyKey`) 같은 키로는 메일 제공사가 중복으로 버린다. 재발송 회차를 키에 넣는 변경이 `lib/renders/notify.ts`에 필요하다.
