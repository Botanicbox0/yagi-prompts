# KAIPER 셀프서비스 운영 전 검증

상태: 구현 브랜치의 검증 절차. 운영 개방 완료 문서가 아니다.

## 연결할 사용자 흐름

1. TWINGS 관리자는 브랜드 작업공간에서 KAIPER 프로젝트와 제작 계약을 준비한다. 캠페인에 제공할 비공개 포맷과 제작 한도를 지정한다. 운영 확인 시점 KAIPER에는 프로젝트·계약이 없었으므로 기존에 준비된 것처럼 표시하지 않는다.
2. `/admin/campaigns/[id]`에서 제작 계약과 같은 브랜드 프로젝트를 참여 공간에 연결한다. 이 연결은 이후 다른 프로젝트로 교체할 수 없다. 연결 전에 프로젝트 이름·브랜드를 확인한다.
3. 브랜드 담당자는 프로젝트의 참여자 화면에서 한 사람용 초대 링크를 만든다. 선택적으로 수신 이메일을 제한할 수 있다. 링크는 담당자가 직접 전달하며 자동 메일을 발송하지 않는다.
4. 초대받은 사람은 `/campaigns/[slug]/join#token=…`에서 토큰을 임시 보관하고 로그인한다. URL fragment는 OAuth query·서버 로그로 넘기지 않는다. 다른 브라우저로 이어가는 안내에서는 같은 참여 페이지의 fragment로 복원한다. 초대 수락은 캠페인 신청만 만들며 브랜드 권한이나 선정 상태를 부여하지 않는다.
5. 참여자가 본 보상·게시 조건의 버전을 확인해 신청한다. 표시 후 조건이 바뀌면 다시 확인해야 한다. 신청이 생긴 캠페인의 보상 조건은 덮어쓸 수 없다.
6. TWINGS가 선정하면 참여자 공간에서 대화·파일 공유와 기존 본인 얼굴 제작 화면으로 이동할 수 있다. 파일은 PDF/JPG/PNG/WebP, 최대 3MB이며 얼굴 등록은 별도 본인 인증 경로를 사용한다.
7. 기존 제작 완료 결과를 사용해 게시 링크를 제출하고 TWINGS가 검수한다. `게시 링크 제출`, `검수 통과`, `지급 기록`을 분리해 보여준다. 계정·얼굴 자산은 참여자 소유이며 미래 캠페인 추천이나 브랜드의 재사용 권한을 자동 생성하지 않는다.

## 플랫폼 결제의 범위

`/admin/funding`에서 관리자가 실제 합의된 총액·세금 설명·서비스/환불 조건·문서 버전·유효기간으로 견적을 발행한다. 브랜드 소유자가 `/brand/projects/[id]/funding`에서 견적을 수락하고 결제한다. TWINGS 관리자나 브랜드 편집자가 구매자를 대신할 수 없다.

견적 수락 후 금액은 불변이다. 결제액은 서버 견적에서 결정하고 확인 요청에 다른 금액이 오면 거절한다. 승인 중복 요청은 lease와 조건부 갱신으로 처리한다. 결과가 불명확하면 기존 결제를 조회하며 새 주문으로 결제를 반복하지 않는다. 환불은 관리자가 결제 기록·사유를 확인해 명시적으로 요청한다. 불명확한 취소 요청을 자동 재전송하지 않는다.

결제 기록은 TWINGS 서비스 대금 수납이며 참여자에게 돈을 보낸 증거가 아니다. 자동 선정·캠페인 공개·생성·창작자 지급을 실행하지 않는다. 기존 결제 제공사 계약이 이 판매 유형을 허용하는지, 환불 정책과 정산 역할은 운영 개방 전에 확인해야 한다. 수락 후 만료된 미결제 견적은 관리자가 사유를 기록해 종료하고 새 견적을 발행할 수 있다. 기존 수락자·시각·금액·조건은 보존하며 불명확하거나 입금된 주문이 있으면 이 복구를 거절한다. 부분 환불이나 자동 정책 판정은 제공하지 않는다.

같은 브랜드 화면에서 참여자 1인당 보상 금액과 조건을 별도로 제안할 수 있다. 현재 소유자/편집자가 입력한 제안은 TWINGS의 검토·피드백 대상이며, 실제 캠페인의 약정 보상이나 이미 신청한 사람의 동의 내용을 변경하지 않는다. 서비스 견적과 참여자 보상을 합쳐 표시하지 않는다.

신규 결제 개방을 중단해도 환경이 일치하는 기존 결제의 조회·환불은 수행할 수 있다. 비동기 입금 대기는 별도 상태로 유지하고 브랜드의 상태 확인 또는 관리자 대사 작업으로 실제 제공사 결과를 조회한다. 상시 스케줄러·입금 webhook 연결은 이번 버전에 없다.

## 운영자가 적용할 선행 조건

- 클라우드 스키마: 기존 제작 `0045/0130`, 이번 협업 `0047/0132`, 위험 검토 `0048/0133`, 결제 `0049/0134`가 필요하다. 저장소의 전체 마이그레이션 순서와 기존 적용 이력을 확인한 뒤 대표/Director가 적용한다. Executor가 운영 DB에 적용하지 않는다.
- 제작: 기존 `CAMPAIGN_PRODUCTION_PUBLIC`와 승인된 포맷·계약·본인 검증·제공사 준비. 실제 인물 생성은 별도 운영 검증이다.
- 참여 공간: `CAMPAIGN_COLLABORATION_PUBLIC`. 기본 off. 미적용 DB에 테이블이 있다고 가정하지 않는다.
- 결제: `CAMPAIGN_FUNDING_PUBLIC` 및 `CAMPAIGN_FUNDING_POLICY_READY`, 환경에 맞는 Toss 키. preview/local에서 live gateway를 사용하지 않고 production에서 test/fake를 사용하지 않는다. 정책 검토 없이 두 플래그만 켜지 않는다.
- 대리 얼굴: [검토용 동의·약관 변경안](../legal/drafts/KAIPER-DELEGATED-LIKENESS-AND-MESSAGING.md)을 확인한다. 현행 약관이나 본인 얼굴 검증을 변경하지 않았으며 대리 얼굴 실행 기능은 아직 개방하지 않는다.
- 위험 감지/Slack: [별도 워커 문서](campaign-risk-worker.md). 비공개 Slack 채널은 생성됐지만 bot credential·멤버십·운영 알림 연결과 상시 워커는 아직 설정하지 않았다. 분석 목적의 고지와 검토 권한을 먼저 확정한다.

## 검증을 구분해서 기록할 것

| 종류 | 실제 입증하는 것 |
| --- | --- |
| TypeScript | 현재 코드의 타입 검사 |
| Vitest/PGlite | 합성 데이터의 권한·동시성·상태 전이·중복 처리 |
| Fake Toss | 요청 순서·조건부 상태 갱신·실패 복구. 실제 PG 승인 증거 아님 |
| local build/start/sweep | 프로덕션 빌드와 실제 HTTP 익명 접근 경계 |
| 브라우저 | 실제 화면·키보드·모바일·OAuth 복귀. 도구 오류 시 미확인으로 남김 |
| 로컬 AI 합성 호출 | 실제 모델 응답 여부. timeout이면 분류 성공이라 하지 않음 |
| 운영 QA | 실계정, 승인된 금액·사진, 실제 제공사 결과. 이번 로컬 검증과 분리 |

검증 결과·정확한 리뷰 소스 해시는 `docs/evidence/kapier-campaign/`에 기록한다. PR의 프리뷰는 새 기능 플래그와 마이그레이션이 닫힌 상태일 수 있으므로 화면이 보이지 않는 것을 실행 완료로 바꾸어 보고하지 않는다.
