# 브랜드 캠페인 크리에이터 직접 제작

2026-10-14 대표 요청: 브랜드가 요청한 고정 포맷을 선정된 크리에이터가 자기 사진으로 생성하고, SNS 게시 링크를 제출한 뒤 검수·보상을 받는 흐름.

## 점검 결과

기존 캠페인에는 지원, 인원 제한, 선정, 게시 링크 제출, 검수, 지급 대기, 수동 이체 기록이 있다. 브랜드 공간에는 의뢰·파일·콘텐츠 승인·게시물·리포트와 제작 계약, 비공개 포맷, 제작 수량 장부가 있다. 두 영역 사이의 크리에이터 생성 권한과 결과 연결은 없었다. 운영 DB의 테이블 존재 여부도 읽기 전용으로 확인했다.

이번 구현은 `campaign_productions`로 기존 캠페인과 브랜드 제작 계약·포맷을 연결한다. `campaign_render_jobs`는 제작 결과의 지원자·계약·포맷 관계와 실패 재제작 승인을 기록한다. 제작 수량은 기존 `brand_production_reservations`에서 차감하며 별도 금액·재화 장부를 만들지 않는다. 소비자 구독·단건 결제와 독립된 권한이다.

## 운영 순서

1. 브랜드는 `brand.twings.app`에서 캠페인을 의뢰하고, 제작 방식으로 크리에이터 제작을 선택한다. 의상·제품 파일은 해당 프로젝트에 비공개 첨부한다.
2. TWINGS는 계약·예산·원고료·일정을 별도로 합의한다. 브랜드 프로젝트를 진행 상태로 전환하고, 제작 계약의 기간·생성 한도와 비공개 영상 포맷을 준비한다. 인물 입력 외 장면·의상·제품은 스튜디오가 정한다.
3. `/admin/campaigns/[id]`에서 모집 인원(예: 30명), 원고료, 모집·게시 마감, 플랫폼, 광고 표기·해시태그를 설정한다. 새 제작 연결 패널에서 브랜드 계약·포맷과 선택 제품 이미지(최대 3장)를 연결한다. 제품 이미지에는 인물 사진을 넣지 않는다.
4. 모집·선정은 기존 큐에서 진행한다. 인원 계산과 선정은 같은 캠페인 행을 잠가 동시에 마지막 인원을 선정하는 경우도 초과하지 않는다.
5. 선정된 크리에이터는 내 캠페인 → 캠페인 영상 만들기에서 본인 사진과 동의를 제출한다. 정면·단순 배경 사진 예시를 제공한다. 서버가 포맷·화면비·720p를 결정하며, 개인 구독 이용량은 차감하지 않는다.
6. 기존 본인 인물 자산·제공사 검수·렌더 큐·결과/다운로드를 그대로 사용한다. 제품 참고 이미지는 해당 프로젝트의 준비된 파일만 서버가 정제·복사해 제공사에 전달한다. 원본 프롬프트·계약 ID·입력 사진·스토리지 키는 브랜드/공개 화면에 전달하지 않는다.
7. 크리에이터는 완성본을 확인하고 본인 SNS에 직접 게시한다. 캠페인 생성이 필요한 경우 성공한 영상이 있어야 게시 링크를 제출할 수 있다. TWINGS가 실제 영상·플랫폼·광고 표기·해시태그를 확인해 검수한다. 검수한 게시물 링크는 같은 트랜잭션에서 기존 브랜드 게시물·리포트 영역에도 연결한다. 원래 SNS 게시 시각과 조회수는 추정하지 않는다.
8. 캠페인에 표시된 지급 대기 기간이 지난 뒤 관리자가 실제 이체 후 지급 참조를 기록한다. 자동 은행 이체나 SNS 자동 게시 기능은 없다. 조회수는 기존 관리자 확인/수집 화면을 사용한다.

연결하지 않은 캠페인은 기존 수동 제작·게시 방식으로 운영한다. 브랜드가 제작을 모두 맡기는 방식도 기존 브랜드 콘텐츠 승인 기능을 이용한다.

## 중복·실패·권한

- 지원자 본인·선정 상태·게시 마감·진행 캠페인·활성 프로젝트/계약을 확인한다. 브랜드 조직 멤버로 가입시켜 생성 권한을 주지 않는다.
- 첫 생성은 지원당 1회다. 동일 요청·동일 사진은 같은 결과 주소를 돌려주며, 바뀐 입력은 충돌로 거절한다. 완료/진행 영상이 있으면 새로운 요청 ID로도 추가 생성하지 않는다.
- 실제 최종 실패 시 기존 계약 장부가 수량을 복구한다. 크리에이터의 추가 시도는 실패 영상마다 관리자가 한 번 승인해야 한다. 실패가 발생했다고 자동 추가 생성하지 않는다.
- 생성 후 계약·포맷·제품 이미지 연결은 바꿀 수 없다. 제작 허용/중단은 버전 검사 후 변경한다.
- 브랜드의 영상 접근은 게시물 제출 후 해당 브랜드 프로젝트의 현재 권한을 다시 확인한다. 관리자·본인만 게시 전 결과를 볼 수 있다. 공유/다운로드·미디어는 비공개 캐시를 사용한다.
- 신규 테이블은 RLS enable/force, public·anon·authenticated 권한 회수, service_role만 접근한다. 원장과 지원자를 복합 외래키로 묶는다.
- 제공사 생성 직전에 발송 표식을 먼저 저장해 겹친 작업·자산 폴링이 중복 요청하지 않는다. 응답이 유실되면 작업을 진행 상태로 유지해 제작 한도와 인물 자산을 보호하고, 자동 재요청하지 않는다. 20분 이후 관리자가 제공사에서 원래 작업 ID를 확인해 연결하거나 미생성을 확인해 실패 처리한다. 실패 처리 후에도 추가 제작은 별도 승인해야 한다.

## 배포·운영 개방

클라우드 적용 필요: `0045_core_campaign_production.sql`, `0128_glue_campaign_production.sql`. AGENTS.md §3에 따라 대표/Director 적용 대상이다. 기존 데이터는 삭제하지 않는다. 새 테이블이 없는 배포에서는 수동 캠페인 화면을 유지하고 직접 제작 요청은 닫힌 상태로 응답한다.

서버 환경변수 `CAMPAIGN_PRODUCTION_PUBLIC=on`과 캠페인의 명시적 제작 허용, 활성 브랜드 프로젝트·계약이 모두 필요하다. 기본값은 닫힘이다. PG 소비자 결제 승인은 캠페인 제작 개방 조건으로 사용하지 않는다. 브랜드 제작비 계약과 실제 모델·자산·큐 운영 검증은 별도다.

운영 개방 전: 테스트 환경에서 본인 사진 → 자산 검수 → 생성 → 실패/허용 → SNS 실제 링크 → 검수 → 브랜드 결과 → 지급 대기/수동 지급 기록을 확인한다. 실제 모델 호출·지급·캠페인 공개·메일 발송은 각 실제 운영 행위로 구분한다. 이 구현 검증의 합성 사진·DB/스토리지·제공사 대역은 실제 제작이나 지급 증거가 아니다.

## 검증 기록

기능 검증: 실제 PGlite 스키마/SQL로 권한, 개인 구독과의 분리, 계약 수량 공유, 중복 요청, 추가 생성 제한, 실패 후 관리자 승인, 인원 선정 경쟁, 브랜드 프로젝트 접근 철회를 검사한다. 경계 검증: 같은 출처, 본문 크기, 중복·임의 필드, 보류 시 미실행, 미디어 비공개 접근. 전체 검증 결과와 정확한 커밋·프리뷰는 PR에 기록한다.
