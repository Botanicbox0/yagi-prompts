# 캠페인 결제의 미확정 결과 복구

운영 미반영 절차 초안. 테스트 제공사 대역 검증만 완료했으며 실제 Toss 동작·콘솔·지원 절차를 검증한 기록은 아니다. 대표 또는 Director가 운영 환경과 권한을 확인한 뒤 사용한다. 결제 공개 플래그를 끈 상태에서도 기존 결제의 조회·복구·환불은 같은 환경의 게이트웨이로 처리할 수 있다.

## 먼저 확인할 근거

- 프로젝트·캠페인·서버 주문 ID, 견적 버전, 최종 원화 총액, 운영/테스트 환경을 대조한다.
- 제공사 콘솔에서 **동일 주문 ID**의 상태, 총액, 잔액과 취소 이력을 확인한다. 다른 주문의 결제 내역을 이 주문의 입금이나 환불 근거로 쓰지 않는다.
- 로그·채팅·증거 문서에 비밀 키나 원문 paymentKey를 남기지 않는다. 주문 ID와 허용된 상태 메타데이터를 사용한다.
- DB의 lease 만료나 네트워크 오류는 미결제·미환불의 증거가 아니다. 재시도 버튼을 누르기 전에 현재 제공사 결과를 조회한다.

## 상태별 처리

`confirming` 또는 `awaiting_deposit`: 관리자 「결제 제공사 상태 확인하기」나 브랜드 「현재 상태 확인하기」는 조회만 실행한다. 일치하는 `DONE` 전액이면 입금 기록으로 바뀐다. 가상계좌 입금 대기는 완료로 표시하지 않는다. provider 조회 404만으로 주문을 해제하지 않는다.

다른 주문의 키: 신규 요청은 소유자 인가 후, 키를 DB에 묶기 전에 제공사 조회 결과의 주문 ID를 비교하여 거부한다. 기존에 잘못 묶인 행은 제공사 응답이 **그 키가 다른 주문 소속임을 증명**한 경우에만 조회 대사나 관리자 미결제 해제로 실패 처리한다. 외부 주문에는 승인·취소 요청을 보내지 않는다.

확정 거절: 제공사가 승인 요청을 명시적으로 거절했고 해당 키가 없다는 조회 결과까지 있거나, 정확히 일치하는 주문이 종료된 미결제 상태임이 확인된 경우에만 실패/해제가 가능하다. 새 주문은 별도 ID를 사용한다.

만료 견적: 관리자 「만료된 미결제 견적 무효 처리」는 미확정·입금·환불 주문이 있으면 거부한다. 허용되는 경우에도 기존 수락자·수락시각·금액·조건을 보존한다. 새 견적은 별도 버전으로 발행하고 구매자가 다시 수락한다.

`refund_pending`인데 제공사는 `DONE`: 취소 요청이 도달하지 않았을 수도 있고, 응답 또는 반영이 지연되었을 수도 있다. 저장된 `refund_started_at`은 호출 경계 진입 기록이며 취소 성공 증거가 아니다. 앱은 같은 취소를 자동 재전송하지 않는다. 마커를 지우거나 DB 상태를 임의로 환불 완료로 바꾸지 않는다. 제공사 취소 이력·멱등성 처리 결과를 확인하고, 필요하면 제공사 지원을 통해 결과를 확정한다. 대표가 기존 합의 조건에 따라 별도의 제공사 콘솔 조치를 승인한 경우에도 타 주문이나 부분 금액을 이 주문의 전액 환불로 간주하지 않는다. 제공사가 동일 주문의 전액 `CANCELED`·잔액 0을 확인하면 앱 대사를 다시 실행해 환불 기록을 남긴다.

`review`의 동일 주문 금액·통화·잔액 불일치: 자동 해제나 환불 재요청을 하지 않는다. 제공사 원장과 서버의 불변 견적/주문을 대조하고 대표 또는 Director에게 확인을 요청한다. 소스가 허용하지 않는 임의 DB 수정으로 새 결제를 열지 않는다. 제공사 정정으로 정확한 원금·잔액이 확인되면 정식 관리자 작업을 사용한다. 현재 관리자 경로로 해결할 수 없으면, 확인된 근거를 포함한 별도 수정안을 검토·검증한 뒤 적용한다.

모든 복구는 입금 기록에만 영향을 준다. 캠페인 공개, 제작, 크리에이터 동의나 지급 기록을 자동 변경하지 않는다.

## 아직 필요한 운영 검증

실제 테스트 키로 거절/404, 가상계좌, 취소 결과 지연과 멱등성 결과를 확인해야 한다. 실제 PostgreSQL 다중 연결 경합 및 브라우저 위젯/복귀 화면 검증도 별도다. 이 절차서는 해당 검증이나 운영 개방 승인을 대신하지 않는다.
