## 0. 추천안

1. **돈의 단위는 청구서 하나로 통일한다.** 이미 운영 중인 `brand_invoices`(정가 − 할인 + 부가세)를 그대로 쓰고, 고객사마다 **받는 방법**만 고른다. 기본은 계좌이체("청구서에 적힌 계좌로 기한 안에 입금"), 선택지는 카드 자동결제("청구서가 발행되는 날 등록 카드로 결제")다. 할인·일할·부가세 계산은 한 곳(`invoiceAmounts`)에서만 일어난다.
2. **계좌이체는 세 단계로 자동화한다.** ① 관리자가 입금을 확인(오늘 가능) → ② 청구서마다 가상계좌를 발급하고 입금 웹훅으로 자동 확인 → ③ 고객사마다 같은 계좌번호(고정식 가상계좌). ②와 ③은 토스 계약이 필요하고, 계약이 안 되거나 장애가 나면 ①로 떨어진다. 법인계좌에서 매달 자동으로 빼 가는 방식은 토스에 없다(§2.2).
3. **증빙은 수단에 따라 하나만.** 카드는 카드 매출전표, 계좌이체는 세금계산서(홈택스 수기 발행). 한 거래에 둘을 같이 내지 않는다(§2.4).
4. **크레딧은 차감표를 건드리지 않고 플랜의 크레딧 수로 마진을 잡는다.** 마진 기준은 10~12%이고 월 27,000 / 46,000 / 65,000 크레딧으로 확정됐다(§6, 대표 결정 2026-11-23). 다 쓰고, 가장 비싼 모델만 쓰고, 카드로 내도 11~12%가 남는다. 고객사 할인은 이 계산에 넣지 않고 영업 비용으로 따로 본다.

이용 차단은 새 상태를 만들지 않고 지금 있는 규칙(`planActiveWithGrace` → `loadAllowance`)을 그대로 쓴다. 구독 엔진은 플랜의 `ends_on`만 움직인다(§5.3).

## 2. 조사 결과 (2026-11-23, 공식 문서)

### 2.1 카드 자동결제

- 자동결제는 "리스크 검토 및 추가 계약 후" 쓸 수 있고, 정기 구독형이 아니면 제한된다. 결제 주기 실행은 상점이 직접 한다. [자동결제 이해하기](https://docs.tosspayments.com/guides/v2/billing), [연동](https://docs.tosspayments.com/guides/v2/billing/integration)
- 수단은 국내 발급 신용·체크카드와 퀵계좌이체(개인 계좌). 카카오페이는 안 된다.
- 법인카드: 빌링키 발급 API가 사업자등록번호 10자리를 받고 응답에 `ownerType: 법인`이 있다. 등록창(`requestBillingAuth`)에서 법인카드, 특히 무기명 카드를 등록할 수 있는지는 **토스 확인 필요**. [API 연동](https://docs.tosspayments.com/guides/v2/billing/integration-api)
- 승인은 최대 60초가 걸린다(타임아웃 60초 이상). 모든 POST에 `Idempotency-Key`를 쓸 수 있고 15일간 유효하다. 처리 중 재요청은 409 `IDEMPOTENT_REQUEST_PROCESSING`. 주문 조회는 `GET /v1/payments/orders/{orderId}`. [멱등키](https://docs.tosspayments.com/reference/using-api/idempotency-key), [API](https://docs.tosspayments.com/reference)
- **토스 이용계약 제42조가 상점에 요구하는 것.** [전자결제서비스 이용계약](https://pages.tosspayments.com/terms/onboarding/)
  - 가입 약관과 **따로** 자동결제 약관을 알리고 사전 동의를 받는다.
  - 금액이 바뀌거나 유료로 전환될 때는 **결제 7일 전까지** 금액·결제일·환불 조건·해지 방법을 알린다.
  - **영업시간 밖에도** 해지를 신청할 수 있어야 한다.
  - 환불은 이용 일수·회차에 비례해야 하고, 자체 포인트로만 돌려주는 것은 안 된다.
- 자동결제 심사가 화면에서 보는 항목의 공식 체크리스트는 찾지 못했다(**토스 확인 필요**).

### 2.2 계좌 기반 수단

| 수단 | 정기 과금에 쓸 수 있나 | 근거 |
| --- | --- | --- |
| **가상계좌**(청구서마다 발급) | 된다. 고객이 매달 입금하고 웹훅으로 자동 확인 | 발급 `POST /v1/virtual-accounts`, 유효기간 최대 90일, 입금 시 `DEPOSIT_CALLBACK`. [웹훅](https://docs.tosspayments.com/reference/using-api/webhook-events), [용어](https://docs.tosspayments.com/resources/glossary/virtual-account) |
| **고정식 가상계좌**(고객사마다 같은 번호) | 된다. `accountKey`가 같으면 같은 계좌번호. 그래도 청구마다 발급 요청은 필요 | "리스크 검토 및 추가 계약 필요". 수수료·지원 은행은 **토스 확인 필요** |
| 계좌이체(퀵계좌이체·뱅크페이) | **법인계좌는 안 된다.** 자동결제는 개인 계좌만, 법인계좌(뱅크페이)는 매번 결제창 인증 | "뱅크페이(법인계좌)는 자동결제를 지원하지 않아요." [계좌이체](https://docs.tosspayments.com/resources/glossary/transfer-payment) |
| 출금 동의 자동이체(CMS) | 토스 상품으로 확인되지 않는다 | 제공 여부 **토스 확인 필요** |

가상계좌에서 알아 둘 것:

- 입금액은 주문 금액과 정확히 같아야 하고 나눠 낼 수 없다. 다른 금액이 은행 단계에서 거절되는지는 **토스 확인 필요**. [가상계좌 안내](https://www.tosspayments.com/blog/articles/30637)
- 입금 기한이 지나도 웹훅이 오지 않는다. 만료는 우리 쪽 작업이 처리한다. [가상계좌 웹훅](https://docs.tosspayments.com/blog/virtual-account-webhook)
- 입금 완료가 은행 사정으로 **되돌아갈 수 있다**(`DONE → WAITING_FOR_DEPOSIT`). "2분 지연 통보" 옵션이 있다(신청 방법 **토스 확인 필요**).
- 웹훅은 10초 안에 200을 받아야 하고, 실패하면 최대 7회 다시 온다. 본문의 `secret`을 발급 때 받은 값과 비교한다. [웹훅 가이드](https://docs.tosspayments.com/guides/v2/webhook)
- 입금 뒤 환불은 환불 계좌(`refundReceiveAccount`)가 필요하다. [결제 취소](https://docs.tosspayments.com/guides/v2/cancel-payment)

### 2.4 증빙

- 카드로 결제하면 카드 매출전표가 증빙이고, 세금계산서를 또 내면 이중 발급이다(부가가치세법 제33조 ②, [국세청 상담 사례](https://call.nts.go.kr/call/qna/selectQnaInfo.do?mi=1329&ctgId=CTG11945)).
- 토스는 상점의 고객에게 세금계산서를 발행해 주지 않는다. **우리가 홈택스에서 수기로 낸다**(대표 결정). 발행 대행(팝빌·바로빌)은 건수가 늘면 붙인다.
- 가상계좌·계좌이체는 토스가 현금영수증을 자동 발급한다. 세금계산서를 내는 건은 발급 요청에서 현금영수증을 `미발행`으로 지정한다(요청 단위 지정이 문서에 있다, **토스 재확인**). [현금영수증](https://docs.tosspayments.com/resources/glossary/cash-receipt)
- 대가를 먼저 받고 그 금액으로 세금계산서를 내면 발급한 때가 공급시기다(부가가치세법 제17조 ①). 6개월 선결제분을 받은 날 한 장으로 낼 수 있는 근거다. 선납 계속 용역의 신고 시기(시행령 제29조 ② 3호의 "유사한 용역" 해당 여부)는 **세무 대리인 확인**.

### 2.5 참고한 구조

**Stripe Billing.** [수금 방식](https://docs.stripe.com/billing/collection-method), [은행 송금](https://docs.stripe.com/invoicing/bank-transfer), [재시도](https://docs.stripe.com/billing/revenue-recovery/smart-retries), [실패 메일](https://docs.stripe.com/billing/revenue-recovery/customer-emails), [거절 코드](https://docs.stripe.com/declines/codes)

- 구독은 청구서를 만들고, 고객마다 자동 청구 또는 청구서 + 납기를 고른다. → §0-1
- 고객마다 변하지 않는 입금 계좌 번호와 자동 대사. → 고정식 가상계좌
- 재시도 기본값은 2주 안에 최대 8회, 직접 정하면 최대 3회. 분실·도난·승인 철회 같은 거절은 새 결제 수단이 등록될 때까지 실제로 재시도하지 않는다. 실패할 때마다 결제 수단 변경 링크가 든 메일을 보낸다. → §5.5
- 다른 사례: Recurly는 월 구독의 독촉 기간을 27일 이내로 권하고, 카드사·게이트웨이 오류는 2~3일 간격으로 다시 시도한다. Chargebee는 직접 정하는 재시도를 최대 5회로 둔다. [Recurly](https://docs.recurly.com/docs/dunning-management), [Chargebee](https://www.chargebee.com/docs/payments/2.0/dunning/dunning-v2)

**Higgsfield 크레딧 구조**(공개 도움말만 읽었다. 요금 페이지는 스크립트로 그려져 플랜 가격·플랜별 크레딧 수·모델별 차감표는 **미확인**이다). [크레딧](https://higgsfield.ai/creator-hub/help-center/credits/how-credits-work), [만료](https://higgsfield.ai/creator-hub/help-center/credits/top-up-credits-expire), [크레딧 팩](https://higgsfield.ai/creator-hub/help-center/credits/how-credit-packs-work), [플랜 변경](https://higgsfield.ai/creator-hub/help-center/plans/how-do-i-upgrade-or-downgrade-my-plan), [팀·비즈니스](https://higgsfield.ai/creator-hub/help-center/business/team-and-business-higgsfield)

- 구독 크레딧은 결제 주기마다 새로 채워지고 **이월되지 않는다**. 연간 플랜도 30일마다 새로 채운다.
- 추가 크레딧 팩은 구독 중인 계정만 살 수 있고 구매 후 90일 유효, 자동 갱신 없음.
- 구독 크레딧을 먼저 쓰고, 그다음 만료가 가까운 것부터 쓴다.
- 차감량은 모델·해상도·길이로 정해지고 생성 버튼에 미리 표시된다. 실패한 생성은 돌려준다.
- 올리면 즉시 적용, 내리면 다음 주기부터. 해지하면 구독 크레딧은 기간 끝에 사라진다.
- 비즈니스 플랜은 좌석별 크레딧이 워크스페이스 공용으로 합쳐진다.

우리 구조는 이미 이 모양이다(월 한도, 모델별 차감, 버튼에 미리 표시, 실패 시 미차감, 이월 없음). 빠진 것은 플랜별 크레딧 수, 추가 팩, 차감 순서다(§6).

## 3. 구조

```
brand_subscriptions (조직당 1행: 플랜, 받는 방법, 상태, 해지 예약)
        │  매달: D-7 초안 + 예정 안내 → 1일 발행
        ▼
brand_invoices (지금 있는 장부. 금액은 invoiceAmounts)
        │  청구서 하나에 결제 시도 여러 번
        ▼
brand_invoice_payments (시도 1건 = 토스 주문 1건: 카드 승인 / 가상계좌 / 수동 입금)
        │  done 1건 → 청구서 paid → 플랜 ends_on = 그 달 말일
        ▼
brand_plan_assignments.ends_on  →  planActiveWithGrace  →  loadAllowance (지금 그대로)
```

- *(B1c로 바뀜 → §5.8)* **주기는 달력 월**이다. 지금 장부가 `period = YYYY-MM`, 조직·월당 1장이고 첫 달 일할(`proposeProration`)이 있다. 매달 1일(KST) 그 달 이용료를 선불로 청구한다.
- **승인제.** 워크스페이스는 관리자가 승인해야 열린다(대표 결정). 승인할 때 체험 크레딧을 한 번 준다(§6.5). 구독 신청은 승인된 조직만 할 수 있다.
- **플랜 변경**: 올릴 때는 바로 적용하고 남은 일수의 차액을 추가 청구서로 낸다. 크레딧도 같은 비율로만 더 준다(§6.4). 내릴 때는 다음 달부터 적용하고 환불하지 않는다.
- 구독 행이 없는 조직(관리자가 손으로 플랜을 넣은 고객, 프로젝트 전용, 샌드박스)은 지금과 똑같이 동작한다.

## 4. 화면

### 4.1 고객 — `/brand/billing` (소유자·관리자만)

1. **플랜 선택.** 카드 3장: 월 290,000 / 490,000 / 690,000원 "(부가세 별도)", 월 크레딧, 그 아래 실제 결제 금액과 결제일("매월 1일, 첫 달은 남은 일수만큼"). 할인이 있으면 할인 후 금액과 남은 회차를 같이 보여 준다. 할인 코드는 여기서 먼저 넣는다.
2. **받는 방법 선택.** 계좌이체가 먼저 선택되어 있다: "계좌이체 — 매달 청구서의 계좌로 입금, 세금계산서". 다른 칸: "카드 자동결제 — 매달 1일 등록 카드로 결제, 카드 매출전표". 계좌이체는 세금계산서 정보(이미 있는 폼)가 필수다.
3. **동의.** B2B 이용약관과 **별도 칸**의 자동결제 동의(카드만). 금액·결제일·해지 방법·환불 기준을 동의 칸 바로 위에 적는다.
4. **카드 등록 또는 입금 안내.**
   - 계좌이체: 첫 청구서와 입금 계좌·금액·기한(발행일 + 14일)을 보여 주고 메일로도 보낸다. 입금이 확인되면 플랜 크레딧이 열린다. 계약서로 먼저 시작한 고객은 관리자가 먼저 열어 줄 수 있다.
   - 카드: 토스 등록창 → 돌아오면 첫 청구서를 바로 결제 → 활성.
5. **이후 같은 화면에서**: 다음 결제 예정(날짜·금액), 청구 내역과 증빙(세금계산서 발행 여부 / 매출전표 링크), 미납 청구서의 "입금 계좌 보기"·"지금 카드로 결제", 결제 수단 변경, 카드 교체, 플랜 변경, 추가 크레딧, **해지**(확인 한 번, "○월 ○일까지 이용" 표시, 해지 취소 가능).

메일(문안은 대표 확정 뒤): 결제 예정 안내(D-7), 청구서 발행, 결제 완료, 카드 결제 실패(§5.5), 입금 기한 3일 전·당일·경과, 생성 중단 예정·중단, 해지 접수.

화면 문구에는 내부 용어(MID, 빌링키, 웹훅, 가상계좌 발급 상태 이름)를 쓰지 않는다. 고객에게는 "입금 전용 계좌"라고 부른다. 이 화면은 PC 기준으로만 만든다.

### 4.2 공개 요금 페이지 (대표 결정: 로그인 뒤 화면과 공개 페이지 둘 다)

- **위치**: `twings.app/{locale}/brands/pricing` — `app/(marketing)/[locale]/brands/pricing/page.tsx`. brand.twings.app은 로그인 전용이고 검색이 차단되어 있어서, 공개 페이지는 브랜드 랜딩과 같은 마케팅 쪽에 둔다(정적 + 캐시 태그 + 1시간, AGENTS.md §4). 브랜드 랜딩과 `/brand/billing`에서 서로 연결한다.
- **담을 것**: 플랜 3개(월 이용료 "부가세 별도"와 부가세 포함 결제 금액, 월 크레딧, 그 크레딧으로 만들 수 있는 양의 예, 저장 용량), 결제 주기(매월 1일, 첫 달 일할), 결제 수단(계좌이체·세금계산서 / 카드 자동결제), 6개월 선결제(확정되면), 추가 크레딧, 시작 방법(신청 → 승인 → 체험 크레딧), **해지 방법과 환불 기준 요약**, 약관 링크, 자주 묻는 질문, 문의.

- **SEO·GEO**(AGENTS.md §7): `Product` + 플랜별 `Offer`(원화, `UnitPriceSpecification`에 월 단위와 `valueAddedTaxIncluded: false`), `FAQPage`, ko/en `alternates`, 사이트맵, 첫 화면 아래 정의형 문단 하나와 답변형 제목("얼마인가요", "어떻게 해지하나요", "세금계산서는 어떻게 받나요"). 본문은 HTML에 실제로 있어야 한다. 스윕 마커 `data-brand-pricing`, `data-brand-plan`.

- **하지 않는 것**: 샌드박스 고객의 영상·이름, 개인 쪽 실적 숫자를 B2B 예시로 쓰지 않는다. 아직 없는 기능은 "얼리 액세스"로 표시한다. `docs/BRAND-ENGINE.md` §7-5의 "정하기 전 가격 노출 금지"는 이 결정으로 풀리므로 구현 PR에서 그 문서를 같이 고친다.

## 5. 상태와 실패 처리

### 5.1 상태

구독(`brand_subscriptions.status`):

```
pending ──첫 청구서 결제──▶ active ──미납(기한 경과)──▶ past_due ──유예 경과──▶ suspended
                              ▲                            │                      │
                              └──────────── 결제 확인 ─────┴──────────────────────┘
active / past_due / suspended ──해지 예약(cancel_at_period_end)·기간 종료──▶ ended
```

청구서는 지금 전이에 둘을 더한다: `paid → issued`(입금 되돌림 전용, 사유 기록)와 `paid → refunded`(전액 환불). 부분 환불은 청구서를 `paid`로 두고 환불 금액을 따로 기록한다.

결제 시도(`brand_invoice_payments.status`): `pending → charging → done | failed`(카드), `pending → waiting_deposit → done | expired | canceled`(가상계좌), `done → refunded`, 그리고 사람이 봐야 하는 `review`.

### 5.2 매달 일정

> **B1c-2부터 자동 청구 엔진은 플랜 시작일 기준 주기로 동작한다(§5.9).** 이 절의 1일 발행·달력 월 일정은 그 절이 대신한다. 입금 기한 14일, 유예 14일, D-7 초안·안내는 주기 기준으로 그대로다.

입금 기한 14일과 유예 14일은 대표 결정이다. D0은 발행일(매월 1일)이다.

| 날 | 계좌이체(기본) | 카드 자동결제 |
| --- | --- | --- |
| D-7 (전달 24~25일) | 다음 달 청구서 초안 + 청구 예정 안내(금액, 지난달과 다르면 이유) | 같은 초안 + **결제 예정 안내** |
| D0 (1일) | 발행 → 입금 계좌 안내. 납기 = D+14(15일) | 발행 → 등록 카드 결제 → `paid`. 납기 = D0 |
| 납기 전후 | D+11·D+14·D+15에 안내 메일 | 실패하면 §5.5의 재시도 |
| 유예 | D+15 ~ D+28 (`past_due`) | D+1 ~ D+14 (`past_due`) |
| 새 생성 중단 | D+29부터 (`suspended`). 보기·내려받기·룸은 그대로 | D+15부터. 같다 |
| 결제 확인 | 즉시 `active`, 그 달 말일까지 | 같다 |

- D-7 안내는 토스 계약 제42조(금액 변경 7일 전 고지)를 매달 지키는 가장 단순한 방법이다. 할인이 끝나는 달, 플랜이 바뀌는 달에도 따로 챙길 것이 없다.
- `suspended`인 동안에는 다음 달 청구서를 만들지 않는다. 밀린 청구서를 내면 그날부터 남은 일수만 일할로 이어 간다. *(B1c-2에서 바뀜 → §5.9)* — 재개는 입금일에 새 주기, 전액(§5.9 8번). 60일 넘게 `suspended`면 확인 필요 큐에 올린다(해지 여부는 사람이 정한다).
- `BRAND_PLAN_GRACE_DAYS`의 값을 14로 바꾸는 것은 구현 때 한다. 이 값은 손으로 관리하는 조직의 유예에도 똑같이 적용된다.

### 5.3 차단은 `ends_on` 하나로

`planActiveWithGrace(plan, 오늘, 유예일수)`가 이미 "`ends_on` + 유예일까지 유효"를 판정하고, `loadAllowance`가 그 결과로 한도를 정한다. 구독 엔진은 구독이 있는 조직의 `ends_on`만 쓴다.

- 청구서가 `paid`가 되면 `ends_on = 다음 달 1일`(결제된 달의 다음 날. 구현 규칙은 §5.7). *(B1c-2에서 바뀜 → §5.9)* — 결제된 주기의 끝.
- 미납 청구서가 있으면 `ends_on = 가장 오래된 미납 청구서의 납기일`. 그래서 "납기 + 유예"까지 이용이 이어진다. 카드의 납기일은 발행일이다.
- 그 뒤에도 미납이면 지금 규칙대로 한도가 기본값으로 떨어져 새 생성이 닫힌다.

검사 지점이 늘지 않고, 수동으로 관리하는 조직의 동작도 바뀌지 않는다. `docs/BRAND-PRODUCT.md` §6.4의 "연체는 스튜디오를 막지 않는다"는 수동 청구 기준이고, 구독 조직은 위 규칙을 따른다(대표 결정).

### 5.4 경우별 처리

| 경우 | 처리 |
| --- | --- |
| 카드 승인 실패 | 청구서는 `issued`로 남는다(취소하지 않으므로 할인 회차가 두 번 줄지 않는다). 시도 행만 `failed`. 재시도마다 새 시도 행 = 새 주문번호. 일정은 §5.5 |
| 입금 기한 경과 | 가상계좌 유효기간을 "납기 + 유예"(발급일 + 28일)로 잡아 유예 중에도 입금된다. 만료는 우리 작업이 처리하고, 고객이 "입금 계좌 보기"를 누르면 새로 발급한다 |
| 부분 입금·초과 입금 | 가상계좌는 금액이 맞아야 입금된다(은행 단계 거절 여부 토스 확인 필요). 수동 입금에서 금액이 다르면 `paid`로 바꾸지 않고 확인 필요 큐로 보낸다. 잔액으로 쌓지 않는다 |
| 중복 결제·중복 입금 | 청구서당 `done` 시도는 1건만(부분 유니크 인덱스). 받는 방법을 바꾸거나 "지금 카드로 결제"를 누르면 열려 있는 가상계좌를 먼저 취소한 뒤 승인한다. 그래도 이미 `paid`인 청구서에 돈이 들어오면 자동으로 다음 달에 충당하지 않고 확인 필요 큐 → 환불 |
| 입금 되돌림(`DONE → WAITING_FOR_DEPOSIT`) | 청구서 `paid → issued`, `ends_on`을 납기일로 되돌리고 고객·관리자에게 알린다. 지연 통보 옵션을 쓸 수 있으면 켠다 |
| 웹훅 지연·중복·순서 뒤바뀜 | 웹훅 본문은 힌트로만 쓰고 토스에서 결제를 다시 조회해 상태를 정한다(지금 단건 웹훅과 같은 방식). `secret` 비교, 모든 전이는 조건부 UPDATE라 같은 웹훅이 여러 번 와도 결과가 같다. 웹훅이 끝내 안 오면 주기 작업이 `waiting_deposit` 건을 조회한다 |
| 결제 수단 변경 | 다음 청구서부터 적용. 열려 있는 청구서는 위 "중복" 규칙으로 한 경로만 살린다. 계좌이체 → 카드는 카드 등록과 자동결제 동의가 끝나야 바뀐다 |
| 카드 교체 | 새 빌링키 저장 후 이전 키는 폐기 대기열로(개인 구독의 `key_cleanup` 방식). 미납 청구서가 있으면 바로 재결제 |
| 해지 | `cancel_at_period_end`. 결제된 기간 끝까지 이용, 다음 청구서를 만들지 않는다. 기간이 끝나면 빌링키 폐기. 결제한 적이 없으면 바로 종료 |
| 플랜 올림 | *(B1c-3에서 바뀜 → §5.10)* ~~즉시 적용 + 차액 일할 추가 청구서. 추가 크레딧도 같은 비율(§6.4)~~ → 지금 주기가 입금된 경우에만, 올린 날 새 플랜 전액·새 주기, 남은 크레딧 1회 이월 |
| 플랜 내림 | 다음 달 청구서부터 |
| 환불 | 식은 §6.4. 카드는 승인 취소(부분 취소 가능), 가상계좌는 환불 계좌를 받아 취소. 환불 계좌는 저장하지 않고 토스로 넘기기만 한다. 세금계산서가 나간 건은 수정 세금계산서를 홈택스에서 낸다(관리자 체크 항목) |
| 할인 | 발행 때 1회 차감, 청구서 취소 때 복원 — 지금 그대로이고 두 수단에 똑같이 적용된다. 6개월 선결제 할인과는 겹치지 않는다(§7) |

### 5.5 카드 결제 실패 재시도

**일정: D0 결제 뒤 D+2, D+5, D+9, D+13에 다시 시도한다(자동 5회, 오전 10시 KST). D+15에 새 생성이 닫힌다.**

- 14일 유예 안에 끝나도록 잡았다. Stripe 기본값(2주 안에 최대 8회)보다 적고 직접 설정 상한(3회 재시도)보다 하나 많다. 간격을 점점 넓힌 것은 한도가 다시 차거나 담당자가 조치할 시간을 주기 위해서다. 같은 카드에 거절이 쌓이면 카드사가 가맹점을 나쁘게 볼 수 있어 매일 시도하지 않는다.
- 고객이 카드를 바꾸거나 "지금 결제"를 누르면 일정과 상관없이 바로 시도한다(같은 청구서에 하루 3회까지).
- 마지막 자동 시도(D+13)가 실패해도 유예 끝(D+14)까지 고객이 직접 결제하거나 **이번 청구서만 계좌이체로** 낼 수 있다. 실패 메일마다 두 길을 다 적는다.

**실패 사유별 분기.** 코드는 토스 [에러 코드](https://docs.tosspayments.com/reference/error-codes)의 "카드 자동결제 승인" 절에 있는 것이다. 분류는 메시지를 보고 우리가 한 것이고 토스의 공식 분류가 아니다.

| 분류 | 토스 코드 | 처리 |
| --- | --- | --- |
| 일시 오류 | `FAILED_INTERNAL_SYSTEM_PROCESSING`, `FAILED_CARD_COMPANY_RESPONSE`, 응답 없음 | 먼저 같은 주문을 조회한다. 결제되지 않았으면 1시간 뒤와 그다음 날 다시 시도하고, 일정의 5회에 넣지 않는다. 고객 메일 없음 |
| 한도·잔액 | `REJECT_CARD_PAYMENT`(한도 초과 또는 잔액 부족), `REJECT_ACCOUNT_PAYMENT` | 일정대로 재시도. 첫 실패 때 바로 메일: 한도를 확인하거나 카드를 바꾸거나 계좌이체로 내 달라고 안내. 토스가 한도와 잔액을 한 코드로 주기 때문에 둘을 나눠 처리할 수 없다 |
| 사유를 알 수 없는 거절 | `REJECT_CARD_COMPANY` | 일정대로 재시도하되 D+5까지 같은 사유면 자동 재시도를 멈추고 카드 교체를 요청 |
| 카드를 바꿔야 함 | `INVALID_STOPPED_CARD`, `INVALID_CARD_LOST_OR_STOLEN`, `INVALID_CARD_EXPIRATION`, `INVALID_CARD_NUMBER`, `INVALID_REJECT_CARD`, `INVALID_BILL_KEY_REQUEST`, `NOT_SUPPORTED_CARD_TYPE`, `NOT_REGISTERED_CARD_COMPANY`, `EXCEED_MAX_AUTH_COUNT`, `KYC_BLOCKED` | **자동 재시도를 멈춘다.** 즉시 메일: 카드를 바꾸거나 이번 청구서를 계좌이체로. 새 카드가 등록되면 바로 결제. 메일에는 분실·정지 같은 사유를 적지 않고 "등록된 카드로 결제하지 못했습니다"라고만 쓴다 |
| 우리 쪽 설정 오류 | `UNAUTHORIZED_KEY`, `NOT_MATCHES_CUSTOMER_KEY`, `DUPLICATED_ORDER_ID`, `INVALID_REQUEST`, 할부 관련 코드, `BELOW_MINIMUM_AMOUNT`, `INCORRECT_BASIC_AUTH_FORMAT`, `FAILED_DB_PROCESSING` | 재시도하지 않는다. 고객 메일 없음, 확인 필요 큐와 운영 알림. 고객 잘못이 아니므로 고칠 때까지 그 청구서의 납기를 미룬다(유예가 흐르지 않는다) |

목록에 없는 코드는 "사유를 알 수 없는 거절"로 다룬다.

**메일 시점**: 첫 실패 직후, D+5 실패, D+9 실패("○일 뒤 새 생성이 중단됩니다"), D+13 실패(마지막 자동 시도였음을 알림), D+15 중단 안내. 받는 사람은 소유자와 관리자다.

**멱등과 응답 유실**

- 시도 1건 = 시도 행 1개 = 주문번호(행 UUID) 1개 = 멱등 키 1개(`brand-charge-{시도 id}`). 재시도는 항상 새 시도 행이다. 토스는 오류 뒤 키를 바꿔 같은 주문을 다시 보내지 말라고 안내한다.
- 승인 요청 전에 시도 행을 `charging`으로 바꾸고 임대 시간(lease)을 건다. 타임아웃은 60초 이상.
- 응답이 없거나 409(`IDEMPOTENT_REQUEST_PROCESSING`)면 실패로 적지 않는다. 같은 키로 다시 요청하거나 `GET /v1/payments/orders/{주문번호}`로 조회해 `DONE`이면 `done`, 승인 기록이 없으면 `failed`로 맞춘다. 판정이 안 되면 `review`로 두고 **새 시도를 만들지 않는다**(이중 결제 방지).
- 청구서당 열려 있는 시도는 1건, `done`은 1건만(부분 유니크 인덱스). 청구서가 `paid`·`void`·`refunded`면 새 승인을 보내지 않는다.

### 5.6 개인 구독 엔진에서 가져올 것과 새로 만들 것

| 가져온다 | 새로 만든다 |
| --- | --- |
| 빌링키 암호화(`crypto.ts`, AES-256-GCM, 환경·구독 id를 AAD로) | 조직 단위 구독 행과 권한(소유자·관리자, `requireBrandBillingSeat`) |
| 토스 빌링 클라이언트(`gateway.ts`): 발급·승인·조회·취소 | 청구서–결제 시도 모델(개인 쪽은 기간 행이 곧 주문) |
| 주문번호 = 행 UUID, 멱등 키, 재시도 전 재조회 | 달력 월 주기와 D-7 초안·안내(개인 쪽은 가입일 기준 주기) |
| 승인 중 임대(lease)와 조건부 UPDATE | 가상계좌 발급·입금 웹훅·만료·되돌림·환불 계좌 |

| 준비 상태 판정(`availability`) 방식 | 브랜드 host 심사 로그인·심사 조직(§11), 크레딧 일할·팩·체험(§6) |

**주기 작업 등록이 선행 조건이다.** 개인 구독 갱신 작업(`/api/creator-subscriptions/tick`)은 `vercel.json`에 없고 Cloudflare Worker는 배포되지 않았다. 브랜드 청구 작업은 `vercel.json`에 직접 등록한다(이미 있는 세 tick과 같은 방식, `CRON_SECRET`).

### 5.7 B1a 구현에서 확정된 규칙 (2026-11-24)

1단계(매달 자동 청구 + 계좌이체, 수금은 수동 확인)를 구현하면서 정한 규칙이다. 위 절의 설명과 다르면 이 절이 맞다. 플래그는 `BRAND_BILLING_AUTO_ISSUE`(값이 정확히 `on`일 때만 켜진다, 기본 off)이고, 코드는 `lib/brands/subscriptions/*`, 마이그레이션은 0182·0183이다.

**이용 기한과 상태**

- 구독마다 회차(`epoch`)가 있고, 엔진은 지금 회차의 청구서만 본다. 예전에 결제된 청구서나 끝난 구독의 청구서는 이용 기한에 영향을 주지 않는다.
- `ends_on`은 `planActiveWithGrace`가 읽는 값 그대로 쓴다(그 함수는 `ends_on` 당일을 유예 0일째로 센다).
  - 미납 청구서가 없으면 `ends_on` = 결제된 마지막 달의 **다음 달 1일**. *(B1c-2에서 바뀜 → §5.9)* — 결제된 마지막 주기의 끝.
  - 미납 청구서가 있으면 `ends_on` = 가장 오래된 미납 청구서의 납기일. 납기 15일, 유예 14일이면 16일부터 `past_due`, 30일부터 `suspended`(= 새 생성 중단)다.
- `suspended` 판정은 엔진이 따로 계산하지 않고 `planActiveWithGrace`를 그대로 호출한다. 엔진 상태와 실제 차단이 어긋날 수 없다.
- 끝난(`ended`) 구독은 아무것도 하지 않는다. 그 뒤 관리자가 넣은 수동 플랜을 건드리지 않는다.
- 구독이 끝나지 않은 동안 플랜 배정(`brand_plan_assignments`)은 주기 작업이 소유한다. 관리자가 플랜·기간을 손으로 바꾸는 것은 거부되고, 한도 덮어쓰기·레인 같은 한도 쪽 변경은 그대로 된다. 한도 덮어쓰기 조직은 구독 상태와 무관하게 덮어쓰기 한도를 받는다.

**청구서**

- 구독 중인 조직의 월 청구서(`kind='subscription'`)는 **주기 작업만 만들고 발행한다.** 관리자가 할 수 있는 일은 초안 메모 수정, 취소, 입금 확인, 세금계산서 기록이다. 지금 바로 발행시키려면 "재계산"(`brandSubscription.reconcile`)을 쓴다.
- 금액을 다르게 받는 방법은 둘이다. 발행 전에 할인을 주거나 끝낸다(주기 작업이 발행일 기준으로 반영한다). 발행 뒤라면 취소하고 같은 달 안에 "다시 발행"한다.
- 납기는 `max(발행일, 그 달 1일) + 14일`이다. *(B1c-2에서 바뀜 → §5.9)* — `max(발행일, 주기 시작일) + 14일`.
- **첫 청구서**(입금 전 먼저 열지 않은 경우)의 납기는 `min(시작일 + 14일, 시작한 달 말일)`이다(**결정됨 2026-11-24**). 그 달 말일 + 7일이 지나도록 입금이 없으면 주기 작업이 취소하고, 구독은 `pending`으로 남아 관리자 화면에 "다시 발행 또는 해지" 안내가 계속 뜬다. 다시 발행하면 그날부터 일할이다. *(B1c-2에서 바뀜 → §5.9)* — 납기 = 시작일 + 14일, 납기 + 14일이 지나면 취소, 다시 발행은 전액·주기 없음(§5.9 3·4번).
- 첫 청구서는 시작일부터 계산하고, 플랜은 입금이 확인된 날 열린다. *(B1c-2에서 바뀜 → §5.9)* — 첫 청구서는 전액, 결제 주기가 입금일에 시작한다. 입금 판정은 기록한 시각이 아니라 관리자가 적은 **입금일** 기준이다(미래 날짜는 거부).
- 관리자가 **발행된** 청구서를 취소하면 그 달은 "청구하지 않는 달"이 된다: 이용은 이어지고, 자동으로 다시 청구하지 않는다. 그 달 안에서만 "다시 발행"할 수 있다. 초안을 취소한 것은 해당하지 않고, 주기 작업이 다시 초안을 만든다. *(B1c-2에서 바뀜 → §5.9)* — 달 대신 주기(§5.9 9번).
- 중단(`suspended`)된 동안에는 새 청구서를 만들지 않는다. 밀린 청구서를 내면 그 달은 입금일부터 일할로 청구한다. 건너뛴 달은 나중에 청구하지 않는다. *(B1c-2에서 바뀜 → §5.9)* — 입금일에 새 주기, 전액(§5.9 8번).
- 플랜 내림은 예약한 다음 달 1일에, 그 달 청구서와 함께 적용된다. *(B1c-2에서 바뀜 → §5.9)* — 예약 뒤 처음 시작하는 주기부터. 플랜 올림은 B1b에서 크레딧 일할과 함께 연다(B1a에서는 거부). *(B1c-3에서 바뀜 → §5.10: 일할 없이 올린 날 새 주기)*
- 해지: 결제된 달이 있으면 그 달 끝까지 이용하고 다음 달 초안은 취소된다. *(B1c-2에서 바뀜 → §5.9)* — 달 대신 주기. 한 번도 내지 않았으면 미납 청구서를 모두 취소하고 바로 끝난다("입금 전 먼저 열기"였어도 같다. 이용분을 받으려면 따로 청구한다).
- 플래그가 꺼져 있던 동안 관리자가 만든 초안은 플래그를 켜면 주기 작업이 취소하고 다시 만든다. 그동안 발행·결제된 청구서는 지금 회차로 편입한다.

**주기 작업과 알림**

- `/api/brand-billing/tick`, 매시 정각(`vercel.json`). 플래그가 꺼져 있으면 DB에 접근하지 않고 끝난다. 구독이 없으면 아무것도 쓰지 않는다.
- 조직마다 따로 처리하고, 한 조직의 실패가 다른 조직을 막지 않는다. 실패는 구독 행에 횟수와 코드로 남고 관리자 화면에 보인다.
- 내부 팀 알림(고객 메일 아님, 건수만): 그날 발행된 청구서(세금계산서 발행 필요), 주기 작업이 취소한 청구서(세금계산서가 기록된 건수 포함), 재계산 실패(결제한 고객이 이용하지 못하게 되는 실패는 첫 번째부터, 그 밖은 3회부터, 하루 한 번).
- 입금 확인·취소 뒤의 재계산은 그 기록이 커밋된 뒤 별도 트랜잭션으로 돈다. 재계산이 실패해도 입금 기록은 남고, 다음 주기 작업이 다시 시도한다.

**켜기 전에 알아야 하는 것**

1. 입금을 늦게 기록해도 입금일이 1일 이전이면 다음 달은 전액 청구된다. 첫 청구서는 시작일부터 계산된다. *(B1c-2에서 바뀜 → §5.9)*
2. 구독이 있는 상태에서 플래그를 끄면 이용 기한이 멈춘다. 꺼져 있는 동안 기록한 입금은 다시 켤 때까지 기한을 늘리지 않는다.
3. 첫 청구서가 자동 취소된 뒤 들어온 입금은 "다시 발행" 뒤에 기록해야 한다.
4. `BRAND_PLAN_GRACE_DAYS`를 14로 둔다. 0이면 납기일 당일에 차단된다. 이 값은 손으로 관리하는 조직의 유예에도 적용된다.
5. 주기 작업이 하루 넘게 멈추면 그날의 내부 알림은 나가지 않는다.
6. 두 연결이 동시에 붙는 잠금 충돌은 로컬 DB(연결 하나)로 실행해 보지 못했다. 잠금 순서와 방식(`FOR NO KEY UPDATE`)은 코드로 확인했다.
7. 형식 검증(TLA+/Lean)은 돌리지 못했다(미설치). 대신 엔진을 순수 함수로 두고 속성 테스트로 덮었다.
8. 플래그를 끄면 구독 조직의 플랜 종료일이 그 자리에 멈춘다. 끈 동안 이용을 이어 주려면 관리자가 플랜 종료일을 손으로 늘려야 한다(꺼져 있으면 관리자 플랜 수정이 막히지 않는다). 다시 켜면 주기 작업이 그 사이 끝난 주기를 청구하지 않고 오늘 새 주기로 다시 시작한다(§5.9 6번).

**미납 상태로 1일을 맞는 경우 — 결정됨(2026-11-24, "Stripe 그대로")**

지금 구현을 유지한다. 유예 중(`past_due`)에는 1일에 새 달 청구서를 정상 발행하고, 중단(`suspended`)된 동안에는 발행하지 않는다. Stripe 공식 문서와의 대응(2026-11-24 확인):

**켜기 전에 반드시 고칠 것** — 전부 닫혔다. 1번은 대표 결정으로 닫혔고(위 표), 2~6번은 B1a-2에서 고쳤고, 7번은 1번 결정에 따라 지금 동작을 유지한다.

여섯 번째 리뷰가 실제 서비스를 로컬 DB에서 돌려 확인한 것이다. 후속 PR(B1a-2)에서 고치고 다시 독립 리뷰를 돌린다.

1. *(대표 결정으로 닫힘 2026-11-24: 지금 구현 유지)* **미납 상태로 1일을 맞으면 그 달이 전액 청구된다.** 납기가 지난 미납 청구서가 있어도 유예 중이면 1일에 다음 달 청구서가 전액으로 나가고, 며칠 뒤 중단되면 쓰지 못한 날까지 청구된다.
   - 재현 1: 12월분을 1월 9일에 입금 → 1월분 23/31일, 납기 1월 23일. 1월분 미납 → 2월 1일에 2월분 전액(539,000원) 발행 → 2월 7일 중단 → 1월분을 2월 20일에 내도 2월분은 전액 그대로(13일은 이용 불가).
   - 재현 2: 2월분 미납, 평년이면 2월 15일 + 14일 = 3월 1일 → 3월 1일에 3월분 전액(319,000원) 발행, 3월 2일 중단. 3월 5일 해지하면 하루 쓴 3월분이 미수로 남는다.
   - 제안: 1일에 납기가 지난 미납 청구서가 있으면 그 달 초안을 발행하지 않고, 밀린 금액을 낸 날부터 일할로 청구한다(이미 있는 재개 경로). "미납 중에도 청구는 계속된다"는 1차 리뷰 때의 규칙을 바꾸는 것이라 결정이 필요하다.
2. *(B1a-2에서 수정: 다시 발행은 취소된 청구서의 일수와 납기를 그대로 쓴다)* **"다시 발행"이 금액과 납기를 다시 잡는다.** 일할로 시작한 달을 취소하고 다시 발행하면 오늘부터 다시 일할하고 납기도 오늘 + 14일이 된다.
   - 재현: 1월분 23/31일(399,902원, 납기 1월 23일) → 1월 12일 취소·다시 발행 = 20/31일, 납기 1월 26일 → 1월 25일 다시 = 7/31일(121,709원), 납기 2월 8일.
   - 고칠 방향: 다시 발행은 주기 작업과 같은 일할 시작일을 쓰고, 같은 달 안에서는 취소된 청구서의 납기를 유지한다.
3. *(B1a-2에서 수정)* **실패 알림이 빠질 수 있다.** 중복 방지 키가 "날짜 + 실패 조직 수"라서, 한 조직이 회복하고 다른 조직이 실패하면 같은 키가 되어 알림이 나가지 않는다. 키를 실패 조직 묶음의 해시로 바꾼다.
4. *(B1a-2에서 수정)* **입금 확인 뒤 플랜 기록이 실패해도 관리자 화면은 "입금 완료"만 보여 준다.** 내부 알림과 구독 카드에는 뜨지만, 입금 확인 결과 화면에도 표시해야 한다.
5. *(B1a-2에서 수정: 등록된 오퍼레이션 178개 전체를 분류)* **관리자 오퍼레이션 분류 테스트가 `brandBilling.`·`brandSubscription.` 두 이름만 센다.** 플랜을 쓰는 `brandEngine.plan`(지금은 올바르게 거부됨)이 빠져 있다. 플랜·청구를 쓰는 오퍼레이션 전체를 세도록 넓힌다.
6. *(B1a-2에서 수정: 중단·재발행 대기 건수를 하루 한 번 알림)* **계속 중단 상태인 고객에 대한 팀 알림이 없다.** "먼저 열기"로 시작하고 끝내 내지 않는 조직은 중단된 채 아무 알림도 내지 않는다. 중단 조직 수를 일일 알림에 넣는다.
7. *(지금 동작 유지: 해지는 결제된 기간 끝에 효력이 생기고, 1일에 이미 발행된 달은 그 달 끝까지 간다)* **1일 해지의 결과가 그날 주기 작업 전후로 다르다.** 작업 전이면 청구 없이 바로 끝나고, 작업 뒤면 그 달 전액이 미수로 남고 납기 + 유예까지 이용한다. 1번과 함께 정리한다.

### 5.8 결제 주기 — 플랜 시작일 기준 (B1c, 결정 2026-11-24)

플랜이 있는 모든 조직(관리자가 손으로 배정했든 구독이 배정했든)의 결제 주기는 **플랜 시작일부터 한 달**이다. 이 절이 위의 "달력 월 주기", "첫 달 일할(이용료·크레딧)", 손으로 관리하는 플랜의 "1일 청구"를 대신한다.

**결정된 규칙**

1. 주기는 시작일부터 한 달이다. 17일에 시작했으면 주기는 매달 17일에 시작한다(`brand_plan_assignments.started_on`이 주기의 기준일이다).
2. 그 달에 시작일이 없으면 그 달의 마지막 날이 주기 시작이고, 그 날짜가 있는 달에는 다시 원래 날짜로 돌아온다: 1월 31일 → 2월 28일(윤년 29일) → 3월 31일 → 4월 30일. Stripe의 문서화된 동작과 같다(https://docs.stripe.com/billing/subscriptions/billing-cycle). 다른 점: 날짜는 한국 시간 달력 날짜이고, 주기는 그 날의 한국 시간 0시에 바뀐다(Stripe는 UTC 시각).
3. 일할은 어디에도 없다. 주기마다 월 이용료 전액을 청구하고 월 크레딧 전액을 준다.
4. 쓰지 않은 크레딧은 다음 주기로 넘어가지 않는다. 예외는 플랜 올림 하나다: 한 번 넘어가고 새 주기가 끝나면 사라진다(§5.10).
5. 한도 덮어쓰기 조직과 플랜이 없는 조직은 지금처럼 한국 시간 달력 월이다. 운영 테스트 조직(덮어쓰기, 계정 레인)은 아무것도 바뀌지 않는다(SQL·결과 대조 테스트).
6. 플랜이 없는 조직과 덮어쓰기 조직에서는 관리자가 준 추가 크레딧과 체험 크레딧이 지금처럼 달력 월(`valid_month`)로 유효하다. 플랜 조직에서는 아래 "지급은 주기 하나에 속한다"를 따른다.

**플랜 조직의 기간은 하나다: 지금 주기.** (B1c 수정 라운드, 대표 결정 2026-11-24 — 처음 넣은 "플랜 크레딧 먼저" 장부 계산은 같은 지급을 두 주기에서 쓰게 하거나 지난 주기 사용이 새 주기를 깎는 오류가 확인되어 걷어냈다.)
- 사용량 = 지금 주기 안의 사용(실패·취소 제외). 그 전 날의 어떤 사용도 더하거나 빼지 않는다. 새 주기는 언제나 0에서 시작한다.
- 한도 = 플랜 월 한도 전액 + **지금 주기에 속한 지급**.
- **지급은 주기 하나에 속한다**: 지급의 시작일이 들어 있는 주기다. 달 단위 지급(`valid_month`)의 시작일은 "만든 날(한국 시간)과 그 달 1일 중 늦은 날", 기간 지급(`valid_from`·`valid_until`)의 시작일은 `valid_from`이다(플랜 조직에서는 기간의 끝은 보지 않고 그 주기가 끝날 때까지 쓴다). 시작일이 플랜 시작일보다 앞이면 어느 주기에도 속하지 않는다(플랜 전에 준 크레딧은 플랜 주기로 넘어오지 않는다). 회수한 지급은 세지 않는다. 그래서 어떤 지급도 두 번 쓰이지 않고, 팀원별 사용량의 합이 전체와 같다.
- 다음 달용 지급은 그 달 1일이 들어 있는 주기에 속한다(11월 3일 시작 플랜에 12월분을 주면 11월 3일 ~ 12월 2일 주기).
- 관리자 화면의 지급 목록은 각 지급이 어느 주기에 속하는지와 "이번 주기 끝(12월 16일)까지"를 보여 준다.
- 체험 크레딧 이월은 플랜 조직에는 하지 않는다(지급이 주기 하나에 속하고 그 주기 끝까지 유효하므로). 이월 작업은 그 원래 지급을 확인한 것으로 기록하고 "플랜 조직 — 이월 안 함"으로 센다.

**청구서는 시간이 겹치지 않는다.**
- 구독 청구서(`kind = 'subscription'`)는 주기 청구서면 그 주기, 달 청구서면 그 달을 덮는다. 새 초안(주기든 달이든, 관리자든 자동 청구 엔진이든)은 취소되지 않은 구독 청구서와 하루라도 겹치면 거부된다. "이번 주기", "다음 주기", 시작일 지정, 달 지정 어느 쪽으로 물어도 답이 같다. 다른 종류(추가 크레딧 팩, 조정)는 날짜를 덮지 않으므로 막지 않는다.
- 지금 또는 앞으로의 날을 덮는 구독 청구서가 있으면 플랜 시작일을 바꿀 수 없다(`cycle_already_invoiced`). 그 청구서를 먼저 취소한다. 주기 중간에 새로 시작하며 다시 청구하는 것은 플랜 올림(§5.10)뿐이다. 같은 시작일로 플랜·종료일·좌석·메모만 바꾸는 것은 된다.
- 플랜 종료일 이후에 시작하는 주기는 청구하지 않는다.
- 지난 주기도, 겹치는 청구서가 없으면 시작일을 지정해 청구할 수 있다(놓친 주기). "청구서가 없는 주기" 목록은 플랜 시작부터 지금 주기까지 청구서가 덮지 않은 주기를 모두(최근 12개까지) 보여 준다.

**자동 청구 엔진도 주기 기준이다(B1c-2, §5.9).** 엔진은 주기마다 전액으로 청구하고 일할하지 않는다. 플래그(`BRAND_BILLING_AUTO_ISSUE`)를 켜는 결정과 그 전에 할 일은 §5.9 "켜기 전에"를 따른다.

**어디에 쓰이나.** 플랜 조직의 한도·사용량·초기화일(`loadAllowance`, `reserveAllowance`)은 주기 기준이다. 화면과 작업은 모두 같은 함수(`allowanceWindow`)에서 기간을 받는다: 고객 청구 화면, 스튜디오 크레딧 표시, 팀원별 사용량, 관리자 조직 목록·상세, 업로드 승인 판정. 관리자 조직 목록의 사용량 정렬과 80% 필터만 달력 월 기준이고 화면에 그렇게 적혀 있다.

**손으로 만드는 청구서.** 플랜이 있는 조직의 관리자 청구서는 주기 하나다. 관리자는 "이번 주기" 또는 "다음 주기"를 고른다(주기 시작일을 직접 줄 수도 있다; 겹치는 청구서가 없으면 지난 주기도 된다). 금액은 월 이용료 전액 − 할인 + 부가세, 일할 없음. 청구서에 `cycle_start`·`cycle_end`를 적고 `period`는 주기가 시작하는 달이다. 취소되지 않은 구독 청구서끼리는 시간이 겹치지 않는다(위 규칙). 관리자 화면에 플랜 시작일(= 주기 기준일), 이번 주기 날짜, 다음 청구일, 이번 주기 사용 크레딧, "청구서가 없는 주기" 목록이 보이고, 세금계산서 기록 대기 목록은 한 달에 묶이지 않고 오래된 순이다. 플랜이 없는 조직은 지금처럼 달 단위로 만든다.

**달 중간에 손으로 플랜을 바꿀 때.** 더 높은 플랜은 "플랜 올림"(§5.10), 더 낮은 플랜은 다음 주기 시작일에 플랜 폼으로 바꾼다(R3부터 폼이 주기 중간의 내림을 거부한다, §5.11). 그 주기 안의 차이가 필요하면 일회성 추가 크레딧으로 준다. 시작일을 바꾸면 주기도 옮겨진다(관리자 화면에 새 이번 주기가 보인다).

**배포하면 바뀌는 것(플래그 없음).** 운영에는 지금 플랜 배정·청구서·구독이 없고 덮어쓰기 조직 하나만 있어서 배포 시점에 영향을 받는 조직은 없다. 하지만 동작은 바뀐다.
- 플랜 조직의 한도 기간: 달력 월 → 플랜 시작일 기준 주기. 초기화일도 주기 끝.
- 플랜 조직의 첫 달 한도: 시작일 기준 일할(B1b) → 전액.
- 플랜 조직의 관리자 청구서: 달 단위·첫 달 일할 → 주기 단위·전액, 플랜 시작 전 달은 만들 수 없음, 겹치는 청구서는 거부.
- 모든 구독 청구서 초안(플랜 없는 조직의 달 청구서 포함): "같은 달에 취소되지 않은 청구서가 있으면 거부"(종류 무관) → "취소되지 않은 구독 청구서와 날짜가 겹치면 거부"(팩·조정은 막지 않음).
- 플랜 시작일 변경: 언제나 가능 → 지금 또는 앞으로의 날을 덮는 구독 청구서가 있으면 거부.
- 플랜 조직의 추가·체험 크레딧: 달력 월 → 시작일이 들어 있는 주기 하나(그 주기 끝까지), 플랜 시작 전 지급은 플랜 주기에 포함되지 않음, 체험 이월 없음.
- 세금계산서 기록 대기 목록(자동 청구 플래그가 켜졌을 때만 보임): 고른 달 → 전체, 오래된 순.
- 덮어쓰기 조직, 플랜이 없는 조직: 바뀌지 않음.

### 5.9 자동 청구 엔진 — 플랜 시작일 기준 주기 (B1c-2, 결정 2026-11-24)

§5.2·§5.3·§5.7의 달력 월 규칙(1일 발행, 첫 청구서 말일 납기, 말일 + 7일 취소, 재개한 달 일할)은 이 절로 바뀌었다. 플래그(`BRAND_BILLING_AUTO_ISSUE`)와 스키마 확인, 회차, "주기 작업만 발행한다", 편입, 알림은 §5.7 그대로다. 코드는 `lib/brands/subscriptions/engine.ts`·`service.ts`. 새 마이그레이션은 없다(0186의 `cycle_start`·`cycle_end`를 쓴다. 0186이 없으면 주기 작업은 `schema_not_ready`로 아무것도 하지 않는다).

1. **주기**: 기준일(플랜 배정의 `started_on`, 엔진이 쓴다)부터 한 달. 말일 규칙은 §5.8과 같다.
2. **일할 없음**: 모든 청구서는 그 주기 플랜의 월 이용료 전액이다(할인·부가세는 발행일 기준). 날짜는 `cycle_start`·`cycle_end`가 정한다. `period`(표시용)는 주기 청구서면 주기가 시작하는 달, 첫 청구서면 발행한 달이다. 첫 입금으로 주기가 정해져도 `period`는 바꾸지 않는다(그 달로 세금계산서가 이미 나갔을 수 있다).
3. **납기** = 발행일 + 14일. 늦게 발행되면 `max(발행일, 주기 시작일) + 14일`. 첫 청구서 예외(시작한 달 말일)와 "말일 + 7일 취소"는 없앴다.
4. **첫 청구서(먼저 열기 없음)**: 구독은 언제나 오늘(한국 시간) 시작하고, 시작하면 바로 전액으로 발행한다. 납기 = 오늘 + 14일, 주기 없음, 이용 없음. 입금일 P(오늘 이전)로 입금이 확인되면 주기 0 = [P, 다음 주기 시작), 기준일 = P, `active`. **입금일의 한계**(수정 라운드 1): P는 구독을 시작한 날보다 앞설 수 없고(다시 발행 전 입금은 시작일 이후면 된다), [P, 한 달 뒤)가 다른 구독 청구서(어느 회차든, 달 청구서는 그 달)와 겹치면 안 된다. 어기면 입금 확인이 거부되고 아무것도 기록하지 않는다(`paid_at_before_start` / `paid_at_overlaps_cycle`). 플래그가 꺼져 있던 동안 기록된 그런 입금은 주기 작업이 주기 0으로 만들지 않고 실패로 알린다(구독은 그대로 기다린다). `오늘 > 납기 + 14일`이 되도록 입금이 없으면 주기 작업이 취소하고(할인 회차 복원, 팀 알림) 구독은 `pending`으로 남아 "다시 발행 또는 해지" 안내가 뜬다. 다시 발행하면 새 첫 청구서(전액, 납기 = 오늘 + 14일, 주기 없음)다.
5. **먼저 열기**: 주기 0이 시작일에 시작하고 바로 이용한다. 첫 청구서가 주기 0이고 납기 = 시작일 + 14일, 자동 취소 없이 보통 미납 흐름을 따른다.
6. **다음 주기**: 주기 끝 7일 전부터 초안, 주기 끝 날(= 다음 주기 시작일) 이후 첫 실행에서 발행한다. `active`·`past_due`일 때만 발행한다("Stripe 그대로", §5.7). `suspended`·`ended`·해지 예약·`pending`이면 발행하지 않는다. **한 주기 내내 주기 작업이 돌지 않아** 청구할 다음 주기가 이미 끝났으면(`다음 주기 끝 ≤ 오늘`) 그 주기는 청구하지 않고 오늘 새 주기로 다시 시작한다(재개와 같은 방식: 기준일 = 오늘, 전액, 예전 초안은 시스템 취소). 건너뛴 기간은 청구하지 않는다. 늦은 발행이나 재시작으로 그다음 주기의 초안 시점(7일 전)이 이미 지났으면 같은 실행에서 그 초안도 만든다.
7. **이용 기한(`ends_on`)**: 미납이 있으면 가장 오래된 미납 청구서의 납기, 없으면 결제됐거나 청구하지 않기로 한 주기의 끝. 상태는 `planActiveWithGrace` 그대로다.
8. **재개**: `suspended`인 동안 밀린 청구서가 입금일 P로 결제되면 P에 새 주기를 시작한다(기준일 = P). 그 주기 청구서를 바로 전액 발행하고, 예전 기준일의 초안은 주기 작업이 취소한다. 중단된 날은 청구하지 않는다. `past_due`일 때 내면 아무것도 다시 시작하지 않는다.
9. **청구하지 않는 주기**: 결제된 주기가 있는 회차에서 관리자가 **발행된** 주기 청구서를 취소하면 그 주기 끝까지 이용하고 자동으로 청구하지 않는다. "다시 발행"은 그 주기가 지금 주기인 동안만 되고, 같은 주기 날짜·전액(그때의 할인)·**취소된 청구서와 같은 납기**로 낸다. 초안 취소는 해당하지 않는다(주기 작업이 다시 만든다). 먼저 열기로 시작해 아무것도 내지 않은 구독에서 주기 0 청구서를 취소했다면, 주기 0이 끝나기 전에는 같은 날짜·납기로, 끝난 뒤에는 오늘부터 새 주기(납기 오늘 + 14일)로 다시 발행한다. 중단된 날을 청구하지 않기 위해서다(수정 라운드 1, 속성 테스트가 찾음).
10. **플랜 변경·해지**: 플랜 내림은 예약한 뒤 처음 시작하는 주기부터 적용된다(그 주기 청구서가 새 플랜을 싣고, 그 주기 시작일에 배정이 바뀐다). 플랜 올림은 §5.10(지금 주기가 입금된 경우에만, 올린 날 새 주기). 해지: 결제된 주기가 있으면 다음 주기 청구서를 만들지 않고(초안은 취소) 지금 주기 끝까지 이용한 뒤 `ended`. 한 번도 내지 않았으면 미납을 모두 취소하고 바로 끝난다. 주기가 끝나기 전에 해지를 취소하면 청구가 이어진다. 해지해도 예약한 플랜 내림은 남아서 해지 취소 뒤 그대로 적용되고, 구독이 실제로 끝나면 지운다(수정 라운드 1).
11. **편입**(플래그가 꺼져 있던 동안의 청구서): 초안은 취소한다. 발행·결제된 청구서는 `cycle_start`가 있으면 그대로, 없으면 기준일의 주기 가운데 그 달에 시작하는 주기를 준다. 기준일이 없거나 겹치면 편입하지 않고 보류해 센다(추측하지 않는다). 보류한 청구서는 주기 작업 결과(`held`)와 하루 한 번 나가는 내부 알림(건수만)에 세고, 관리자 구독 카드에 청구서와 이유("플랜 배정이 없음" / "다른 청구서와 겹치지 않게 주기에 넣을 수 없음")를 "구독 상태 지금 재계산" 버튼과 함께 보여 준다.

**구현하며 정한 것 (대표 확인 2026-11-24)**

- 재개는 경계일(다음 주기 시작일)에 청구할 수 없는 상태였고 지금은 청구할 수 있을 때만 새 주기로 시작한다. 중단 중에 냈어도 입금일이 지금 주기 끝보다 앞이면 다시 시작하지 않고 그 경계에서 이어 청구한다.
- 늦게 기록한 재개 입금: 재개 청구서는 입금을 본 실행에서 바로 발행하고, 납기는 `max(발행일, 주기 시작일) + 14일`이다(입금일 + 14일보다 늦을 수 있다).
- 구독은 언제나 오늘(한국 시간) 시작한다(수정 라운드 1). 시작 화면에는 시작일 입력이 없고 "오늘 시작"만 보인다. 앞당긴 시작은 발행하자마자 납기가 지난 청구서를 만들었다. 다른 날을 직접 보내면 `started_on_must_be_today`로 거부한다.
- 짧은 입금 기간 경고는 없앴다: 시작은 늘 오늘이고 첫 청구서 납기는 오늘 + 14일이다.
- 플랜 배정이 없는 조직의 편입 대상 청구서는 보류해 센다.

**겹침 규칙과 기준일 (§5.8과 함께)**

- 엔진의 초안도 겹침 규칙을 지난다. 주기 초안은 그 주기, 주기가 없는 첫 청구서는 오늘부터 한 주기(`[오늘, 다음 달 같은 날)`)로 확인한다. 그래서 앞 구독의 주기가 끝난 같은 달에도 새로 시작할 수 있다. 겹치면 그 조직의 단계 실패로 세고 아무것도 만들지 않는다.
- 플랜 시작일 변경 거부(`cycle_already_invoiced`)는 관리자 경로에만 있다. 엔진은 첫 입금과 재개 때 시스템 권한으로 기준일을 옮긴다(테스트로 고정).

**미납 중 크레딧 50%** (§6.4, 플래그가 켜졌을 때만)

- **납기가 지난 뒤에만**(대표 결정 2026-11-24): 구독이 끝나지 않은 플랜 조직에서 지금 회차의 발행된 구독 청구서 가운데 **납기가 지난(`오늘 > 납기`, 한국 시간) 미납이 하나라도 있으면** 지금 주기 한도의 **플랜 몫**이 `floor10(플랜 한도 × 50 / 100)`이다. 지금 주기 것만 보지 않으므로, 오래된 미납을 두고 새 청구서만 내면 반으로 남는다.
- 발행됐어도 납기 전이면 전액이다(납기 당일도 전액, 다음 날 0시부터 반). 입금이 확인되어 납기가 지난 미납이 없어지면 바로 전액이다. 유예가 끝나면(`suspended`) 지금의 이용 규칙대로 새 생성이 닫힌다. 지급(추가·체험·이월 크레딧)은 줄이지 않는다.
- 납기가 지날 때 이미 반 넘게 썼으면 새 예약은 거절되고 남은 크레딧은 0으로 보인다(음수가 되지 않는다). 이미 쓴 것은 되돌리지 않는다.
- 먼저 열지 않은 첫 청구서는 입금 전에 플랜이 없으므로 해당하지 않는다. 먼저 열기면 해당한다.
- 덮어쓰기 조직은 덮어쓰기 한도 그대로다(SQL도 같다). 확인은 플랜 조직의 한도 문장 하나에 붙여서 문장 수가 늘지 않는다. 플래그가 꺼져 있으면 SQL이 B1c 그대로다(기록 대조).

**켜기 전에**

1. 0186·0187 클라우드 적용.
2. `BRAND_PLAN_GRACE_DAYS=14`.
3. 고객 화면의 "매달 1일 … 초기화" 설명과 "이번 달" 문구 다섯 곳은 아직 달력 월 말투다(고객 문안은 대표 결정).
4. 두 연결이 동시에 붙는 잠금 충돌과 형식 검증은 여전히 돌리지 못했다(§5.7). "같은 날 두 번 실행" 테스트는 로컬 DB(연결 하나)에서 차례로 돌므로 반복 실행에 안전한지(멱등)를 보여 줄 뿐 동시성을 증명하지 않는다. 잠금 순서(조직 → 구독 → 청구서)는 문장 순서로 확인한다.
5. 플래그를 끄면 구독 조직의 플랜 종료일이 멈춘다. 관리자가 손으로 늘려야 한다(§5.7 8번).

### 5.10 플랜 올림 — 주기 중간 (B1c-3, 결정 2026-11-24)

구독 조직(자동 청구, `BRAND_BILLING_AUTO_ISSUE`)과 관리자가 손으로 플랜을 배정하는 조직 모두에 적용된다. 계산은 `lib/brands/billing/plan-upgrade.ts`, 적용은 `plan-upgrade-apply.ts`, 관리자 오퍼레이션은 `brandSubscription.upgrade`(구독 조직, 플래그)와 `brandBilling.planUpgrade`(손 관리 조직, 플래그 없음)다. 새 마이그레이션은 없다(0186의 `valid_from`·`valid_until`과 `carry` 종류를 쓴다).

1. 올리는 날 새 플랜의 월 이용료 전액을 청구하고, 그날 새 주기가 시작한다(기준일 = 올린 날, 한 달, 말일 규칙은 §5.8). 이전 주기는 `[시작일, 올린 날)`로 잘린다. 결제된 청구서의 `cycle_end`가 올린 날로 바뀌고 변경 전후가 기록된다. 이전 플랜의 남은 기간은 환불하지 않는다.
2. 이전 주기에서 **올린 날 전까지** 쓸 수 있던 크레딧을 **한 번** 새 주기로 넘긴다: `이월 = max(0, floor10(이전 플랜 한도 + 올린 날 전에 시작한 지급 − [주기 시작일, 올린 날)의 사용))`. 지급의 시작일은 한도 계산과 같은 식으로 본다(§5.8 "지급은 주기 하나에 속한다"). **올린 날이나 그 뒤에 시작하는 지급**(다음 달용 지급, 당일 아침에 준 지급, 다음 달로 넘어간 체험 크레딧 등)은 넘기지 않는다. 그런 지급은 새 주기(또는 그 뒤 주기)에 그대로 속해 한 번만 센다(수정 라운드 1: 처음 구현은 이전 주기 한도 전체를 써서 이런 지급을 이월과 새 주기에서 두 번 셌다). 넘긴 크레딧은 지급 한 줄이다(`kind = 'carry'`, `valid_from` = 올린 날, `valid_until` = 새 주기 마지막 날). 새 주기에 속하므로 새 주기가 끝나면 사라진다. 그 밖에는 넘어가지 않는다.
3. 지금 주기 청구서가 **결제됐을 때만** 올린다. 미납(발행됨), 청구하지 않기로 한 주기(면제), 청구서 없음(초안만 있는 경우 포함)이면 거부한다. 이번 주기를 먼저 청구하고 입금을 기록한다.
4. 플랜 내림은 그대로다(다음 주기 시작부터, 이월 없음). 내림이 예약된 상태에서 올리면 예약이 취소된다.
5. 넘긴 크레딧은 지급이라 미납 50% 규칙(§5.9)으로 줄지 않는다. 50% 규칙은 보통과 같다: 새 청구서는 납기(올린 날 + 14일)까지 새 플랜 크레딧 전액이고, 납기가 지나도 미납이면 새 플랜 크레딧만 반이 된다.

**예.** 플랜 29(한도 270,000원)를 11월 17일에 시작했고 11월 25일(주기 9일째)까지 100,000원을 썼다. 이날 49로 올린다.
- 이전 주기: 11월 17일 ~ 11월 24일(청구서 `cycle_end` = 11월 25일).
- 이월: 170,000원, 12월 24일까지.
- 새 주기: 11월 25일 ~ 12월 24일, 다음 청구일 12월 25일.
- 새 플랜 한도: 460,000원. 구독 조직이면 12월 9일(납기)까지는 미납이어도 460,000원이고, 12월 10일부터 입금 전까지는 230,000원이다. 이월은 그와 상관없이 다 쓴다.
- 청구: 539,000원(490,000 + 부가세 49,000), 납기 12월 9일.
- 12월 25일부터는 이월이 없고 한도는 460,000원이다.

**구독 조직.**
- 새 주기 청구서는 그 자리에서 발행된다. 자동 청구 엔진의 쓰기 경로를 지나므로 시스템 발행, 지금 회차, 납기 오늘 + 14일, 계좌이체다.
- 그 뒤는 보통 규칙을 따른다. 미납이면 납기 + 유예까지 이용하고, 연체 다음은 중단이며, 입금하면 복구된다. 이전 플랜은 돌아오지 않는다.
- 예약된 내림은 취소되고, 이전 기준일로 만든 다음 주기 초안은 시스템이 취소한다.
- 엔진은 기준일의 한 달보다 짧은 주기(올림으로 잘린 주기)에서 실행을 끊고, 그 끝날에 시작하는 주기를 새 기준일로 본다. 잘린 주기가 없으면 엔진의 계산은 전과 같다.

**손 관리 조직.** 새 주기 청구서는 같은 금액의 초안으로 만들어진다. 관리자가 청구서 목록에서 발행하고, 납기는 발행할 때 정해진다(발행일 + 14일). 미리보기의 납기는 오늘 발행한다고 보고 계산한 날이다. 미납 50% 규칙은 구독 조직에만 있다.

**공통.**
- 한 트랜잭션이고 조직을 먼저 잠근다. 한 단계라도 실패하면 아무것도 바뀌지 않는다.
- 두 단계로 확정한다. 미리보기(새 플랜, 오늘 날짜, 이월, 새 주기, 청구 금액, 납기)의 요약값이 확정할 때와 다르면 거부한다(`preview_stale`). 같은 날 두 번째 확정은 `already_upgraded_today`로 거부한다.
- 주기 중간에 플랜 시작일을 옮기는 것은 이 기능뿐이다. 잘린 청구서가 오늘 끝나고 다음 주기 초안이 취소되므로, 공용 쓰기 함수에 있는 관리자 시작일 변경 거부(`cycle_already_invoiced`)를 그대로 통과한다. 보통 수정에서는 그 거부가 그대로다.
- 다음 주기 청구서가 이미 발행되었으면 거부한다(`later_cycle_already_issued`). 그 청구서를 먼저 취소한다.
- 덮어쓰기 조직: 청구 목적으로는 올릴 수 있지만 이월 지급은 만들지 않는다. 한도는 덮어쓰기 값 그대로다.
- **플랜 폼으로는 주기 중간에 올리지 못한다**(수정 라운드 1): 취소되지 않은 구독 청구서가 오늘을 덮는 동안, 관리자 플랜 폼(`brandEngine.plan`, `brandBilling.planAndAllowance.set`)은 **더 높은** 플랜을 거부하고 "플랜 올림"을 가리킨다(`plan_upgrade_required`). 오늘을 덮는 청구서가 없으면 전과 같다. **더 낮은** 플랜은 R3(§5.11)부터 다음 주기 시작일에 바꾼다: 발행·입금된 구독 청구서가 오늘을 덮는 동안 두 폼이 거부한다(`plan_downgrade_next_cycle`).
- 손 관리 조직에서 올린 뒤에는 새 플랜 크레딧이 바로 열리고 새 주기 청구서는 **초안**이다. 미리보기와 결과 문구가 그렇게 말하고, 그 청구서를 발행할 때까지 플랜 패널에 "올린 주기의 청구서가 아직 발행되지 않았습니다"가 보인다.
- 그 밖의 거부: 주기 첫날(`upgrade_on_cycle_start`; 다음 날부터 올릴 수 있다), 내림·같은 플랜·프로젝트 전용, 플랜이 오늘 유효하지 않음(종료일이 지나 유예 중인 경우 포함), 샌드박스 조직, 새 플랜 기본 크레딧 미설정(R3부터 세 유료 플랜에서는 일어나지 않는다: 확정 크레딧을 쓴다), 구독 조직을 손 관리 오퍼레이션으로 올리려 함(`subscription_upgrade_only`), 구독이 정상(`active`)이 아니거나 해지 예약됨, 플래그 꺼짐(구독 오퍼레이션만).

**구현하며 정한 것 (확인 필요)**
- 이전 주기 사용량은 올린 날 0시(한국 시간)까지만 센다. 그날 올리기 전에 쓴 것은 새 주기 사용량에 들어간다(새 주기가 그날 0시에 시작한다). 이월에서 또 빼지 않으므로 두 번 빠지지 않는다.
- 하루에 한 번만 올릴 수 있다.
- 오늘을 덮는 청구서가 주기 청구서가 아니라 달력 월 청구서(주기 이전에 만든 것)면 자를 수 없으므로 거부한다(`current_invoice_not_cycle`).
- 구독은 정상(`active`)일 때만 올린다. 연체 중이면 입금부터 기록한다.
- 이월은 한도가 플랜에서 오는 조직에만 만든다. 덮어쓰기·기본값 조직은 0이다.
- 한 주기에 날을 달리해 두 번 올리면 두 번째 이월에 첫 이월의 남은 몫이 함께 들어간다(첫 이월은 올린 날에 시작한 지급이므로 두 번째 올린 날 전에 시작했다). 새 크레딧은 생기지 않는다.
- **이월은 올린 순간의 스냅숏이다.** 올린 뒤에 이전 주기의 지급을 회수해도 이월 안의 몫은 그대로 남고, 이전 주기의 작업이 나중에 실패해도 이월에 돌려주지 않는다.
- 올린 주기의 청구서를 내지 않아 중단된 뒤 입금으로 새 주기가 다시 시작되면(§5.9 8번) 이월은 남겨 두고 간다. 이월은 어차피 올린 주기와 함께 끝나는 지급이다.
- **마진 속성(정직하게)**: 올림은 **청구서가 발행된(구독) 또는 초안이 만들어진(손 관리) 주기의 플랜 한도**보다 많은 플랜 크레딧을 쓸 수 있게 만들지 않는다. "입금된 주기"가 아니다. 새 청구서를 끝내 내지 않으면 보통 규칙대로 납기까지 전액, 납기 뒤 플랜 몫 반, 유예 뒤 중단이므로 입금 없이 쓰이는 플랜 크레딧은 한 주기 한도를 넘지 않는다(속성 테스트와 미납 시나리오 테스트).
- 이월 지급의 `valid_month`는 올린 달이다(비워 둘 수 없는 열). 플랜 조직은 `valid_from`으로 센다. 플랜이 끊겨 기본 한도로 떨어지면 그 달 말까지 달력 월로 센다(언제나 새 주기 끝보다 앞이다).
- 추가 크레딧 팩(B5)은 아직 없다. 지금 계산은 주기에 속한 지급을 모두 넘기므로, 팩을 만들 때 팩도 넘길지 정한다.
- 플랜 내림 예약 오퍼레이션에 더 높은 플랜을 넣으면 "플랜 올림을 쓰라"는 이유로 거부한다(`upgrade_use_upgrade_operation`, 전에는 `upgrade_not_available_yet`).

**배포하면 바뀌는 것.**
- 관리자 화면에 오퍼레이션 둘이 생긴다. 실제로 올리기 전에는 아무것도 바뀌지 않는다.
- `brandSubscription.scheduleDowngrade`가 올림을 거부할 때 주는 이유가 `not_available_yet:upgrade_not_available_yet`에서 `invalid:planId:upgrade_use_upgrade_operation`으로 바뀐다.
- 엔진의 실행 계산은 잘린 주기가 없으면 전과 같다. 기존 엔진 표 테스트와 속성 테스트는 그대로 통과한다.
- 덮어쓰기 조직과 플랜 없는 조직의 한도 계산은 바뀌지 않는다.

### 5.11 수동 경로 보완 (R3, 2026-11-24)

자동 청구 플래그를 끈 채 첫 유료 고객을 받는 수동 경로(승인 → 플랜 → 주기 청구서 → 발행 → 입금 → 세금계산서 → 할인 → 추가 크레딧 → 올림 → 내림 → 종료)를 실제 화면으로 눌러 보고 고친 것. 마이그레이션 없음, 플래그는 그대로 기본 off.

1. 미리보기가 리디렉트 주소에서 잘리지 않는다: 관리자 결과 `detail`은 1,000자(인코딩 3,000자)까지 실린다(전에는 200자라 플랜 올림 확정 버튼이 나오지 않았다). 미리보기마다 형식·해석 함수가 하나씩 있고(`lib/admin/billing-preview-detail.ts`), 미리보기 상태마다 제목이 따로 있다(모르는 미리보기는 중립 문장).
2. 세금계산서 기록(작성일·승인번호)은 플래그가 꺼져 있어도 된다: 발행·입금된 계좌이체 청구서, 샌드박스가 아닌 조직, 0182 열이 있을 때만(없으면 칸이 보이지 않는다). 감사 기록은 그대로. `/admin/brand-billing`의 "발행할 세금계산서" 목록은 여전히 플래그가 켜졌을 때만 보인다.
3. 수동 입금일은 청구서 발행일(한국 시간)부터 오늘까지만 받는다(`paid_at_before_issue` / `paid_at_in_future`, 관리자 문장에 허용 범위). 구독 조직은 §5.9의 규칙 그대로다. 수정 라운드 1(B1): 주기 청구서에만 적용한다. 달 청구서(플랜 없는 조직, 덮어쓰기 조직, 주기 전 구독 첫 청구서)는 R3 전처럼 어떤 날짜든 받는다.
4. 관리자가 발행하는 주기 청구서(플랜 조직)는 `due_on`을 적는다. 수정 라운드 1(M4): 엔진과 같은 함수·같은 규칙 `max(발행일, 주기 시작일) + 14일`이라, 주기 시작 전에 미리 발행한 청구서도 플래그를 켠 뒤 엔진이 지킬 날짜를 갖는다. 플랜 없는 조직의 달 청구서는 전과 같다. 플래그가 꺼져 있으면 아무것도 이 날짜를 읽지 않는다(연체는 여전히 "발행 후 14일 초과", 크레딧 반감 없음). 플래그를 켜면 편입이 적힌 납기를 그대로 두고(`coalesce`), 미납 50% 규칙이 그 날짜를 쓴다.
5. 고객 청구 내역에 발행된 적 없는 취소 초안은 보이지 않는다(발행 뒤 취소는 그대로 보인다).
6. 플랜 기본 한도 행이 없거나 비어 있는 유료 플랜은 확정 크레딧(§6.3, 크레딧 × 10원)을 쓴다. 저장된 행이 이기고, 개별 덮어쓰기가 둘 다 이긴다. 한도·스냅숏·올림 미리보기와 이월·관리자 요약이 모두 `resolvePlanCapKrw`(lib/brands/billing/plan-credits.ts) 하나를 거친다. `plan_cap_not_set`은 확정 크레딧이 없는 플랜 id에만 남는 방어 경로다.
7. 플랜 내림은 다음 주기 시작일부터다(대표 확인 2026-11-24): 발행·입금된 구독 청구서가 오늘을 덮는 동안 두 플랜 폼은 더 낮은 유료 플랜을 거부하고(`plan_downgrade_next_cycle`) 다음 주기 시작일을 알려 준다. 초안만 있으면 막지 않는다(경계일에 발행 전에 바꾼다). 종료일, 같은 플랜 수정, 구독 조직의 내림 예약은 그대로다.
   - 수정 라운드 1(M1): 거부 문장이 상태마다 맞는 길을 말한다 — 다음 주기 청구서가 이미 발행됨(그 청구서를 먼저 취소, `plan_downgrade_next_issued`), 다음 주기도 이미 입금됨(그 주기는 지금 플랜, 그다음 주기 시작일, `plan_downgrade_next_paid`), 오늘 시작한 주기의 청구서가 발행·미입금(취소하고 바꾼 뒤 다시 발행, `plan_downgrade_cycle_issued_today`).
   - 수정 라운드 1(M2): `project_only`도 모든 유료 플랜보다 낮은 플랜으로 보고 같은 조건·문장으로 거부한다. 플랜을 끝내는 방법은 종료일이다.
   - 수정 라운드 1(M3): 플랜 올림으로 시작한 주기(올림 이벤트의 `upgradedOn` = 플랜 시작일) 안에서는 청구서 상태와 상관없이(초안을 취소해도) 낮은 플랜을 거부한다(`plan_downgrade_upgraded_cycle`, 다음 주기 시작일). 이월은 높은 플랜 몫으로 준 것이다.
   - 덮어쓰기 조직이 플랜도 갖고 있으면 4·7번(납기, 내림 거부)은 적용된다. "덮어쓰기 조직은 그대로"는 한도 계산에 대한 보장이다(리뷰 m1).
8. 관리자 화면: 월 한도 기준은 실제 상태로 미리 선택되고(덮어쓰기 행이 있으면 "개별 한도 직접 지정"과 그 값, 아니면 "플랜 기본값 따름"), 플랜·청구·구독 오퍼레이션의 충돌 제목은 캠페인 문장이 아닌 중립 문장(`billingConflict`)이다. 유예 표기는 "종료일 종료 · 유예 끝까지 유예", 크레딧을 뜻하는 원 입력칸 옆에 "10원 = 1크레딧 · …원 = …크레딧"이 보인다.

## 6. 크레딧

요구는 "마진 계산에 오류가 없을 것"이다. 아래 숫자는 저장소의 상수에서 계산했고, 표는 스크립트로 돌린 결과다. 입력값과 식을 같이 적는다.

### 6.1 지금 차감되는 크레딧과 원가

**입력값(코드 상수)**

- 1크레딧 = 이용액 10원: `STUDIO_CREDIT_KRW = 10` (`lib/brand-studio/credits.ts`)
- 환율 1,400원/USD, 이미지·오디오 배수 1.12, 영상 배수 1.11: `STUDIO_USAGE_FACTORS` (`lib/brand-studio/usage-rate.ts`)
- 원가는 결과 1건마다 센트 단위로 올린다: `billedUsd(usd) = 올림(usd × 100) ÷ 100` (`lib/brand-studio/models.ts`)
- 차감액: `usageKrw = 올림(billedUsd × 1,400 × 배수 ÷ 10) × 10`. 고객이 내는 크레딧은 레인(계정·API)과 무관하게 견적 그대로다. 제공사 실제 청구액은 `cost_usd`에만 기록된다.

**모델별 표** (원화 원가 = 올림한 USD × 1,400, 마진율 = (크레딧 × 10 − 원화 원가) ÷ (크레딧 × 10))

Seedream 5.5 2K 한 장을 식으로 따라가면: 정가 $0.035 → 센트 올림 $0.04 → × 1,400 = 56원 → × 1.12 = 62.72원 → ÷ 10 올림 = **7크레딧(70원), 원가 56원, 마진 20%**. 참조 이미지를 2~3장 붙이면 10크레딧, 원가 84원이다.

**최악의 크레딧당 원가.** `usageKrw ≥ billedUsd × 1,400 × 배수`이므로 원가 ÷ 이용액 ≤ 1 ÷ 배수다. 배수가 가장 작은 영상 기준으로 **크레딧당 원가는 10 ÷ 1.11 = 9.0090원을 넘지 않는다**(이미지·오디오는 10 ÷ 1.12 = 8.9286원). 아래 계산은 전부 9.0090원을 쓴다.

**"한도를 월 요금과 같게 잡으면 마진 약 10%"의 근거.** 따로 조사한 문서는 찾지 못했다. 위 배수에서 바로 나오는 값이다: 이미지 1 − 1/1.12 = 10.7%, 영상 1 − 1/1.11 = 9.9%. 즉 지금 차감표에는 마진이 10% 남짓만 들어 있고, 나머지 마진은 플랜이 주는 크레딧 수로 정해야 한다.

**이 식에 들어 있지 않은 원가**(크레딧으로 묶이지 않는다. §6.6의 월 원가 점검으로 본다)

- 제공사가 청구했지만 고객에게는 차감하지 않는 실패·차단·재시도.
- 크레딧을 받지 않는 기능: Prompt Architect, 말로 편집, 영상 분석, 가사 초안, 내보내기.
- 원가와 연결되지 않은 고정 차감: 업스케일(로컬 GPU), 효과음(코드에 USD 상수 없음, 문서상 초당 $0.002).
- 저장 용량(200 / 400 / 800 GB)과 전송.
- 실제 환율이 1,400원보다 높을 때의 차이(§6.3 민감도).

### 6.2 구조 — 차감표는 그대로, 플랜 크레딧 수로 마진을 잡는다

- 크레딧 단위(10원)와 모델별 차감표는 바꾸지 않는다. 가격 코드에 손을 대지 않으므로 계산 오류가 들어갈 자리가 없다.
- 플랜은 매달 크레딧을 준다. 값은 `brand_plan_allowance_defaults.monthly_cap_krw`에 넣는다(크레딧 × 10원). 지금 있는 관리자 오퍼레이션(`brandBilling.planDefault.set`)으로 들어간다. 행이 없거나 비어 있으면 확정 크레딧(`BRAND_PLAN_CREDITS` × 10원)을 쓰고, 저장된 행이 있으면 행이 이긴다(R3, §5.11-6).
- 고객이 크레딧 1개에 내는 값은 `월 이용료 ÷ 월 크레딧`이다. 이 값과 9.0090원의 차이가 마진이다.
- 차감 순서: 플랜 크레딧 → 추가 팩·체험 크레딧(만료가 가까운 것부터).

### 6.3 플랜별 월 기본 크레딧

**기준(대표 결정 2026-11-23): 마진 10~12%.** 카드로 결제해도 10~12%가 남도록 잡는다. 고객사 할인은 크레딧 수를 정하는 데 넣지 않는다. 할인은 영업 비용으로 따로 본다.

**식**

```
카드 수수료   = 올림(월 이용료 × 1.1 × 0.0374)        (부가세 포함 결제액 기준)
계좌이체 수수료 = 440원 (가상계좌 공개 요금, 수동 입금은 0원)
최악 원가     = 크레딧 × 10 ÷ 1.11
마진         = 월 이용료(부가세 제외) − 결제 수수료 − 최악 원가
목표 마진 m에서의 크레딧 = 내림((월 이용료 × (1 − m) − 카드 수수료) × 1.11 ÷ 10), 500 단위로 내림
```

**세 가지 안**

| 안 | 290,000원 | 490,000원 | 690,000원 |
| --- | --- | --- | --- |
| 10% | 27,646 → **27,500** | 46,713 → **46,500** | 65,780 → **65,500** |
| 12% | 27,002 → **27,000** | 45,625 → **45,500** | 64,248 → **64,000** |
| **결정됨 (2026-11-23)** | **27,000** | **46,000** | **65,000** |

**결정됨(2026-11-23): 월 27,000 / 46,000 / 65,000 크레딧.** 운영 DB의 플랜 기본 한도로는 270,000 / 460,000 / 650,000원이다(크레딧 × 10원, `brandBilling.planDefault.set`). 세 플랜 모두 10~12% 안에 있고, 숫자가 외우기 쉽고, 높은 플랜일수록 크레딧 1개 값이 조금 싸다(10.74 → 10.65 → 10.62원).

**기준을 계좌이체로 잡으면 안 되는 이유.** 계좌이체 수수료(440원)로 10~12%를 맞추면 크레딧이 28,000~28,500 / 47,500~48,500 / 67,000~68,500으로 늘고, 같은 고객이 카드로 내면 마진이 6.4~8.9%로 내려간다.

**이 마진에서 지켜야 하는 것**

1. **모델별 차감 하한을 테스트로 고정**한다(§6.6-1). 새 모델이 배수 1.11보다 낮게 들어오면 빌드가 깨진다.
2. *(B1c로 바뀜 → §5.8)* **일할은 돈과 크레딧에 같은 비율로**(§6.4). 지금 코드는 첫 달 이용료만 일할하고 크레딧은 한 달 치를 다 준다. 30일짜리 달의 28일에 시작한 고객이 29,000원을 내고 27,000크레딧(원가 최대 243,243원)을 받는 구멍이다. 구독을 열기 전에 반드시 고친다.
3. **미납 중 크레딧 제한**(§6.4, 결정됨).
4. **월 원가 점검은 필수다**(§6.6-8). 마진이 10~12%면 §6.1의 "식에 들어 있지 않은 원가"(무료 기능, 실패·차단 청구분, 저장 공간, 환율)가 마진의 큰 부분을 차지할 수 있다. 재 보기 전에는 실제 마진을 알 수 없다.
5. **환율 상수 갱신 절차.** 분기마다, 그리고 월평균 환율이 상수(1,400원)에서 3% 넘게 벗어나면 `STUDIO_USAGE_FACTORS.krwPerUsd`를 실제 환율로 고치고 이 절의 표를 다시 계산한다. 상수를 올리면 차감 크레딧이 같이 올라 마진율이 돌아온다. 고객이 보는 차감량이 바뀌므로 약관 초안 제12조 ④의 사전 통지를 거친다.

**환율 민감도** (확정 크레딧 기준. 차감표는 1,400원에 고정돼 있어서 실제 환율이 오르면 원가만 오른다)

### 6.5 체험 크레딧

대표 결정: 승인제, 체험 크레딧으로 Seedream 5.5 이미지 약 40장, 금액으로 9,000원 이하. **400크레딧을 관리자가 워크스페이스를 승인할 때 조직당 1회 지급하고, 승인한 달과 다음 달 말일까지 쓸 수 있다 — 결정됨(2026-11-23).**

| 체험 크레딧 | Seedream 2K 참조 없음(7) | 참조 2~3장(10) | 참조 4장(11) | Nano Banana Pro(22) | 영상에 다 썼을 때 | 최악 원가 |
| --- | --- | --- | --- | --- | --- | --- |
| 280 | 40장 | 28장 | 25장 | 12장 | 720p 5초 1편 | 2,523원 |
| **400 (결정됨)** | 57장 | **40장** | 36장 | 18장 | 720p 5초 2편 | **3,604원** |

- **400크레딧으로 정한 근거.** 브랜드는 대부분 제품 사진을 참조로 붙이므로 한 장이 10크레딧 안팎이다. 400이면 그렇게 써도 40장이고, Seedream만 썼을 때 실제 원가는 3,360원(40장 × $0.06 × 1,400)이다.
- **원가 상한 9,000원은 어떤 모델에 쓰여도 지켜진다.** 크레딧당 원가가 9.0090원을 넘지 않으므로 999크레딧까지는 영상·고가 모델에 전부 써도 9,000원 이하다(999 × 10 ÷ 1.11 = 9,000원). 그래서 **이미지 전용 제한은 필요 없다.** 지금 추가 크레딧에는 모델을 가리는 열도 없다.
- 유효기간: 승인한 달과 다음 달 말일까지(결정됨. 추가 팩에도 같은 규칙을 제안했다).
- 구현: 지금의 `brand_allowance_grants`에 줄 하나를 넣으면 된다. 더할 것은 셋이다. ① 종류 열(`kind`: 추가 / 체험 / 팩)과 "조직당 체험 1건" 유니크 인덱스. ② 다음 달로 한 번 넘기는 처리(지금은 한 달만 유효). ③ 승인 오퍼레이션. 지금은 한도가 0보다 크면 승인된 것으로 판정하므로 체험 크레딧이 사라지면 업로드 제한이 다시 걸린다. 승인 사실을 따로 기록해야 한다.
- 크레딧을 받지 않는 기능(§6.1)은 체험 중에도 열리므로 체험 원가는 9,000원을 조금 넘을 수 있다.

### 6.6 마진 오류를 막는 검증 (구현 때 넣는다)

1. **모델별 하한.** `STUDIO_MODELS`의 모든 모델 × 옵션(해상도·길이·참조 수)에 대해 `usageKrw ≥ billedUsd × krwPerUsd × 1.11`. 고정 차감 항목(업스케일·효과음)은 원가 상수를 코드에 적고 같은 단언에 넣는다.
2. **플랜 크레딧.** 세 플랜 모두 `크레딧 × 10 ÷ 1.11 + 카드 수수료 ≤ 월 이용료 × (1 − 0.10)`. 확정 크레딧의 값: 255,174 ≤ 261,000 / 434,573 ≤ 441,000 / 613,973 ≤ 621,000.
3. **상수 고정.** 환율 1,400, 배수 1.12·1.11, 카드 요율, 플랜 금액, 플랜 크레딧을 한 테스트에 값으로 적는다. 하나라도 바뀌면 "이 문서 §6.3 표를 다시 계산하라"는 메시지와 함께 실패한다.
4. *(B1c로 바뀜 → §5.8)* **일할 속성 테스트.** 임의의 시작일·변경일에 대해 받은 이용료 대비 준 크레딧의 비율이 한 달 전체일 때보다 높지 않다(첫 달, 플랜 올림).
5. **환불 속성 테스트.** 임의의 사용 크레딧·경과 일수에 대해 `남긴 금액 ≥ min(결제한 이용료, 사용 크레딧 × 9.0090)`.
6. **체험·팩.** `체험 크레딧 × 10 ÷ 1.11 ≤ 9,000`, 팩의 크레딧 1개 값 ≥ 플랜의 크레딧 1개 값의 최댓값, 팩의 카드 마진 ≥ 10%.
7. **공개 숫자 일치.** 공개 요금 페이지·`/brand/billing`·DB 플랜 기본값이 같은 상수를 쓴다.
8. **월 원가 점검(필수, 구독을 열기 전에 켠다).** 조직·월별로 `cost_usd` 합계 × 실제 환율과 이용액을 비교해 관리자 화면에 보여 준다. 함께 보는 것: 차감 없이 나간 원가(실패·차단·재시도, 무료 기능), 저장 용량. 조직의 원가가 이용액의 90.1%(= 1 ÷ 1.11)를 넘거나, 전체 마진이 10% 아래로 내려가면 운영 알림을 보낸다. 테스트가 못 잡는 §6.1의 "식에 들어 있지 않은 원가"를 여기서만 볼 수 있다.

## 7. 6개월 선결제 15% 할인 — 계좌이체로만

**결정됨(2026-11-23).** 연 결제는 만들지 않는다. 6개월 치를 한 번에 내면 15%를 할인하고, **선결제는 계좌이체로만 받는다**(카드 자동결제로는 선결제할 수 없다). 세부(고객사 할인과 겹치지 않음, 중도 해지 때 할인 전 값으로 재계산, 크레딧 매달 지급)도 같은 날 제안대로 결정됐다.

| 플랜 | 6개월 정가 | 할인 15% | 공급가액 | 부가세 | 결제 금액 | 월 환산 |
| --- | --- | --- | --- | --- | --- | --- |
| 290,000원 | 1,740,000원 | 261,000원 | 1,479,000원 | 147,900원 | **1,626,900원** | 246,500원 |
| 490,000원 | 2,940,000원 | 441,000원 | 2,499,000원 | 249,900원 | **2,748,900원** | 416,500원 |
| 690,000원 | 4,140,000원 | 621,000원 | 3,519,000원 | 351,900원 | **3,870,900원** | 586,500원 |

- **금액 식**은 지금의 `invoiceAmounts` 그대로다(정가 = 월 이용료 × 6, 할인율 15, 부가세 10%). 청구서 종류에 `prepay`를 더하고 덮는 달 수를 적는다. 그 6개월 동안은 월 청구서를 만들지 않고, `ends_on`은 여섯째 달 말일이다.
- **받는 방법**: 선결제 청구서는 계좌이체만 열린다(회사 계좌 입금 또는 입금 전용 계좌). "지금 카드로 결제"는 이 청구서에 나오지 않는다. 카드 자동결제 고객도 선결제분만 계좌이체로 낸다.
- **시작**: 다음 달 1일부터 6개 달력 월. 이번 달 남은 일수는 보통의 일할 청구서로 따로 낸다.
- **마진**(확정 크레딧, 전량 소진·최고 원가 모델). 플랜 마진이 11~12%인데 15%를 깎으므로, 크레딧을 다 쓰는 선결제 고객에게서는 거의 남지 않는다.

  | 플랜 | 6개월 공급가액 | 6개월 최악 원가 | 수동 입금(수수료 0원) | 입금 전용 계좌(수수료 440원 1회) |
  | --- | --- | --- | --- | --- |
  | 290,000원 | 1,479,000원 | 1,459,459원 | **+19,541원** (월 +3,257원, 1.3%) | **+19,101원** (월 +3,183원, 1.3%) |
  | 490,000원 | 2,499,000원 | 2,486,486원 | **+12,514원** (월 +2,086원, 0.5%) | **+12,074원** (월 +2,012원, 0.5%) |
  | 690,000원 | 3,519,000원 | 3,513,514원 | **+5,486원** (월 +914원, 0.2%) | **+5,046원** (월 +841원, 0.1%) |

  (마진 = 6개월 공급가액 − 수수료 − 월 크레딧 × 10 ÷ 1.11 × 6. 예: 1,479,000 − 0 − 243,243.24 × 6 = 19,541원.) 이 표는 환율 1,400원 기준이다. 실제 환율이 1,419 / 1,407 / 1,402원을 넘으면 다 쓰는 선결제 고객에게서 손실이 난다(§6.3의 환율 갱신 절차와 §6.6-8의 월 원가 점검이 여기서 가장 먼저 걸린다).
- **참고 — 카드로 받았다면**: 6개월에 −41,306 / −90,295 / −139,286원이다(1,479,000 − 올림(1,626,900 × 0.0374) − 1,459,459 = −41,306원). 계좌이체로만 받기로 한 이유다.
- **고객사 할인과 겹치지 않는다 — 결정됨.** 둘 다 이용료를 깎는 것이라 큰 쪽 하나만 적용한다.
- **중도 해지 환불 — 결정됨**: `환불액 = 선결제 공급가액 − (이용한 달 수 × 정가 월 이용료) − 진행 중인 달의 일할 이용액(정가 기준)`, 0원 미만이면 0원. 쓴 기간은 할인 전 값으로 다시 계산한다는 뜻이다.

  | 해지 시점 | 290,000원 | 490,000원 | 690,000원 |
  | --- | --- | --- | --- |
  | 1개월 뒤 | 1,189,000원 | 2,009,000원 | 2,829,000원 |
  | 3개월 뒤 | 609,000원 | 1,029,000원 | 1,449,000원 |
  | 5개월 뒤 | 29,000원 | 49,000원 | 69,000원 |

  (공급가액 기준, 부가세는 같은 비율로 돌려준다.) 할인을 되돌리는 방식이 약관규제법 제9조(원상회복 의무의 과중 부담)와 토스 계약의 "이용 일수 비례"에 맞는지는 법무 확인이 필요하다.
- **크레딧은 매달 지급 — 결정됨.** 6개월 치를 한 번에 주지 않는다(§6.4).
- **선결제 중 플랜 변경**: 올림은 즉시, 남은 기간의 차액을 15% 할인된 값으로 일할해 추가 청구(계좌이체). 내림은 6개월이 끝난 뒤부터.
- **끝난 뒤**: 자동으로 다시 6개월을 청구하지 않는다. 끝나기 30일 전에 알리고, 답이 없으면 월 결제(그 조직의 받는 방법)로 이어진다.
- **세금계산서**: 받은 날 전액으로 한 장(§2.4). 신고 시기는 세무 대리인 확인.
- **정산한도**: 회사 계좌로 직접 받으면 한도와 무관하다. 입금 전용 계좌(가상계좌)로 받으면 단건 MID의 월 1,000만 원 한도에 들어가고, 290,000원 플랜 6건, 490,000원 3건, 690,000원 2건이면 찬다. 그래서 선결제는 가상계좌 자동 확인을 켠 뒤에도 회사 계좌 입금을 기본으로 둔다(제안).

## 8. 세금계산서 — 홈택스 수기 (대표 결정)

1. 계좌이체 청구서가 발행되면 관리자 화면의 "이번 달 발행할 것" 목록에 올라온다. 공급가액·세액·고객사 세금계산서 정보(상호, 사업자등록번호, 대표자, 주소, 수신 메일)를 그대로 보여 준다.
2. 관리자가 홈택스에서 전자세금계산서를 발행하고, 발행일과 승인번호를 그 청구서에 적는다. 적기 전까지 목록에 남는다.
3. 고객의 `/brand/billing`에는 "세금계산서 발행됨(발행일)"만 보인다. 세금계산서 자체는 국세청이 고객 메일로 보낸다.
4. 환불·금액 정정이 생기면 확인 필요 큐에 "수정 세금계산서 필요"로 올린다.
5. 카드로 결제한 청구서는 이 목록에 올라오지 않는다(매출전표가 증빙). "이번 청구서만 계좌이체"로 바꿔 낸 건은 올라온다.

작성일을 발행일로 할지 입금일로 할지는 세무 대리인 확인 뒤 정한다(§15.2-3). 한 달 발행 건수가 손으로 하기 어려워지면 발행 대행 API를 붙인다. 그때도 2번의 기록 칸은 그대로 쓴다.

## 9. 스키마 초안

번호는 구현 시작 때 `origin/main`에서 다시 확인한다(지금 다음 빈 번호 0182, 0174·0175는 다른 브랜치 예약). 전부 RLS deny-all, service role만 쓴다(0177과 같은 방식).

```sql
-- NNNN_core_brand_subscriptions.sql (초안)
create table brand_subscriptions (
  organization_id uuid primary key references organizations(id),
  environment text not null check (environment in ('test','live')),
  status text not null check (status in ('pending','active','past_due','suspended','ended')),
  plan_id text not null,                     -- b2b_29 | b2b_49 | b2b_69
  pending_plan_id text,                      -- 다음 달부터 적용할 플랜(내림)
  collection_method text not null check (collection_method in ('transfer','card')),
  prepaid_through date,                      -- 6개월 선결제가 덮는 마지막 날
  cancel_at_period_end boolean not null default false,
  canceled_at timestamptz, ended_at timestamptz,
  terms_version text not null, autopay_terms_version text,
  consented_by uuid not null, consented_at timestamptz not null,
  revision integer not null default 0,
  created_at timestamptz not null default now(), updated_at timestamptz not null default now()
);

create table brand_payment_methods (        -- 카드 빌링키. 조직·환경당 활성 1개
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null, environment text not null,
  customer_key text not null unique,         -- 무작위 값. 조직 id를 쓰지 않는다
  billing_key_cipher text not null,
  card_company text, card_last4 text, owner_type text,
  status text not null check (status in ('active','replaced','revoked')),
  registered_by uuid not null, created_at timestamptz not null default now()
);
create unique index brand_payment_methods_one_active
  on brand_payment_methods (organization_id, environment) where status = 'active';

alter table brand_invoices
  add column kind text not null default 'subscription'
    check (kind in ('subscription','adjustment','prepay','credit_pack')),
  add column covers_months integer not null default 1,
  add column due_on date,
  add column collection_method text check (collection_method in ('transfer','card')),
  add column tax_invoice_issued_on date, add column tax_invoice_ref text,
  add column refunded_krw integer not null default 0;
-- status에 'refunded' 추가. 조직·월 유니크 인덱스는 kind = 'subscription'에만 걸리도록 다시 만든다.

create table brand_invoice_payments (       -- 시도 1건 = 토스 주문 1건 (id가 orderId)
  id uuid primary key default gen_random_uuid(),
  invoice_id uuid not null references brand_invoices(id),
  organization_id uuid not null, environment text not null,
  method text not null check (method in ('card','virtual_account','manual')),
  status text not null check (status in
    ('pending','charging','waiting_deposit','done','failed','expired','canceled','refunded','review')),
  amount_krw integer not null,               -- 청구서 total_krw와 같아야 한다
  attempt_no integer not null,
  scheduled boolean not null default true,   -- 일정에 따른 자동 시도인지(§5.5)
  payment_key text, failure_code text, failure_class text, receipt_url text,
  va_bank text, va_account_number text, va_due_at timestamptz, va_secret_hash text,
  lease_until timestamptz, refunded_krw integer not null default 0,
  created_at timestamptz not null default now(), settled_at timestamptz
);
create unique index brand_invoice_payments_one_done
  on brand_invoice_payments (invoice_id) where status = 'done';
create unique index brand_invoice_payments_one_open
  on brand_invoice_payments (invoice_id) where status in ('pending','charging','waiting_deposit');

alter table brand_allowance_grants           -- 체험·팩·올림 크레딧(§6.4, §6.5)
  add column kind text not null default 'extra' check (kind in ('extra','trial','pack','upgrade')),
  add column carried_from uuid references brand_allowance_grants(id);
create unique index brand_allowance_grants_one_trial
  on brand_allowance_grants (organization_id) where kind = 'trial' and carried_from is null;

create table brand_subscription_events (    -- 감사 기록(누가·언제·무엇을, 스냅샷 jsonb)
  id bigint generated always as identity primary key,
  organization_id uuid not null, action text not null, actor uuid,
  snapshot jsonb not null, created_at timestamptz not null default now()

```

워크스페이스 승인 기록(승인한 사람·시각)을 어디에 둘지는 구현 때 `organizations` 스키마를 보고 정한다. 고정식 가상계좌를 쓰게 되면 `brand_subscriptions`에 `account_key`(무작위 12자 이내)를 더한다. 사업자등록번호와 환불 계좌는 이 테이블들에 넣지 않는다.

### 10.2 월 정산한도 1,000만 원이 뜻하는 숫자

정기결제 MID 기준(개인 구독 매출과 합산), 카드 자동결제 고객사만 셌을 때:

| 플랜 | 월 결제(실결제) | 카드로 들어가는 고객사 수 | 6개월 선결제 금액 | 가상계좌로 받을 때 한 달 건수(단건 MID) |
| --- | --- | --- | --- | --- |
| 290,000원 | 319,000원 | 31곳 | 1,626,900원 | 6건 |
| 490,000원 | 539,000원 | 18곳 | 2,748,900원 | 3건 |
| 690,000원 | 759,000원 | 13곳 | 3,870,900원 | 2건 |

가상계좌는 단건 MID의 한도(개인 템플릿 결제와 합산)에 들어간다. 회사 계좌로 직접 받는 수동 입금은 한도와 무관하다. 계좌이체가 기본이므로 한도에 먼저 닿는 것은 가상계좌 자동 확인을 켠 뒤다. 한도 상향 문의는 보류 중이다.

## 13. 형식 검증 (AGENTS.md §11)

결제 상태 전이와 크레딧이라 대상이다. TLA+/TLC 모델 두 개와 Lean(또는 속성 테스트) 하나를 만든다.

1. **청구서 × 결제 시도.** 사건: 발행, 카드 승인 성공·실패·응답 유실, 사유별 재시도, 가상계좌 발급·입금·만료·취소·되돌림, 웹훅 중복·지연·순서 뒤바뀜, 받는 방법 전환, 수동 입금 확인, 환불. 불변 조건: 청구서가 `paid`이면 `done` 시도가 정확히 1건이고 금액이 같다 / `done`이 2건이 되는 경로가 없다 / `paid`·`void`·`refunded` 청구서에 새 승인이 나가지 않는다 / 응답을 모르는 시도가 있는 동안 새 시도가 생기지 않는다 / 할인 회차 사용 수 = 취소되지 않은 발행 청구서 수.
2. **이용 가능 기한.** 불변 조건: 새 생성이 닫히는 것은 가장 오래된 미납 청구서의 "납기 + 유예"가 지났을 때뿐이다 / 결제가 확인되면 다음 판정에서 반드시 열린다 / 해지 예약은 결제된 기간을 줄이지 않는다 / 우리 쪽 설정 오류로 실패한 결제는 유예를 흐르게 하지 않는다.
3. **크레딧 산술**(§6.6의 2·4·5·6). 일할·올림·환불·팩에서 "받은 돈 ≥ 준 크레딧의 최악 원가 ÷ (1 − 목표 마진)"이 유지되는지. 정수 내림이 섞여 있어 손으로 확인하기 어렵다.

규칙은 이 문서 §5·§6과 토스 계약 제42조에서 정의한다. 일부러 틀린 조건(예: 전환 때 가상계좌를 취소하지 않음, 첫 달 크레딧을 일할하지 않음)을 넣어 반례가 나오는지 확인한다. 이 PC에는 TLC·Lean이 설치되어 있지 않다. 설치 전에는 "미실행"으로 보고하고, 같은 불변 조건을 vitest 속성 테스트로 먼저 건다.

## 17. 확인하지 못한 것

- §16의 일곱 가지(토스 회신 전).
- **Higgsfield의 플랜 가격, 플랜별 크레딧 수, 모델별 차감표, 팩 가격.** 요금 페이지가 스크립트로 그려져 읽지 못했다. 구조(이월 없음, 팩 90일, 차감 순서, 플랜 변경)는 공개 도움말에서 확인했다. 다른 사이트의 숫자로 채우지 않았다.
- **토스 에러 코드의 재시도 가능 분류.** 토스의 공식 분류가 없어 메시지를 보고 나눴다. 타임아웃 뒤 주문을 조회하라는 명시 문구도 찾지 못했다(조회 API와 멱등 키 동작은 문서에 있다).
- **실제 환율과 제공사 실제 청구액.** 마진표는 코드 상수(1,400원, 정가의 센트 올림)로 계산했다. 운영 DB의 `cost_usd`와 대조하지 않았다.
- **식에 없는 원가의 크기**(§6.1): 실패·재시도, 크레딧을 받지 않는 기능, 로컬 GPU, 저장 용량. 숫자를 재지 않았다. 마진이 10~12%라서 이 원가가 크면 실제 마진은 표보다 낮거나 음수일 수 있다. 월 원가 점검(§6.6-8)을 켜기 전에는 알 수 없다.
- 부가가치세법 시행령에서 "세금계산서를 발급하지 않는 사업자"의 범위를 정한 조문과, 선납 계속 용역의 신고 시기(시행령 제29조 ② 3호 해당 여부). 세무 대리인 확인 대상이다.
