## 0. 추천안

1. **돈의 단위는 청구서 하나로 통일한다.** 이미 운영 중인 `brand_invoices`(정가 − 할인 + 부가세)를 그대로 쓰고, 고객사마다 **받는 방법**만 고른다. 기본은 계좌이체("청구서에 적힌 계좌로 기한 안에 입금"), 선택지는 카드 자동결제("청구서가 발행되는 날 등록 카드로 결제")다. 할인·일할·부가세 계산은 한 곳(`invoiceAmounts`)에서만 일어난다.
2. **계좌이체는 세 단계로 자동화한다.** ① 관리자가 입금을 확인(오늘 가능) → ② 청구서마다 가상계좌를 발급하고 입금 웹훅으로 자동 확인 → ③ 고객사마다 같은 계좌번호(고정식 가상계좌). ②와 ③은 토스 계약이 필요하고, 계약이 안 되거나 장애가 나면 ①로 떨어진다. 법인계좌에서 매달 자동으로 빼 가는 방식은 토스에 없다(§2.2).
3. **증빙은 수단에 따라 하나만.** 카드는 카드 매출전표, 계좌이체는 세금계산서(홈택스 수기 발행). 한 거래에 둘을 같이 내지 않는다(§2.4).
4. **크레딧은 차감표를 건드리지 않고 플랜의 크레딧 수로 마진을 잡는다.** 마진 기준은 10~12%이고 월 27,000 / 46,000 / 65,000 크레딧으로 확정됐다(§6, 대표 결정 2026-11-23). 다 쓰고, 가장 비싼 모델만 쓰고, 카드로 내도 11~12%가 남는다. 고객사 할인은 이 계산에 넣지 않고 영업 비용으로 따로 본다.

이용 차단은 새 상태를 만들지 않고 지금 있는 규칙(`planActiveWithGrace` → `loadAllowance`)을 그대로 쓴다. 구독 엔진은 플랜의 `ends_on`만 움직인다(§5.3).

## 2. 조사 결과 (2026-11-23, 공식 문서)

### 2.1 카드 자동결제

- 자동결제는 "리스크 검토 및 추가 계약 후" 쓸 수 있고, 정기 구독형이 아니면 제한된다. 결제 주기 실행은 상점이 직접 한다. [자동결제 이해하기](https://docs.tosspayments.com/guides/v2/billing), [연동](https://docs.tosspayments.com/guides/v2/billing/integration)
- 수단은 국내 발급 신용·체크카드와 퀵계좌이체(개인 계좌). 카카오페이는 안 된다.
- 법인카드: 빌링키 발급 API가 사업자등록번호 10자리를 받고 응답에 `ownerType: 법인`이 있다. 등록창(`requestBillingAuth`)에서 법인카드, 특히 무기명 카드를 등록할 수 있는지는 **토스 확인 필요**. [API 연동](https://docs.tosspayments.com/guides/v2/billing/integration-api)
- 승인은 최대 60초가 걸린다(타임아웃 60초 이상). 모든 POST에 `Idempotency-Key`를 쓸 수 있고 15일간 유효하다. 처리 중 재요청은 409 `IDEMPOTENT_REQUEST_PROCESSING`. 주문 조회는 `GET /v1/payments/orders/{orderId}`. [멱등키](https://docs.tosspayments.com/reference/using-api/idempotency-key), [API](https://docs.tosspayments.com/reference)
- **토스 이용계약 제42조가 상점에 요구하는 것.** [전자결제서비스 이용계약](https://pages.tosspayments.com/terms/onboarding/)
  - 가입 약관과 **따로** 자동결제 약관을 알리고 사전 동의를 받는다.
  - 금액이 바뀌거나 유료로 전환될 때는 **결제 7일 전까지** 금액·결제일·환불 조건·해지 방법을 알린다.
  - **영업시간 밖에도** 해지를 신청할 수 있어야 한다.
  - 환불은 이용 일수·회차에 비례해야 하고, 자체 포인트로만 돌려주는 것은 안 된다.
- 자동결제 심사가 화면에서 보는 항목의 공식 체크리스트는 찾지 못했다(**토스 확인 필요**).

### 2.2 계좌 기반 수단

| 수단 | 정기 과금에 쓸 수 있나 | 근거 |
| --- | --- | --- |
| **가상계좌**(청구서마다 발급) | 된다. 고객이 매달 입금하고 웹훅으로 자동 확인 | 발급 `POST /v1/virtual-accounts`, 유효기간 최대 90일, 입금 시 `DEPOSIT_CALLBACK`. [웹훅](https://docs.tosspayments.com/reference/using-api/webhook-events), [용어](https://docs.tosspayments.com/resources/glossary/virtual-account) |
| **고정식 가상계좌**(고객사마다 같은 번호) | 된다. `accountKey`가 같으면 같은 계좌번호. 그래도 청구마다 발급 요청은 필요 | "리스크 검토 및 추가 계약 필요". 수수료·지원 은행은 **토스 확인 필요** |
| 계좌이체(퀵계좌이체·뱅크페이) | **법인계좌는 안 된다.** 자동결제는 개인 계좌만, 법인계좌(뱅크페이)는 매번 결제창 인증 | "뱅크페이(법인계좌)는 자동결제를 지원하지 않아요." [계좌이체](https://docs.tosspayments.com/resources/glossary/transfer-payment) |
| 출금 동의 자동이체(CMS) | 토스 상품으로 확인되지 않는다 | 제공 여부 **토스 확인 필요** |

가상계좌에서 알아 둘 것:

- 입금액은 주문 금액과 정확히 같아야 하고 나눠 낼 수 없다. 다른 금액이 은행 단계에서 거절되는지는 **토스 확인 필요**. [가상계좌 안내](https://www.tosspayments.com/blog/articles/30637)
- 입금 기한이 지나도 웹훅이 오지 않는다. 만료는 우리 쪽 작업이 처리한다. [가상계좌 웹훅](https://docs.tosspayments.com/blog/virtual-account-webhook)
- 입금 완료가 은행 사정으로 **되돌아갈 수 있다**(`DONE → WAITING_FOR_DEPOSIT`). "2분 지연 통보" 옵션이 있다(신청 방법 **토스 확인 필요**).
- 웹훅은 10초 안에 200을 받아야 하고, 실패하면 최대 7회 다시 온다. 본문의 `secret`을 발급 때 받은 값과 비교한다. [웹훅 가이드](https://docs.tosspayments.com/guides/v2/webhook)
- 입금 뒤 환불은 환불 계좌(`refundReceiveAccount`)가 필요하다. [결제 취소](https://docs.tosspayments.com/guides/v2/cancel-payment)

### 2.4 증빙

- 카드로 결제하면 카드 매출전표가 증빙이고, 세금계산서를 또 내면 이중 발급이다(부가가치세법 제33조 ②, [국세청 상담 사례](https://call.nts.go.kr/call/qna/selectQnaInfo.do?mi=1329&ctgId=CTG11945)).
- 토스는 상점의 고객에게 세금계산서를 발행해 주지 않는다. **우리가 홈택스에서 수기로 낸다**(대표 결정). 발행 대행(팝빌·바로빌)은 건수가 늘면 붙인다.
- 가상계좌·계좌이체는 토스가 현금영수증을 자동 발급한다. 세금계산서를 내는 건은 발급 요청에서 현금영수증을 `미발행`으로 지정한다(요청 단위 지정이 문서에 있다, **토스 재확인**). [현금영수증](https://docs.tosspayments.com/resources/glossary/cash-receipt)
- 대가를 먼저 받고 그 금액으로 세금계산서를 내면 발급한 때가 공급시기다(부가가치세법 제17조 ①). 6개월 선결제분을 받은 날 한 장으로 낼 수 있는 근거다. 선납 계속 용역의 신고 시기(시행령 제29조 ② 3호의 "유사한 용역" 해당 여부)는 **세무 대리인 확인**.

### 2.5 참고한 구조

**Stripe Billing.** [수금 방식](https://docs.stripe.com/billing/collection-method), [은행 송금](https://docs.stripe.com/invoicing/bank-transfer), [재시도](https://docs.stripe.com/billing/revenue-recovery/smart-retries), [실패 메일](https://docs.stripe.com/billing/revenue-recovery/customer-emails), [거절 코드](https://docs.stripe.com/declines/codes)

- 구독은 청구서를 만들고, 고객마다 자동 청구 또는 청구서 + 납기를 고른다. → §0-1
- 고객마다 변하지 않는 입금 계좌 번호와 자동 대사. → 고정식 가상계좌
- 재시도 기본값은 2주 안에 최대 8회, 직접 정하면 최대 3회. 분실·도난·승인 철회 같은 거절은 새 결제 수단이 등록될 때까지 실제로 재시도하지 않는다. 실패할 때마다 결제 수단 변경 링크가 든 메일을 보낸다. → §5.5
- 다른 사례: Recurly는 월 구독의 독촉 기간을 27일 이내로 권하고, 카드사·게이트웨이 오류는 2~3일 간격으로 다시 시도한다. Chargebee는 직접 정하는 재시도를 최대 5회로 둔다. [Recurly](https://docs.recurly.com/docs/dunning-management), [Chargebee](https://www.chargebee.com/docs/payments/2.0/dunning/dunning-v2)

**Higgsfield 크레딧 구조**(공개 도움말만 읽었다. 요금 페이지는 스크립트로 그려져 플랜 가격·플랜별 크레딧 수·모델별 차감표는 **미확인**이다). [크레딧](https://higgsfield.ai/creator-hub/help-center/credits/how-credits-work), [만료](https://higgsfield.ai/creator-hub/help-center/credits/top-up-credits-expire), [크레딧 팩](https://higgsfield.ai/creator-hub/help-center/credits/how-credit-packs-work), [플랜 변경](https://higgsfield.ai/creator-hub/help-center/plans/how-do-i-upgrade-or-downgrade-my-plan), [팀·비즈니스](https://higgsfield.ai/creator-hub/help-center/business/team-and-business-higgsfield)

- 구독 크레딧은 결제 주기마다 새로 채워지고 **이월되지 않는다**. 연간 플랜도 30일마다 새로 채운다.
- 추가 크레딧 팩은 구독 중인 계정만 살 수 있고 구매 후 90일 유효, 자동 갱신 없음.
- 구독 크레딧을 먼저 쓰고, 그다음 만료가 가까운 것부터 쓴다.
- 차감량은 모델·해상도·길이로 정해지고 생성 버튼에 미리 표시된다. 실패한 생성은 돌려준다.
- 올리면 즉시 적용, 내리면 다음 주기부터. 해지하면 구독 크레딧은 기간 끝에 사라진다.
- 비즈니스 플랜은 좌석별 크레딧이 워크스페이스 공용으로 합쳐진다.

우리 구조는 이미 이 모양이다(월 한도, 모델별 차감, 버튼에 미리 표시, 실패 시 미차감, 이월 없음). 빠진 것은 플랜별 크레딧 수, 추가 팩, 차감 순서다(§6).

## 3. 구조

```
brand_subscriptions (조직당 1행: 플랜, 받는 방법, 상태, 해지 예약)
        │  매달: D-7 초안 + 예정 안내 → 1일 발행
        ▼
brand_invoices (지금 있는 장부. 금액은 invoiceAmounts)
        │  청구서 하나에 결제 시도 여러 번
        ▼
brand_invoice_payments (시도 1건 = 토스 주문 1건: 카드 승인 / 가상계좌 / 수동 입금)
        │  done 1건 → 청구서 paid → 플랜 ends_on = 그 달 말일
        ▼
brand_plan_assignments.ends_on  →  planActiveWithGrace  →  loadAllowance (지금 그대로)
```

- **주기는 달력 월**이다. 지금 장부가 `period = YYYY-MM`, 조직·월당 1장이고 첫 달 일할(`proposeProration`)이 있다. 매달 1일(KST) 그 달 이용료를 선불로 청구한다.
- **승인제.** 워크스페이스는 관리자가 승인해야 열린다(대표 결정). 승인할 때 체험 크레딧을 한 번 준다(§6.5). 구독 신청은 승인된 조직만 할 수 있다.
- **플랜 변경**: 올릴 때는 바로 적용하고 남은 일수의 차액을 추가 청구서로 낸다. 크레딧도 같은 비율로만 더 준다(§6.4). 내릴 때는 다음 달부터 적용하고 환불하지 않는다.
- 구독 행이 없는 조직(관리자가 손으로 플랜을 넣은 고객, 프로젝트 전용, 샌드박스)은 지금과 똑같이 동작한다.

## 4. 화면

### 4.1 고객 — `/brand/billing` (소유자·관리자만)

1. **플랜 선택.** 카드 3장: 월 290,000 / 490,000 / 690,000원 "(부가세 별도)", 월 크레딧, 그 아래 실제 결제 금액과 결제일("매월 1일, 첫 달은 남은 일수만큼"). 할인이 있으면 할인 후 금액과 남은 회차를 같이 보여 준다. 할인 코드는 여기서 먼저 넣는다.
2. **받는 방법 선택.** 계좌이체가 먼저 선택되어 있다: "계좌이체 — 매달 청구서의 계좌로 입금, 세금계산서". 다른 칸: "카드 자동결제 — 매달 1일 등록 카드로 결제, 카드 매출전표". 계좌이체는 세금계산서 정보(이미 있는 폼)가 필수다.
3. **동의.** B2B 이용약관과 **별도 칸**의 자동결제 동의(카드만). 금액·결제일·해지 방법·환불 기준을 동의 칸 바로 위에 적는다.
4. **카드 등록 또는 입금 안내.**
   - 계좌이체: 첫 청구서와 입금 계좌·금액·기한(발행일 + 14일)을 보여 주고 메일로도 보낸다. 입금이 확인되면 플랜 크레딧이 열린다. 계약서로 먼저 시작한 고객은 관리자가 먼저 열어 줄 수 있다.
   - 카드: 토스 등록창 → 돌아오면 첫 청구서를 바로 결제 → 활성.
5. **이후 같은 화면에서**: 다음 결제 예정(날짜·금액), 청구 내역과 증빙(세금계산서 발행 여부 / 매출전표 링크), 미납 청구서의 "입금 계좌 보기"·"지금 카드로 결제", 결제 수단 변경, 카드 교체, 플랜 변경, 추가 크레딧, **해지**(확인 한 번, "○월 ○일까지 이용" 표시, 해지 취소 가능).

메일(문안은 대표 확정 뒤): 결제 예정 안내(D-7), 청구서 발행, 결제 완료, 카드 결제 실패(§5.5), 입금 기한 3일 전·당일·경과, 생성 중단 예정·중단, 해지 접수.

화면 문구에는 내부 용어(MID, 빌링키, 웹훅, 가상계좌 발급 상태 이름)를 쓰지 않는다. 고객에게는 "입금 전용 계좌"라고 부른다. 이 화면은 PC 기준으로만 만든다.

### 4.2 공개 요금 페이지 (대표 결정: 로그인 뒤 화면과 공개 페이지 둘 다)

- **위치**: `twings.app/{locale}/brands/pricing` — `app/(marketing)/[locale]/brands/pricing/page.tsx`. brand.twings.app은 로그인 전용이고 검색이 차단되어 있어서, 공개 페이지는 브랜드 랜딩과 같은 마케팅 쪽에 둔다(정적 + 캐시 태그 + 1시간, AGENTS.md §4). 브랜드 랜딩과 `/brand/billing`에서 서로 연결한다.
- **담을 것**: 플랜 3개(월 이용료 "부가세 별도"와 부가세 포함 결제 금액, 월 크레딧, 그 크레딧으로 만들 수 있는 양의 예, 저장 용량), 결제 주기(매월 1일, 첫 달 일할), 결제 수단(계좌이체·세금계산서 / 카드 자동결제), 6개월 선결제(확정되면), 추가 크레딧, 시작 방법(신청 → 승인 → 체험 크레딧), **해지 방법과 환불 기준 요약**, 약관 링크, 자주 묻는 질문, 문의.

- **SEO·GEO**(AGENTS.md §7): `Product` + 플랜별 `Offer`(원화, `UnitPriceSpecification`에 월 단위와 `valueAddedTaxIncluded: false`), `FAQPage`, ko/en `alternates`, 사이트맵, 첫 화면 아래 정의형 문단 하나와 답변형 제목("얼마인가요", "어떻게 해지하나요", "세금계산서는 어떻게 받나요"). 본문은 HTML에 실제로 있어야 한다. 스윕 마커 `data-brand-pricing`, `data-brand-plan`.
- **심사**: 로그인 없이 상품·금액·주기·해지·환불 안내를 볼 수 있는 주소가 생긴다. 토스에 서비스 주소로 이 페이지를 안내한다.
- **하지 않는 것**: 샌드박스 고객의 영상·이름, 개인 쪽 실적 숫자를 B2B 예시로 쓰지 않는다. 아직 없는 기능은 "얼리 액세스"로 표시한다. `docs/BRAND-ENGINE.md` §7-5의 "정하기 전 가격 노출 금지"는 이 결정으로 풀리므로 구현 PR에서 그 문서를 같이 고친다.
- 문구는 Gemma 2패스 → 대표 확정. 가격·크레딧 숫자·환불 기준은 §15.2가 확정된 뒤에만 올린다.

## 5. 상태와 실패 처리

### 5.1 상태

구독(`brand_subscriptions.status`):

```
pending ──첫 청구서 결제──▶ active ──미납(기한 경과)──▶ past_due ──유예 경과──▶ suspended
                              ▲                            │                      │
                              └──────────── 결제 확인 ─────┴──────────────────────┘
active / past_due / suspended ──해지 예약(cancel_at_period_end)·기간 종료──▶ ended
```

청구서는 지금 전이에 둘을 더한다: `paid → issued`(입금 되돌림 전용, 사유 기록)와 `paid → refunded`(전액 환불). 부분 환불은 청구서를 `paid`로 두고 환불 금액을 따로 기록한다.

결제 시도(`brand_invoice_payments.status`): `pending → charging → done | failed`(카드), `pending → waiting_deposit → done | expired | canceled`(가상계좌), `done → refunded`, 그리고 사람이 봐야 하는 `review`.

### 5.2 매달 일정

입금 기한 14일과 유예 14일은 대표 결정이다. D0은 발행일(매월 1일)이다.

| 날 | 계좌이체(기본) | 카드 자동결제 |
| --- | --- | --- |
| D-7 (전달 24~25일) | 다음 달 청구서 초안 + 청구 예정 안내(금액, 지난달과 다르면 이유) | 같은 초안 + **결제 예정 안내** |
| D0 (1일) | 발행 → 입금 계좌 안내. 납기 = D+14(15일) | 발행 → 등록 카드 결제 → `paid`. 납기 = D0 |
| 납기 전후 | D+11·D+14·D+15에 안내 메일 | 실패하면 §5.5의 재시도 |
| 유예 | D+15 ~ D+28 (`past_due`) | D+1 ~ D+14 (`past_due`) |
| 새 생성 중단 | D+29부터 (`suspended`). 보기·내려받기·룸은 그대로 | D+15부터. 같다 |
| 결제 확인 | 즉시 `active`, 그 달 말일까지 | 같다 |

- D-7 안내는 토스 계약 제42조(금액 변경 7일 전 고지)를 매달 지키는 가장 단순한 방법이다. 할인이 끝나는 달, 플랜이 바뀌는 달에도 따로 챙길 것이 없다.
- `suspended`인 동안에는 다음 달 청구서를 만들지 않는다. 밀린 청구서를 내면 그날부터 남은 일수만 일할로 이어 간다. 60일 넘게 `suspended`면 확인 필요 큐에 올린다(해지 여부는 사람이 정한다).
- `BRAND_PLAN_GRACE_DAYS`의 값을 14로 바꾸는 것은 구현 때 한다. 이 값은 손으로 관리하는 조직의 유예에도 똑같이 적용된다.

### 5.3 차단은 `ends_on` 하나로

`planActiveWithGrace(plan, 오늘, 유예일수)`가 이미 "`ends_on` + 유예일까지 유효"를 판정하고, `loadAllowance`가 그 결과로 한도를 정한다. 구독 엔진은 구독이 있는 조직의 `ends_on`만 쓴다.

- 청구서가 `paid`가 되면 `ends_on = 그 달 말일`.
- 미납 청구서가 있으면 `ends_on = 가장 오래된 미납 청구서의 납기일`. 그래서 "납기 + 유예"까지 이용이 이어진다. 카드의 납기일은 발행일이다.
- 그 뒤에도 미납이면 지금 규칙대로 한도가 기본값으로 떨어져 새 생성이 닫힌다.

검사 지점이 늘지 않고, 수동으로 관리하는 조직의 동작도 바뀌지 않는다. `docs/BRAND-PRODUCT.md` §6.4의 "연체는 스튜디오를 막지 않는다"는 수동 청구 기준이고, 구독 조직은 위 규칙을 따른다(대표 결정).

### 5.4 경우별 처리

| 경우 | 처리 |
| --- | --- |
| 카드 승인 실패 | 청구서는 `issued`로 남는다(취소하지 않으므로 할인 회차가 두 번 줄지 않는다). 시도 행만 `failed`. 재시도마다 새 시도 행 = 새 주문번호. 일정은 §5.5 |
| 입금 기한 경과 | 가상계좌 유효기간을 "납기 + 유예"(발급일 + 28일)로 잡아 유예 중에도 입금된다. 만료는 우리 작업이 처리하고, 고객이 "입금 계좌 보기"를 누르면 새로 발급한다 |
| 부분 입금·초과 입금 | 가상계좌는 금액이 맞아야 입금된다(은행 단계 거절 여부 토스 확인 필요). 수동 입금에서 금액이 다르면 `paid`로 바꾸지 않고 확인 필요 큐로 보낸다. 잔액으로 쌓지 않는다 |
| 중복 결제·중복 입금 | 청구서당 `done` 시도는 1건만(부분 유니크 인덱스). 받는 방법을 바꾸거나 "지금 카드로 결제"를 누르면 열려 있는 가상계좌를 먼저 취소한 뒤 승인한다. 그래도 이미 `paid`인 청구서에 돈이 들어오면 자동으로 다음 달에 충당하지 않고 확인 필요 큐 → 환불 |
| 입금 되돌림(`DONE → WAITING_FOR_DEPOSIT`) | 청구서 `paid → issued`, `ends_on`을 납기일로 되돌리고 고객·관리자에게 알린다. 지연 통보 옵션을 쓸 수 있으면 켠다 |
| 웹훅 지연·중복·순서 뒤바뀜 | 웹훅 본문은 힌트로만 쓰고 토스에서 결제를 다시 조회해 상태를 정한다(지금 단건 웹훅과 같은 방식). `secret` 비교, 모든 전이는 조건부 UPDATE라 같은 웹훅이 여러 번 와도 결과가 같다. 웹훅이 끝내 안 오면 주기 작업이 `waiting_deposit` 건을 조회한다 |
| 결제 수단 변경 | 다음 청구서부터 적용. 열려 있는 청구서는 위 "중복" 규칙으로 한 경로만 살린다. 계좌이체 → 카드는 카드 등록과 자동결제 동의가 끝나야 바뀐다 |
| 카드 교체 | 새 빌링키 저장 후 이전 키는 폐기 대기열로(개인 구독의 `key_cleanup` 방식). 미납 청구서가 있으면 바로 재결제 |
| 해지 | `cancel_at_period_end`. 결제된 기간 끝까지 이용, 다음 청구서를 만들지 않는다. 기간이 끝나면 빌링키 폐기. 결제한 적이 없으면 바로 종료 |
| 플랜 올림 | 즉시 적용 + 차액 일할 추가 청구서. 추가 크레딧도 같은 비율(§6.4) |
| 플랜 내림 | 다음 달 청구서부터 |
| 환불 | 식은 §6.4. 카드는 승인 취소(부분 취소 가능), 가상계좌는 환불 계좌를 받아 취소. 환불 계좌는 저장하지 않고 토스로 넘기기만 한다. 세금계산서가 나간 건은 수정 세금계산서를 홈택스에서 낸다(관리자 체크 항목) |
| 할인 | 발행 때 1회 차감, 청구서 취소 때 복원 — 지금 그대로이고 두 수단에 똑같이 적용된다. 6개월 선결제 할인과는 겹치지 않는다(§7) |

### 5.5 카드 결제 실패 재시도

**일정: D0 결제 뒤 D+2, D+5, D+9, D+13에 다시 시도한다(자동 5회, 오전 10시 KST). D+15에 새 생성이 닫힌다.**

- 14일 유예 안에 끝나도록 잡았다. Stripe 기본값(2주 안에 최대 8회)보다 적고 직접 설정 상한(3회 재시도)보다 하나 많다. 간격을 점점 넓힌 것은 한도가 다시 차거나 담당자가 조치할 시간을 주기 위해서다. 같은 카드에 거절이 쌓이면 카드사가 가맹점을 나쁘게 볼 수 있어 매일 시도하지 않는다.
- 고객이 카드를 바꾸거나 "지금 결제"를 누르면 일정과 상관없이 바로 시도한다(같은 청구서에 하루 3회까지).
- 마지막 자동 시도(D+13)가 실패해도 유예 끝(D+14)까지 고객이 직접 결제하거나 **이번 청구서만 계좌이체로** 낼 수 있다. 실패 메일마다 두 길을 다 적는다.

**실패 사유별 분기.** 코드는 토스 [에러 코드](https://docs.tosspayments.com/reference/error-codes)의 "카드 자동결제 승인" 절에 있는 것이다. 분류는 메시지를 보고 우리가 한 것이고 토스의 공식 분류가 아니다.

| 분류 | 토스 코드 | 처리 |
| --- | --- | --- |
| 일시 오류 | `FAILED_INTERNAL_SYSTEM_PROCESSING`, `FAILED_CARD_COMPANY_RESPONSE`, 응답 없음 | 먼저 같은 주문을 조회한다. 결제되지 않았으면 1시간 뒤와 그다음 날 다시 시도하고, 일정의 5회에 넣지 않는다. 고객 메일 없음 |
| 한도·잔액 | `REJECT_CARD_PAYMENT`(한도 초과 또는 잔액 부족), `REJECT_ACCOUNT_PAYMENT` | 일정대로 재시도. 첫 실패 때 바로 메일: 한도를 확인하거나 카드를 바꾸거나 계좌이체로 내 달라고 안내. 토스가 한도와 잔액을 한 코드로 주기 때문에 둘을 나눠 처리할 수 없다 |
| 사유를 알 수 없는 거절 | `REJECT_CARD_COMPANY` | 일정대로 재시도하되 D+5까지 같은 사유면 자동 재시도를 멈추고 카드 교체를 요청 |
| 카드를 바꿔야 함 | `INVALID_STOPPED_CARD`, `INVALID_CARD_LOST_OR_STOLEN`, `INVALID_CARD_EXPIRATION`, `INVALID_CARD_NUMBER`, `INVALID_REJECT_CARD`, `INVALID_BILL_KEY_REQUEST`, `NOT_SUPPORTED_CARD_TYPE`, `NOT_REGISTERED_CARD_COMPANY`, `EXCEED_MAX_AUTH_COUNT`, `KYC_BLOCKED` | **자동 재시도를 멈춘다.** 즉시 메일: 카드를 바꾸거나 이번 청구서를 계좌이체로. 새 카드가 등록되면 바로 결제. 메일에는 분실·정지 같은 사유를 적지 않고 "등록된 카드로 결제하지 못했습니다"라고만 쓴다 |
| 우리 쪽 설정 오류 | `UNAUTHORIZED_KEY`, `NOT_MATCHES_CUSTOMER_KEY`, `DUPLICATED_ORDER_ID`, `INVALID_REQUEST`, 할부 관련 코드, `BELOW_MINIMUM_AMOUNT`, `INCORRECT_BASIC_AUTH_FORMAT`, `FAILED_DB_PROCESSING` | 재시도하지 않는다. 고객 메일 없음, 확인 필요 큐와 운영 알림. 고객 잘못이 아니므로 고칠 때까지 그 청구서의 납기를 미룬다(유예가 흐르지 않는다) |

목록에 없는 코드는 "사유를 알 수 없는 거절"로 다룬다.

**메일 시점**: 첫 실패 직후, D+5 실패, D+9 실패("○일 뒤 새 생성이 중단됩니다"), D+13 실패(마지막 자동 시도였음을 알림), D+15 중단 안내. 받는 사람은 소유자와 관리자다.

**멱등과 응답 유실**

- 시도 1건 = 시도 행 1개 = 주문번호(행 UUID) 1개 = 멱등 키 1개(`brand-charge-{시도 id}`). 재시도는 항상 새 시도 행이다. 토스는 오류 뒤 키를 바꿔 같은 주문을 다시 보내지 말라고 안내한다.
- 승인 요청 전에 시도 행을 `charging`으로 바꾸고 임대 시간(lease)을 건다. 타임아웃은 60초 이상.
- 응답이 없거나 409(`IDEMPOTENT_REQUEST_PROCESSING`)면 실패로 적지 않는다. 같은 키로 다시 요청하거나 `GET /v1/payments/orders/{주문번호}`로 조회해 `DONE`이면 `done`, 승인 기록이 없으면 `failed`로 맞춘다. 판정이 안 되면 `review`로 두고 **새 시도를 만들지 않는다**(이중 결제 방지).
- 청구서당 열려 있는 시도는 1건, `done`은 1건만(부분 유니크 인덱스). 청구서가 `paid`·`void`·`refunded`면 새 승인을 보내지 않는다.

## 6. 크레딧

요구는 "마진 계산에 오류가 없을 것"이다. 아래 숫자는 저장소의 상수에서 계산했고, 표는 스크립트로 돌린 결과다. 입력값과 식을 같이 적는다.

### 6.1 지금 차감되는 크레딧과 원가

**입력값(코드 상수)**

- 1크레딧 = 이용액 10원: `STUDIO_CREDIT_KRW = 10` (`lib/brand-studio/credits.ts`)
- 환율 1,400원/USD, 이미지·오디오 배수 1.12, 영상 배수 1.11: `STUDIO_USAGE_FACTORS` (`lib/brand-studio/usage-rate.ts`)
- 원가는 결과 1건마다 센트 단위로 올린다: `billedUsd(usd) = 올림(usd × 100) ÷ 100` (`lib/brand-studio/models.ts`)
- 차감액: `usageKrw = 올림(billedUsd × 1,400 × 배수 ÷ 10) × 10`. 고객이 내는 크레딧은 레인(계정·API)과 무관하게 견적 그대로다. 제공사 실제 청구액은 `cost_usd`에만 기록된다.

**모델별 표** (원화 원가 = 올림한 USD × 1,400, 마진율 = (크레딧 × 10 − 원화 원가) ÷ (크레딧 × 10))

Seedream 5.5 2K 한 장을 식으로 따라가면: 정가 $0.035 → 센트 올림 $0.04 → × 1,400 = 56원 → × 1.12 = 62.72원 → ÷ 10 올림 = **7크레딧(70원), 원가 56원, 마진 20%**. 참조 이미지를 2~3장 붙이면 10크레딧, 원가 84원이다.

**최악의 크레딧당 원가.** `usageKrw ≥ billedUsd × 1,400 × 배수`이므로 원가 ÷ 이용액 ≤ 1 ÷ 배수다. 배수가 가장 작은 영상 기준으로 **크레딧당 원가는 10 ÷ 1.11 = 9.0090원을 넘지 않는다**(이미지·오디오는 10 ÷ 1.12 = 8.9286원). 아래 계산은 전부 9.0090원을 쓴다.

**"한도를 월 요금과 같게 잡으면 마진 약 10%"의 근거.** 따로 조사한 문서는 찾지 못했다. 위 배수에서 바로 나오는 값이다: 이미지 1 − 1/1.12 = 10.7%, 영상 1 − 1/1.11 = 9.9%. 즉 지금 차감표에는 마진이 10% 남짓만 들어 있고, 나머지 마진은 플랜이 주는 크레딧 수로 정해야 한다.

**이 식에 들어 있지 않은 원가**(크레딧으로 묶이지 않는다. §6.6의 월 원가 점검으로 본다)

- 제공사가 청구했지만 고객에게는 차감하지 않는 실패·차단·재시도.
- 크레딧을 받지 않는 기능: Prompt Architect, 말로 편집, 영상 분석, 가사 초안, 내보내기.
- 원가와 연결되지 않은 고정 차감: 업스케일(로컬 GPU), 효과음(코드에 USD 상수 없음, 문서상 초당 $0.002).
- 저장 용량(200 / 400 / 800 GB)과 전송.
- 실제 환율이 1,400원보다 높을 때의 차이(§6.3 민감도).

### 6.2 구조 — 차감표는 그대로, 플랜 크레딧 수로 마진을 잡는다

- 크레딧 단위(10원)와 모델별 차감표는 바꾸지 않는다. 가격 코드에 손을 대지 않으므로 계산 오류가 들어갈 자리가 없다.
- 플랜은 매달 크레딧을 준다. 값은 `brand_plan_allowance_defaults.monthly_cap_krw`에 넣는다(크레딧 × 10원). 지금 있는 관리자 오퍼레이션(`brandBilling.planDefault.set`)으로 들어간다.
- 고객이 크레딧 1개에 내는 값은 `월 이용료 ÷ 월 크레딧`이다. 이 값과 9.0090원의 차이가 마진이다.
- 차감 순서: 플랜 크레딧 → 추가 팩·체험 크레딧(만료가 가까운 것부터).

### 6.3 플랜별 월 기본 크레딧

**기준(대표 결정 2026-11-23): 마진 10~12%.** 카드로 결제해도 10~12%가 남도록 잡는다. 고객사 할인은 크레딧 수를 정하는 데 넣지 않는다. 할인은 영업 비용으로 따로 본다.

**식**

```
카드 수수료   = 올림(월 이용료 × 1.1 × 0.0374)        (부가세 포함 결제액 기준)
계좌이체 수수료 = 440원 (가상계좌 공개 요금, 수동 입금은 0원)
최악 원가     = 크레딧 × 10 ÷ 1.11
마진         = 월 이용료(부가세 제외) − 결제 수수료 − 최악 원가
목표 마진 m에서의 크레딧 = 내림((월 이용료 × (1 − m) − 카드 수수료) × 1.11 ÷ 10), 500 단위로 내림
```

**세 가지 안**

**결정됨(2026-11-23): 월 27,000 / 46,000 / 65,000 크레딧.** 운영 DB의 플랜 기본 한도로는 270,000 / 460,000 / 650,000원이다(크레딧 × 10원, `brandBilling.planDefault.set`). 세 플랜 모두 10~12% 안에 있고, 숫자가 외우기 쉽고, 높은 플랜일수록 크레딧 1개 값이 조금 싸다(10.74 → 10.65 → 10.62원).

**기준을 계좌이체로 잡으면 안 되는 이유.** 계좌이체 수수료(440원)로 10~12%를 맞추면 크레딧이 28,000~28,500 / 47,500~48,500 / 67,000~68,500으로 늘고, 같은 고객이 카드로 내면 마진이 6.4~8.9%로 내려간다.

**이 마진에서 지켜야 하는 것**

1. **모델별 차감 하한을 테스트로 고정**한다(§6.6-1). 새 모델이 배수 1.11보다 낮게 들어오면 빌드가 깨진다.
2. **일할은 돈과 크레딧에 같은 비율로**(§6.4). 지금 코드는 첫 달 이용료만 일할하고 크레딧은 한 달 치를 다 준다. 30일짜리 달의 28일에 시작한 고객이 29,000원을 내고 27,000크레딧(원가 최대 243,243원)을 받는 구멍이다. 구독을 열기 전에 반드시 고친다.
3. **미납 중 크레딧 제한**(§6.4, 결정됨).
4. **월 원가 점검은 필수다**(§6.6-8). 마진이 10~12%면 §6.1의 "식에 들어 있지 않은 원가"(무료 기능, 실패·차단 청구분, 저장 공간, 환율)가 마진의 큰 부분을 차지할 수 있다. 재 보기 전에는 실제 마진을 알 수 없다.
5. **환율 상수 갱신 절차.** 분기마다, 그리고 월평균 환율이 상수(1,400원)에서 3% 넘게 벗어나면 `STUDIO_USAGE_FACTORS.krwPerUsd`를 실제 환율로 고치고 이 절의 표를 다시 계산한다. 상수를 올리면 차감 크레딧이 같이 올라 마진율이 돌아온다. 고객이 보는 차감량이 바뀌므로 약관 초안 제12조 ④의 사전 통지를 거친다.

### 6.6 마진 오류를 막는 검증 (구현 때 넣는다)

1. **모델별 하한.** `STUDIO_MODELS`의 모든 모델 × 옵션(해상도·길이·참조 수)에 대해 `usageKrw ≥ billedUsd × krwPerUsd × 1.11`. 고정 차감 항목(업스케일·효과음)은 원가 상수를 코드에 적고 같은 단언에 넣는다.
2. **플랜 크레딧.** 세 플랜 모두 `크레딧 × 10 ÷ 1.11 + 카드 수수료 ≤ 월 이용료 × (1 − 0.10)`. 확정 크레딧의 값: 255,174 ≤ 261,000 / 434,573 ≤ 441,000 / 613,973 ≤ 621,000.
3. **상수 고정.** 환율 1,400, 배수 1.12·1.11, 카드 요율, 플랜 금액, 플랜 크레딧을 한 테스트에 값으로 적는다. 하나라도 바뀌면 "이 문서 §6.3 표를 다시 계산하라"는 메시지와 함께 실패한다.
4. **일할 속성 테스트.** 임의의 시작일·변경일에 대해 받은 이용료 대비 준 크레딧의 비율이 한 달 전체일 때보다 높지 않다(첫 달, 플랜 올림).
5. **환불 속성 테스트.** 임의의 사용 크레딧·경과 일수에 대해 `남긴 금액 ≥ min(결제한 이용료, 사용 크레딧 × 9.0090)`.
6. **체험·팩.** `체험 크레딧 × 10 ÷ 1.11 ≤ 9,000`, 팩의 크레딧 1개 값 ≥ 플랜의 크레딧 1개 값의 최댓값, 팩의 카드 마진 ≥ 10%.
7. **공개 숫자 일치.** 공개 요금 페이지·`/brand/billing`·DB 플랜 기본값이 같은 상수를 쓴다.
8. **월 원가 점검(필수, 구독을 열기 전에 켠다).** 조직·월별로 `cost_usd` 합계 × 실제 환율과 이용액을 비교해 관리자 화면에 보여 준다. 함께 보는 것: 차감 없이 나간 원가(실패·차단·재시도, 무료 기능), 저장 용량. 조직의 원가가 이용액의 90.1%(= 1 ÷ 1.11)를 넘거나, 전체 마진이 10% 아래로 내려가면 운영 알림을 보낸다. 테스트가 못 잡는 §6.1의 "식에 들어 있지 않은 원가"를 여기서만 볼 수 있다.

  (마진 = 6개월 공급가액 − 수수료 − 월 크레딧 × 10 ÷ 1.11 × 6. 예: 1,479,000 − 0 − 243,243.24 × 6 = 19,541원.) 이 표는 환율 1,400원 기준이다. 실제 환율이 1,419 / 1,407 / 1,402원을 넘으면 다 쓰는 선결제 고객에게서 손실이 난다(§6.3의 환율 갱신 절차와 §6.6-8의 월 원가 점검이 여기서 가장 먼저 걸린다).
- **참고 — 카드로 받았다면**: 6개월에 −41,306 / −90,295 / −139,286원이다(1,479,000 − 올림(1,626,900 × 0.0374) − 1,459,459 = −41,306원). 계좌이체로만 받기로 한 이유다.
- **고객사 할인과 겹치지 않는다 — 결정됨.** 둘 다 이용료를 깎는 것이라 큰 쪽 하나만 적용한다.
- **중도 해지 환불 — 결정됨**: `환불액 = 선결제 공급가액 − (이용한 달 수 × 정가 월 이용료) − 진행 중인 달의 일할 이용액(정가 기준)`, 0원 미만이면 0원. 쓴 기간은 할인 전 값으로 다시 계산한다는 뜻이다.

  | 해지 시점 | 290,000원 | 490,000원 | 690,000원 |
  | --- | --- | --- | --- |
  | 1개월 뒤 | 1,189,000원 | 2,009,000원 | 2,829,000원 |
  | 3개월 뒤 | 609,000원 | 1,029,000원 | 1,449,000원 |
  | 5개월 뒤 | 29,000원 | 49,000원 | 69,000원 |

  (공급가액 기준, 부가세는 같은 비율로 돌려준다.) 할인을 되돌리는 방식이 약관규제법 제9조(원상회복 의무의 과중 부담)와 토스 계약의 "이용 일수 비례"에 맞는지는 법무 확인이 필요하다.
- **크레딧은 매달 지급 — 결정됨.** 6개월 치를 한 번에 주지 않는다(§6.4).
- **선결제 중 플랜 변경**: 올림은 즉시, 남은 기간의 차액을 15% 할인된 값으로 일할해 추가 청구(계좌이체). 내림은 6개월이 끝난 뒤부터.
- **끝난 뒤**: 자동으로 다시 6개월을 청구하지 않는다. 끝나기 30일 전에 알리고, 답이 없으면 월 결제(그 조직의 받는 방법)로 이어진다.
- **세금계산서**: 받은 날 전액으로 한 장(§2.4). 신고 시기는 세무 대리인 확인.
- **정산한도**: 회사 계좌로 직접 받으면 한도와 무관하다. 입금 전용 계좌(가상계좌)로 받으면 단건 MID의 월 1,000만 원 한도에 들어가고, 290,000원 플랜 6건, 490,000원 3건, 690,000원 2건이면 찬다. 그래서 선결제는 가상계좌 자동 확인을 켠 뒤에도 회사 계좌 입금을 기본으로 둔다(제안).

## 8. 세금계산서 — 홈택스 수기 (대표 결정)

1. 계좌이체 청구서가 발행되면 관리자 화면의 "이번 달 발행할 것" 목록에 올라온다. 공급가액·세액·고객사 세금계산서 정보(상호, 사업자등록번호, 대표자, 주소, 수신 메일)를 그대로 보여 준다.
2. 관리자가 홈택스에서 전자세금계산서를 발행하고, 발행일과 승인번호를 그 청구서에 적는다. 적기 전까지 목록에 남는다.
3. 고객의 `/brand/billing`에는 "세금계산서 발행됨(발행일)"만 보인다. 세금계산서 자체는 국세청이 고객 메일로 보낸다.
4. 환불·금액 정정이 생기면 확인 필요 큐에 "수정 세금계산서 필요"로 올린다.
5. 카드로 결제한 청구서는 이 목록에 올라오지 않는다(매출전표가 증빙). "이번 청구서만 계좌이체"로 바꿔 낸 건은 올라온다.

작성일을 발행일로 할지 입금일로 할지는 세무 대리인 확인 뒤 정한다(§15.2-3). 한 달 발행 건수가 손으로 하기 어려워지면 발행 대행 API를 붙인다. 그때도 2번의 기록 칸은 그대로 쓴다.

## 9. 스키마 초안

번호는 구현 시작 때 `origin/main`에서 다시 확인한다(지금 다음 빈 번호 0182, 0174·0175는 다른 브랜치 예약). 전부 RLS deny-all, service role만 쓴다(0177과 같은 방식).

  organization_id uuid primary key references organizations(id),
  environment text not null check (environment in ('test','live')),

  organization_id uuid not null, environment text not null,
  customer_key text not null unique,         -- 무작위 값. 조직 id를 쓰지 않는다
  billing_key_cipher text not null,
  card_company text, card_last4 text, owner_type text,
  status text not null check (status in ('active','replaced','revoked')),
  registered_by uuid not null, created_at timestamptz not null default now()

create unique index brand_payment_methods_one_active
  on brand_payment_methods (organization_id, environment) where status = 'active';

alter table brand_invoices
  add column kind text not null default 'subscription'
    check (kind in ('subscription','adjustment','prepay','credit_pack')),
  add column covers_months integer not null default 1,
  add column due_on date,

create unique index brand_invoice_payments_one_open

alter table brand_allowance_grants           -- 체험·팩·올림 크레딧(§6.4, §6.5)

## 13. 형식 검증 (AGENTS.md §11)

결제 상태 전이와 크레딧이라 대상이다. TLA+/TLC 모델 두 개와 Lean(또는 속성 테스트) 하나를 만든다.

1. **청구서 × 결제 시도.** 사건: 발행, 카드 승인 성공·실패·응답 유실, 사유별 재시도, 가상계좌 발급·입금·만료·취소·되돌림, 웹훅 중복·지연·순서 뒤바뀜, 받는 방법 전환, 수동 입금 확인, 환불. 불변 조건: 청구서가 `paid`이면 `done` 시도가 정확히 1건이고 금액이 같다 / `done`이 2건이 되는 경로가 없다 / `paid`·`void`·`refunded` 청구서에 새 승인이 나가지 않는다 / 응답을 모르는 시도가 있는 동안 새 시도가 생기지 않는다 / 할인 회차 사용 수 = 취소되지 않은 발행 청구서 수.
2. **이용 가능 기한.** 불변 조건: 새 생성이 닫히는 것은 가장 오래된 미납 청구서의 "납기 + 유예"가 지났을 때뿐이다 / 결제가 확인되면 다음 판정에서 반드시 열린다 / 해지 예약은 결제된 기간을 줄이지 않는다 / 우리 쪽 설정 오류로 실패한 결제는 유예를 흐르게 하지 않는다.
3. **크레딧 산술**(§6.6의 2·4·5·6). 일할·올림·환불·팩에서 "받은 돈 ≥ 준 크레딧의 최악 원가 ÷ (1 − 목표 마진)"이 유지되는지. 정수 내림이 섞여 있어 손으로 확인하기 어렵다.

규칙은 이 문서 §5·§6과 토스 계약 제42조에서 정의한다. 일부러 틀린 조건(예: 전환 때 가상계좌를 취소하지 않음, 첫 달 크레딧을 일할하지 않음)을 넣어 반례가 나오는지 확인한다. 이 PC에는 TLC·Lean이 설치되어 있지 않다. 설치 전에는 "미실행"으로 보고하고, 같은 불변 조건을 vitest 속성 테스트로 먼저 건다.

**B1은 남은 결정을 기다리지 않는다.** B1이 쓰는 값(플랜 크레딧, 체험 400, 미납 50%, 14일·14일, 선결제 규칙)은 모두 결정됐다. 남은 결정(§15.2)은 B2(고객에게 보이는 약관·문구)와 B5(추가 팩 가격)에서 필요하다. B1 전에 할 일: 마이그레이션 번호 재확인과 클라우드 적용 주체 확인, `BRAND_PLAN_GRACE_DAYS`를 14로 바꾸면 손으로 관리하는 조직의 유예도 14일이 된다는 점 확인, 크레딧 일할은 구독 조직에만 적용해 기존 조직의 한도가 바뀌지 않게 할 것, 월 원가 점검(§6.6-8)을 B1 범위에 넣을 것.

B3와 B4는 서로 기다리지 않는다. 토스 회신이 먼저 오는 쪽부터 한다. 계좌이체가 기본이므로 **B1·B2만으로 출시할 수 있다**: 매달 자동 청구 + 계좌이체(수동 입금 확인) + 세금계산서 수기.

## 17. 확인하지 못한 것

- §16의 일곱 가지(토스 회신 전).
- **Higgsfield의 플랜 가격, 플랜별 크레딧 수, 모델별 차감표, 팩 가격.** 요금 페이지가 스크립트로 그려져 읽지 못했다. 구조(이월 없음, 팩 90일, 차감 순서, 플랜 변경)는 공개 도움말에서 확인했다. 다른 사이트의 숫자로 채우지 않았다.
- **토스 에러 코드의 재시도 가능 분류.** 토스의 공식 분류가 없어 메시지를 보고 나눴다. 타임아웃 뒤 주문을 조회하라는 명시 문구도 찾지 못했다(조회 API와 멱등 키 동작은 문서에 있다).
- **실제 환율과 제공사 실제 청구액.** 마진표는 코드 상수(1,400원, 정가의 센트 올림)로 계산했다. 운영 DB의 `cost_usd`와 대조하지 않았다.
- **식에 없는 원가의 크기**(§6.1): 실패·재시도, 크레딧을 받지 않는 기능, 로컬 GPU, 저장 용량. 숫자를 재지 않았다. 마진이 10~12%라서 이 원가가 크면 실제 마진은 표보다 낮거나 음수일 수 있다. 월 원가 점검(§6.6-8)을 켜기 전에는 알 수 없다.
- 부가가치세법 시행령에서 "세금계산서를 발급하지 않는 사업자"의 범위를 정한 조문과, 선납 계속 용역의 신고 시기(시행령 제29조 ② 3호 해당 여부). 세무 대리인 확인 대상이다.
- 카드 정기결제의 동의·고지를 직접 정한 법률 조항(여신전문금융업법 본문에서는 찾지 못했다).
- 팝빌·바로빌의 건당 단가.
- 브랜드 워크스페이스 화면에 사업자 정보가 표시되는지는 코드 검색으로만 봤다(결과 없음).
- 형식 검증 도구(TLC·Lean)는 이 PC에 없어 모델을 돌리지 않았다. 설계 단계라 모델도 아직 없다.
